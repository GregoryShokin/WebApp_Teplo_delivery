# Saby / SBIS EDO API endpoint map

Дата фиксации: 2026-05-19.

Статус рабочего контура: доступ к реальному кабинету СБИС ЭДО не проверен, потому что в локальном `.env` нет переменных SBIS/Saby/Tensor/EDO с учетными данными или токеном.

## Назначение

Этот документ - локальная карта API СБИС ЭДО для проекта "Тепло". Цель карты - подготовить read-only контур получения входящих электронных документов от поставщиков и подрядчиков:

- счета;
- УПД;
- накладные;
- акты;
- счета-фактуры;
- входящие документы с XML, вложениями и печатными формами.

Данные нужны для P&L: закупки, себестоимость, поставщики, НДС, даты, номера документов, статусы и товарные строки.

Первый бизнес-фокус: строки ОПиУ, которые владелец подтвердил как источник `ЭДО DocsInbox / СБИС`. Обновление 2026-05-22: `Таргетированная реклама` выведена из первичного СБИС-контура, потому что источник суммы и периода найден в WorkMail `smmbux@yandex.ru`: письмо `Документы для ИП Шокина Кристина Юрьевна...` с УПД по абонентскому обслуживанию/продвижению и рекламному бюджету. СБИС для нее остается только резервной документной сверкой.

| Строка ОПиУ | Целевой источник |
| --- | --- |
| `Таргетированная реклама` | резервная сверка; первичный источник ОПиУ — WorkMail `smmbux@yandex.ru`, письмо с УПД от ИП Билинский |
| `Наружная реклама` | входящие документы СБИС/DocsInbox |

## Безопасность

- Никогда не писать в Markdown, чат, логи и raw-файлы логины, пароли, токены, session id, app secret, refresh/access token, cookie и полные authorization headers.
- Секреты хранить только в `.env` или в безопасном хранилище, не переносить их в документацию.
- Для аналитики использовать только read-only методы: списки, чтение карточки, скачивание вложений.
- Не вызывать методы, которые меняют состояние документооборота: `СБИС.ЗаписатьДокумент`, `СБИС.ЗаписатьВложение`, `СБИС.ПодготовитьДействие`, `СБИС.ВыполнитьДействие`, `СБИС.ПодписатьВложение`, `СБИС.УдалитьДокумент`, `СБИС.УничтожитьДокумент`, `СБИС.ПовторитьЭтап`.
- Не подписывать, не принимать, не отклонять, не отправлять и не менять статусы документов.
- Первый тест после получения доступа делать за период не больше 7 дней, страница 5-25 документов.
- Raw-ответы сохранять в `research/raw/sbis/edo/` только после удаления секретов и временных ссылок, если ссылка раскрывает доступ без заголовков.
- В рабочую документацию переносить только агрегат: endpoint, HTTP/API-статус, число документов, типы документов, набор полей.

## Статус авторизации в нашем контуре

Авторизация в рабочем СБИС не выполнялась.

Причина: в `.env` нет ни production base URL с SBIS-переменными, ни логина/пароля, ни service app credentials, ни access token/session id. Выполнять запросы без явного production-доступа нельзя: задача требует реальный рабочий контур, а не песочницу.

Минимальный read-only тест после получения доступа:

1. Авторизоваться сервисным приложением или техническим пользователем.
2. Выполнить `СБИС.СписокНашихОрганизаций` и убедиться, что нужная организация доступна и ЭДО подключен.
3. Запросить `СБИС.СписокДокументовПоСобытиям` по реестру `Входящие` за последние 7 дней или согласованный короткий период.
4. Сохранить очищенный raw-ответ в `research/raw/sbis/edo/`.
5. В этот файл занести только агрегат: статус, количество документов, типы, поля.

## Что нужно для авторизации

Если доступов нет, запросить у владельца:

| Что запросить | Зачем |
| --- | --- |
| URL/домен рабочего кабинета СБИС или базовый API URL | зафиксировать production-контур |
| Тип авторизации: логин/пароль, OAuth/service app, client/secret, сертификат, готовый токен | выбрать безопасный сценарий |
| Логин технического пользователя или приложение СБИС | отделить интеграцию от личной учетной записи |
| Права только на чтение ЭДО | не давать агенту возможность подписывать/отклонять документы |
| ИНН/КПП нашей организации или список организаций в СБИС | фильтр документов и выбор ящика |
| Разрешение читать входящие документы, XML, вложения и печатные формы | P&L требует товарные строки и первичку |
| Ограничения 2FA/сертификата/МЧД/доверенности | понять, будет ли интерактивный блокер |

Предпочтительный вариант: отдельное внешнее приложение Saby с сервисной авторизацией и read-only доступом к нужным участкам ЭДО. Официальная справка описывает получение `token` по `app_client_id`, `app_secret`, `secret_key` и дальнейшую передачу токена в заголовке `X-SBISAccessToken`.

Альтернатива: технический пользователь с логином/паролем. В этом случае API возвращает session id, который нужно передавать в `X-SBISSessionID`. Если включена SMS/2FA или сертификат, автоматический read-only тест блокируется до ручного подтверждения или выдачи сервисного доступа.

## Рецепты read-only запросов

Все команды API ЭДО используют JSON-RPC 2.0. Для пользовательской сессии передается `X-SBISSessionID`, для сервисного приложения - `X-SBISAccessToken`.

Шаблон JSON-RPC:

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.СписокДокументовПоСобытиям",
  "params": {
    "Фильтр": {}
  },
  "id": 1
}
```

Шаблон `curl` без раскрытия секретов:

```bash
curl -sS -X POST "$SBIS_SERVICE_URL" \
  -H "Content-Type: application/json-rpc;charset=utf-8" \
  -H "User-Agent: teplo-business-control/0.1" \
  -H "X-SBISAccessToken: $SBIS_ACCESS_TOKEN" \
  --data-binary @request.json
```

Для пользовательской авторизации заменить заголовок на:

```text
X-SBISSessionID: $SBIS_SESSION_ID
```

Сервисная авторизация приложения:

```bash
curl -sS -X POST "$SBIS_AUTH_URL" \
  --data-urlencode "app_client_id=$SBIS_CLIENT_ID" \
  --data-urlencode "app_secret=$SBIS_CLIENT_SECRET" \
  --data-urlencode "secret_key=$SBIS_SECRET_KEY"
```

В документации и raw-файлах не сохранять ответ целиком, если в нем есть токен.

## Получение списка документов

Базовый метод для первого read-only теста: `СБИС.СписокДокументовПоСобытиям`, потому что он возвращает реестр `Входящие`, `Исходящие` или `Ответы от контрагентов` и не требует заранее знать тип документа.

Черновой фильтр для входящих за короткий период:

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.СписокДокументовПоСобытиям",
  "params": {
    "Фильтр": {
      "ТипРеестра": "Входящие",
      "ДатаС": "13.05.2026",
      "ДатаПо": "19.05.2026",
      "НашаОрганизация": {
        "СвЮЛ": {
          "ИНН": "$SBIS_ORGANIZATION_INN",
          "КПП": "$SBIS_ORGANIZATION_KPP"
        }
      },
      "Навигация": {
        "РазмерСтраницы": "25",
        "Страница": "0"
      }
    }
  },
  "id": 1
}
```

Если метод вернет ошибку по именам полей дат или реестра, сверить с актуальным примером в Saby и зафиксировать рабочий вариант в разделе "Практически проверенные endpoint'ы".

Альтернативный метод: `СБИС.СписокДокументов`. Он полезен, когда известен `Тип` документа. Обязательные/важные фильтры из справки:

| Поле фильтра | Смысл |
| --- | --- |
| `ДатаС`, `ДатаПо` | период документа |
| `Тип` | тип документа, обязательный для метода |
| `Направление` | `Входящий` или `Исходящий` |
| `НашаОрганизация` | наша организация/ИП |
| `Контрагент` | поставщик/подрядчик |
| `Состояние` | текстовое состояние |
| `Навигация.РазмерСтраницы` | 1-200, по умолчанию 20 |
| `Навигация.Страница` | с 0 |

Поля ответа, полезные для P&L:

| Поле | Что дает |
| --- | --- |
| `Документ[].Идентификатор` | ключ для чтения карточки |
| `Дата`, `Номер`, `Сумма`, `Название` | базовые реквизиты |
| `Тип`, `Направление`, `Состояние` | классификация и контроль |
| `НашаОрганизация` | наш ИНН/КПП/название |
| `Контрагент` | поставщик, ИНН/КПП, название |
| `Вложение[]` | XML/УПД/акт/счет-фактура/накладная |
| `СсылкаНаАрхив` | архив документа, вложений и подписей |

## Получение карточки документа

Метод: `СБИС.ПрочитатьДокумент`.

Использовать только если списка недостаточно для классификации, сверки суммы или получения ссылок на вложения. Официальная справка предупреждает, что метод обрабатывает большой объем данных; при перегрузке в ответе может появиться `ЧастичныеДанные=Да`, а недостающие данные нужно дочитывать через `СБИС.СписокИзменений`.

Шаблон:

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.ПрочитатьДокумент",
  "params": {
    "Документ": {
      "Идентификатор": "<document_id>"
    }
  },
  "id": 2
}
```

Что сохранить в агрегат:

| Поле | Назначение |
| --- | --- |
| `Документ.Идентификатор` | стабильная ссылка |
| `Редакция[].Идентификатор` | версия документа |
| `Состояние.Код`, `Состояние.Название` | статус |
| `Вложение[]` | список формализованных и неформализованных файлов |
| `Вложение[].Файл.Имя` | имя XML/PDF/другого файла |
| `Вложение[].Файл.Ссылка` | скачать файл; в Markdown не переносить полную ссылку, если она временно авторизует доступ |
| `СсылкаНаPDF`, `СсылкаНаАрхив` | печатная форма/архив |

## Получение XML, вложений и печатной формы

Файлы скачиваются `GET`-запросом по ссылкам из объекта документа:

| Поле | Что скачать |
| --- | --- |
| `Документ.СсылкаНаАрхив` | архив последней редакции документа, вложений и ЭП |
| `Документ.СсылкаНаPDF` | единое PDF-представление документа, если доступно |
| `Документ.Вложение[].Файл.Ссылка` | бинарные данные вложения: XML, PDF, scan, подпись |
| `Документ.Вложение[].СсылкаНаHTML` | HTML-представление формализованного вложения |
| `Документ.Вложение[].СсылкаНаPDF` | PDF-представление вложения |

Ссылки на вложения и электронные подписи в списочных методах действуют ограниченное время: официальная справка указывает срок один месяц. Для локального архива нужные XML/PDF надо скачивать во время выгрузки, а не хранить только ссылку.

PDF/HTML-представление может генерироваться асинхронно. Если первый `GET` вернул ошибку генерации, повторять с интервалом 3-5 секунд и ограничением числа попыток.

## Получение строк накладной / УПД

API-список возвращает реквизиты документа и вложений, но не гарантирует нормализованные товарные строки в JSON. Для P&L строки нужно получать из формализованного XML-вложения.

Практический алгоритм:

1. Найти входящий документ через `СБИС.СписокДокументовПоСобытиям` или `СБИС.СписокДокументов`.
2. Из ответа взять `Документ.Идентификатор` и вложения с типами/подтипами УПД, счет-фактура, накладная, акт.
3. Через `СБИС.ПрочитатьДокумент` получить актуальные ссылки, если в списке недостаточно данных.
4. Скачать XML по `Вложение[].Файл.Ссылка`.
5. Распарсить XML структурным парсером, не regex.
6. Нормализовать строки в таблицу:

| Поле нормализации | Источник |
| --- | --- |
| `document_id` | `Документ.Идентификатор` |
| `revision_id` | `Редакция.Идентификатор` |
| `document_date` | `Документ.Дата` или дата вложения |
| `document_number` | `Документ.Номер` или номер вложения |
| `supplier_inn`, `supplier_kpp`, `supplier_name` | `Контрагент` или XML |
| `buyer_inn`, `buyer_kpp`, `buyer_name` | `НашаОрганизация` или XML |
| `line_number` | номер строки XML |
| `item_name` | наименование товара/услуги |
| `unit_code`, `unit_name` | единица измерения |
| `quantity` | количество |
| `price_without_vat` | цена без НДС |
| `amount_without_vat` | сумма без НДС |
| `vat_rate` | ставка НДС |
| `vat_amount` | сумма НДС |
| `amount_with_vat` | сумма с НДС |
| `origin_country`, `customs_declaration` | если есть в XML |

Для УПД/счетов-фактур ФНС типовые товарные строки обычно лежат в табличной части XML. Точные XPath и названия тегов зафиксировать после первого raw-снимка, потому что формат зависит от типа и версии вложения.

## Организации и контрагенты

Первый read-only справочный вызов после авторизации:

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.СписокНашихОрганизаций",
  "params": {
    "Фильтр": {
      "Навигация": {
        "РазмерСтраницы": "50",
        "Страница": "0"
      }
    }
  },
  "id": 3
}
```

Ожидаемые поля:

| Поле | Значение |
| --- | --- |
| `НашаОрганизация[].СвЮЛ.ИНН` | наш ИНН |
| `НашаОрганизация[].СвЮЛ.КПП` | наш КПП |
| `НашаОрганизация[].СвЮЛ.Название` | юридическое лицо |
| `ДокументооборотПодключен` | `Да/Нет`, подключен ли ЭДО |

Фильтр `НашаОрганизация` в документах:

- если `КодФилиала` не указан, могут возвращаться документы организации и филиалов;
- если `КодФилиала` передан пустой строкой, ожидается только головная организация без филиалов;
- если указан код филиала, ожидаются документы филиала.

Фильтр `Контрагент`:

- для юрлица использовать `СвЮЛ.ИНН`, `СвЮЛ.КПП`, при необходимости `КодФилиала`;
- если передать только ИНН, могут вернуться контрагенты с разными КПП/филиалами;
- для ИП/физлиц использовать `СвФЛ.ИНН`.

Для P&L нужен отдельный маппинг:

| Ключ | Назначение |
| --- | --- |
| ИНН/КПП контрагента | стабильная привязка поставщика |
| название контрагента | контроль переименований |
| тип/подтип документа | отделить УПД, акт, счет, счет-фактуру |
| ключевые слова в названии/примечании | классификация маркетинга/SEO/сайта |
| статья ОПиУ | целевая P&L-строка |

## Статусы документов

В API документ содержит объект `Состояние`:

| Поле | Смысл |
| --- | --- |
| `Состояние.Код` | числовой/строковый код статуса |
| `Состояние.Название` | человекочитаемый статус, например `Доставлен` |
| `Состояние.Примечание` или `Комментарий` | ошибка/комментарий, если есть |
| `Удален` | `Да/Нет` |

Для P&L на первом этапе не менять статусы и не выполнять переходы. В расчет брать только документы, которые не удалены и не являются явным черновиком/ошибкой. Точное правило по статусам зафиксировать после первого списка документов, потому что реальные названия статусов зависят от регламента.

Контрольные правила:

| Ситуация | Действие |
| --- | --- |
| `Удален=Да` | исключить или вынести в ручную проверку |
| статус содержит отклонение/ошибку | ручная проверка |
| документ без суммы | ручная проверка, возможно сумма только во вложении |
| несколько вложений с суммами | не дублировать сумму документа и сумму вложений |
| корректировка/отрицательная сумма | отдельная категория корректировок |

## Ограничения и риски

- Нет production-доступа в `.env`, поэтому рабочая авторизация не проверена.
- Логин/пароль может требовать SMS/2FA; сертификатный вход требует СКЗИ и ручной/инфраструктурный контур.
- Пользовательская сессия ограничена: в справке указаны лимиты по числу сессий и частоте аутентификации.
- В API-документации есть предупреждение не держать больше 5 параллельных потоков.
- Ссылки на вложения временные; архивировать надо сами файлы, а не ссылки.
- `СБИС.ПрочитатьДокумент` может вернуть частичные данные на тяжелых документах.
- `СБИС.СписокДокументов` требует знать `Тип`; для первого discovery лучше `СБИС.СписокДокументовПоСобытиям`.
- Товарные строки не считать надежно доступными из списочного JSON; целевой источник строк - XML.
- Для P&L надо согласовать дату признания расхода и правило по НДС.
- Документы могут иметь несколько редакций, корректировки, отрицательные суммы, дубли вложений и служебные файлы.

## Следующие действия

1. Получить у владельца production-доступ: service app read-only или технического пользователя без права подписания/изменения.
2. Добавить в `.env` только секреты и идентификаторы, без переноса значений в Markdown.
3. Выполнить read-only `СБИС.СписокНашихОрганизаций`.
4. Выполнить `СБИС.СписокДокументовПоСобытиям` за период не больше 7 дней, `ТипРеестра=Входящие`, маленькая страница.
5. Сохранить очищенный raw в `research/raw/sbis/edo/`.
6. Дочитать 1 документ через `СБИС.ПрочитатьДокумент`, если список вернул кандидат с УПД/актом/накладной.
7. Скачать 1 XML-вложение и зафиксировать фактические XPath товарных строк.
8. Обновить раздел "Практически проверенные endpoint'ы" фактическими статусами, количеством документов и списком полей.
9. Собрать маппинг контрагентов на P&L-строки маркетинга, SEO, сайта/приложения и поставщиков.
