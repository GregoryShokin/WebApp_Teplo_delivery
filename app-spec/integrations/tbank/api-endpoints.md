# T-Bank Business Open API endpoint map

Дата фиксации: 2026-05-19.

Статус рабочего контура: **подключен read-only с 2026-05-19**. В локальном `.env` заполнены `TBANK_API_BASE_URL`, `TBANK_API_ACCESS_TOKEN`, `TBANK_API_ACCOUNT_NUMBER`, `TBANK_API_ORGANIZATION_INN`; КПП отсутствует. Токен выпущен владельцем с доступом к счетам и операциям. Пилотная и целевая выгрузки `GET /api/v1/statement` успешно выполнены на промышленном контуре; сырые ответы лежат только в `research/private/tbank/`.

## Назначение

Этот документ — локальная карта T-Bank Business Open API (далее T-API) для проекта «Тепло». Его задача: чтобы следующие агенты не изучали заново общую витрину Т-Банка, а сразу понимали:

- где лежит официальная документация и как устроен портал разработчика;
- какие read-only endpoint'ы нужны для ДДС, P&L и аналитики поставщиков;
- как авторизоваться, какие scope-доступы выпускать в личном кабинете;
- какие форматы дат, лимиты, пагинация описаны в документации;
- какие переменные `.env` потребуются для подключения;
- какие вопросы нужно закрыть у владельца до первого боевого запроса.

## Важная бизнес-поправка о ролях банков

Факт (подтверждено владельцем 2026-05-19):

**Денежный контур работает как цепочка `Sber → T-Bank → контрагенты` с дополнительным небольшим прямым эквайрингом в T-Bank.**

1. **Sber — основная точка приёма выручки от коммерческой деятельности.** Сюда приходит большая часть денег от торгового эквайринга, интернет-эквайринга и других каналов приёма платежей.
2. **Перевод Sber → T-Bank.** Деньги из Сбера регулярно переводятся на расчётный счёт в Т-Банке. В T-API эти поступления видны как `incomePeople` / `incomeContragent` со счёта Сбербанка и **не являются отдельной выручкой**: это та же выручка, уже учтённая на стороне Sber.
3. **Прямой эквайринг T-Bank — небольшая, но ненулевая доля выручки.** Часть платежей клиентов приходит непосредственно на расчётный счёт в Т-Банке через собственный эквайринг T-Bank. Это **не внутренний перевод из Сбера**, а отдельная реальная выручка, которую нельзя смешивать ни с переводом Sber→T-Bank, ни с поступлениями на стороне Sber. Идентификация — по банку-отправителю (не Sber), категории операции и назначению платежа.
4. **T-Bank — точка распределения по контрагентам.** С расчётного счёта в Т-Банке производятся 98% исходящих операций: поставщики, выплаты сотрудникам, налоги, бизнес-карта, выводы. Поэтому **все статьи ДДС по расходам и весь справочник поставщиков управленческого ДДС находятся внутри T-Bank**.

Подтверждение из данных за `2026-02-01`–`2026-05-19`:

| Банк | Поступления | Списания | Net | Комментарий |
| --- | ---: | ---: | ---: | --- |
| Sber | 10,69 млн ₽ | 10,79 млн ₽ | -101k ₽ | Поступления — основная выручка эквайринга; большая часть списаний — переводы на T-Bank |
| T-Bank | 11,24 млн ₽ | 11,45 млн ₽ | -210k ₽ | Поступления — преимущественно переводы из Sber + небольшая доля собственного эквайринга T-Bank + редкие прочие; списания — поставщики, ФОТ, налоги |

Поэтому схожий объём поступлений по двум банкам — это в основном одно и то же движение в двух точках цепочки, но не полностью: часть T-Bank поступлений — это самостоятельная выручка, не отражённая в Sber.

Период:
актуально на 2026-05-19, подтверждено владельцем в рабочем чате.

Вывод:
- **Выручка управленческого ДДС 2026 = эквайринг Sber + эквайринг T-Bank.** Sber — основной канал; T-Bank-эквайринг учитывается отдельной строкой, чтобы не пропустить меньшую часть выручки и не задвоить за счёт переводов из Сбера.
- **Поступления в T-Bank нужно делить на три потока:**
  1. `internal_transfer_sber_to_tbank` — переводы из Sber (большая часть `incomePeople`/`incomeContragent` с банком-отправителем Sber). Исключаются из выручки и из ДДС поступлений.
  2. `tbank_acquiring_revenue` — собственный эквайринг T-Bank. Включается в выручку как отдельный канал.
  3. `other_inflow` — возвраты, кредиты, прочие поступления; статус `требует проверки`, классификация по реестру правил.
- **Расходы управленческого ДДС 2026 считаются по T-Bank API.** Это включает поставщиков, выплаты сотрудникам, налоги, бизнес-карту и комиссии.
- Сверку P&L по строкам ОПиУ с источником «ДДС классический» (Эквайринг, Транспортные услуги, Расходы на питание персонала, Оплаты систем автоматизации, РКО, Прочие банковские комиссии, Расходы на персонал, Поиск и найм персонала, Листовки, Прочие маркетинговые услуги, Комиссия за овердрафт, Штрафы и пени) нужно строить на выгрузке T-API, а не Sber API. Исключение — `Комиссия за эквайринг`, которая может удерживаться на стороне Sber и/или T-Bank: проверять оба банка отдельно.
- Старая копия Google Sheets `2026 ДДС — Классический • ИП Шокина` остаётся управленческой раскладкой; первичные суммы по расходам должны приходить из T-API, по выручке — из Sber API + T-API (эквайринг T-Bank).

Действие:
- В ETL-скриптах роли банков разделены явно: Sber = выручка эквайринга (по правилам), T-Bank = расходы + переводы из Sber + собственный T-Bank эквайринг.
- Для обоих банков нужна вторая стадия классификации поступлений: `выручка-эквайринг Sber`, `выручка-эквайринг T-Bank`, `прочее поступление`, `внутренний перевод Sber→T-Bank`, `кредит/овердрафт`, `возврат` и т.д.
- Для этой стадии нужен приватный реестр правил по описаниям поступлений/списаний. Безопасный шаблон: `research/processed/bank_operation_rules_template.csv`. В Markdown можно хранить только схему и нечувствительные примеры паттернов; реальные назначения платежей с персональными данными — только в `research/private/`.
- Признак внутреннего перевода `Sber→T-Bank`: получатель в T-Bank — собственный расчётный счёт ИП Шокиной в Т-Банке, отправитель — счёт в Sber (ИНН Сбербанка, BIC Sber). Список собственных счетов фиксируется в `research/private/` и обновляется по подтверждению владельца.
- Признак собственного эквайринга T-Bank: банк-отправитель в T-Bank ≠ Sber и не является сторонним обычным контрагентом-юрлицом; обычно платёж сопровождается признаками эквайринга в категории/назначении. Точный набор признаков подтвердить на разметке `research/processed/tbank/counterparty_summary.csv` отдельной итерацией.

## Безопасность

- Никогда не писать в Markdown, чат, логи и raw-файлы Bearer-токены, ИНН партнёров, номера счетов и любые секреты T-API.
- Секреты хранить только в `.env`.
- До отдельного разрешения владельца использовать только read-only сценарии: выписка, баланс, информация о счетах, контрагенты.
- Платежные методы включаются только отдельным флагом в `.env` и отдельным токеном/scope. Агент не должен подписывать платежи; целевой сценарий — отправить подготовленное платежное поручение в `Платежи в работе -> На подпись`, чтобы владелец подписал его в Т-Бизнесе.
- Метод `/api/v1/payment/create` не является целевым для этого сценария: он создает обычный банковский черновик в `Черновики -> Платежи`.
- Метод `/api/v1/payments-orders/payments-by-requisites/submit` потенциально может двинуть документ дальше, чем `На подпись`, если H2H-сертификат и правила подписи дают интеграции право финальной подписи. Перед боевым включением нужно настроить в Т-Бизнесе такие права, чтобы API-пользователь только готовил/отправлял документ на подпись владельцу.
- Сырые ответы выписок T-API содержат коммерчески чувствительные данные. Хранить только в `research/private/tbank/`; в `research/raw/tbank/` допустимы только нечувствительные метаданные без строк выписки. Оба каталога должны быть в `.gitignore`.
- В рабочую документацию переносить только агрегаты, статусы, поля и методику, а не полные выписки.
- В логах маскировать `Authorization`, `accountNumber`, ИНН физлиц, ФИО и назначение платежа, если оно содержит персональные данные.
- Лимит 20 запросов/сек: запросы выполнять последовательно с задержкой; для больших периодов использовать пагинацию по `nextCursor`, а не уменьшать `from/to`.

## Авторизация

- Тип: Bearer API Token.
- Передача: заголовок `Authorization: Bearer <TBANK_API_ACCESS_TOKEN>`.
- Срок жизни токена: практического истечения за время пилота не было. В документации T-Bank для H2H-токена указано: 90 дней с последнего использования, при постоянном использовании активен бессрочно.
- Поведение при истечении токена на этом проекте не наблюдалось; ожидаемая реакция скрипта — остановиться на `401`/`403`, сохранить маскированную ошибку в `research/private/tbank/` и запросить перевыпуск/проверку scope.
- Дополнительно для трассировки: заголовок `X-Request-Id` (UUID), помогает T-поддержке искать запрос в логах.
- Webhook авторизация: поддерживается Basic и Bearer; конфигурация задаётся при подключении вебхука через openapi@tbank.ru.

Если при выпуске токена попросить только «Информация о счетах компании» и «Информация об операциях компании», токен по определению read-only и не сможет создавать платежи; это рекомендованный сценарий для проекта.

## Форматы дат и таймзона

| Зона API | Формат | Комментарий |
| --- | --- | --- |
| `/api/v1/statement` параметры `from`, `to` | ISO 8601 UTC, например `2026-04-01T00:00:00Z` | `to` — исключающая верхняя граница; целевая выгрузка шла `2026-02-01T00:00:00Z` → `2026-06-01T00:00:00Z` |
| Поля операций `operationDate`, `authorizationDate` | ISO 8601 UTC, секунды или fractional seconds | В пилоте встречались оба варианта: `...Z` и `....<fraction>Z` |
| Поля операций `chargeDate`, `docDate`, `drawDate`, `trxnPostDate` | ISO 8601 UTC seconds | Проверено на пилотной выгрузке |
| Таймзона учёта в кабинете Т-Бизнеса | MSK | При сверке с iiko/Sber учитывать сдвиг UTC↔MSK |

## Платежи на подпись

Дата фиксации: 2026-05-23.

Цель владельца: сотрудник отправляет в бот счет/чек/накладную/платежку, агент распознает реквизиты и заводит платеж так, чтобы владелец видел его в мобильном Т-Бизнесе в блоке `Платежи в работе -> На подпись`, а не в `Черновики -> Платежи`.

Официальная карта методов:

| Сценарий                     | Endpoint                                                     | Контур                              | Что делает                                                                                             | Доступы                                 |
| ---------------------------- | ------------------------------------------------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| Обычный банковский черновик  | `POST /api/v1/payment/create`                                | `https://business.tbank.ru/openapi` | Создает черновик платежного поручения                                                                  | Bearer scope `payments/draft/create`    |
| Платежное поручение в работе | `POST /api/v1/payments-orders/payments-by-requisites/submit` | `https://secured-openapi.tbank.ru`  | Отправляет рублевое платежное поручение; целевой путь для `На подпись` при правильных правилах подписи | Bearer + mTLS + HMAC-SHA256 `Signature` |
| Статус черновика             | `POST /api/v1/payment/status`                                | `https://business.tbank.ru/openapi` | Возвращает статусы documentId для черновиков из `/payment/create`                                      | Bearer                                  |

Источник: страницы T-Bank Dev Portal `Создать черновик платежного поручения`, `Отправить набор платежных поручений`, `Получить список статусов платежных документов`.

Практический вывод:

- Если вызвать `/api/v1/payment/create`, платеж окажется в нижнем блоке `Черновики -> Платежи`. Это не соответствует запросу владельца.
- Для `Платежи в работе -> На подпись` нужен H2H-контур `/payments-orders/payments-by-requisites/submit`.
- Этот H2H-контур требует mTLS-сертификат и криптографическую подпись запроса. Нужно запросить у T-Bank/менеджера ключ `keyId`, секрет для HMAC, mTLS-сертификат и проверить правила подписания документов.
- До получения отдельного платежного доступа агент может только готовить приватный JSON payload и валидировать реквизиты без вызова банка.
- Загрузка документов для распознавания идет через приватный inbox `research/private/tbank/payment_orders/uploads/`: бот или агент сохраняет исходный файл, метаданные сообщения и подготовленный payload. Поддерживаемые входы MVP: PDF, изображения `png/jpg/jpeg/webp/tif/tiff`, текст/CSV/RTF. PDF читается локально через `pdftotext` или `pypdf`, изображения — через локальный OCR `tesseract`, если он установлен.

### Programmatic intake parsers

Runtime-распознавание платежных оснований выполняется без LLM. Слой `research/scripts/tbank/payment_parsers.py` содержит registry source-specific parsers с интерфейсом `name`, `source_type`, `detect(text, metadata)`, `parse(text, metadata)`.

Поддерживаемые типы оснований MVP:

- `invoice` — счет на оплату;
- `upd` — УПД;
- `waybill` — товарная накладная / ТОРГ-12;
- `receipt` — чек / кассовый чек;
- `payment_order` — платежка / платежное поручение;
- `known_counterparty` / `generic` — повторяющиеся контрагенты и общий fallback по реквизитам.

Результат parser registry сохраняется только в private-контуре:

- SQLite: `research/private/tbank/payment_orders/payment_intake.sqlite3`;
- upload-inbox: `research/private/tbank/payment_orders/uploads/`;
- prepared request JSON: `research/private/tbank/payment_orders/requests/` или `uploads/<upload_id>/prepared/`.

Основные таблицы intake DB: `uploads`, `parsed_documents`, `parser_runs`, `payment_order_candidates`, `expense_accrual_candidates`, `document_links`. В `payment_basis` хранятся реквизиты, сумма, НДС, тип/номер/дата документа, период услуги, suggested purpose, кандидаты статей ДДС/P&L, флаг owner review и безопасные `raw_evidence`-фрагменты. Полные реквизиты остаются только в `research/private/`; в `research/processed/` допустимы только агрегаты, схемы и статусы. `document_links` также используется для deterministic-связок документов, когда один платежный кандидат строится из пары оснований, например фактический акт электроэнергии плюс авансовый акт следующего периода.

| Статус | Значение |
| --- | --- |
| `parsed_ready` | parser достал обязательные поля, но банковский request еще не экспортирован |
| `owner_review` | не хватает обязательных полей или нужен владельческий выбор статьи/контекста |
| `low_confidence` | confidence ниже порога; submit payload не готовится |
| `duplicate` | найден повтор candidate hash; нужен review перед повторной оплатой |
| `ready_for_bank_signature` | сформирован private request JSON с `work_queue_payload` для `/payments-orders/payments-by-requisites/submit` |

Команда `upload` теперь выполняет полный intake: сохраняет исходник и metadata, извлекает текст, прогоняет parser registry, пишет результат в SQLite, создает `payment_order_candidates` и формирует request JSON. Если confidence низкий или обязательные поля отсутствуют, request JSON получает `requires_owner_review=true` / `bank_payload_status=blocked_owner_review` и не содержит submit-ready payload. Для актов электроэнергии parser registry различает фактический акт и аванс; при найденной паре с тем же поставщиком и датой фактический candidate получает сумму `остаток к оплате + аванс`, а период/назначение остаются от фактического акта. Отдельно по фактическому акту создается `expense_accrual_candidates` для ОПиУ/P&L: сумма расхода периода равна электроэнергии плюс потерям и не зависит от текущего cash-платежа или аванса.

Для проекта первичны: выписка, баланс, список счетов. Платежи включаются только отдельным владельческим решением и отдельным платежным токеном.

## Лимиты и пагинация

- Лимит запросов: **20 RPS** на токен (из официальной документации `GET /api/v1/statement`).
- Пагинация: `limit` 1–5000, по умолчанию 1000; продолжение по `nextCursor`. Цикл прерывается, когда `nextCursor` отсутствует.
- Фактически проверено: `limit=100` на пилоте и `limit=1000` на периоде сверки. 584 операции за целевой период вернулись одной страницей, без `nextCursor`.
- Средняя плотность целевого периода на дату выгрузки: 584 операции за 108 календарных дней с 2026-02-01 по 2026-05-19 включительно, около 5,4 операции/день; активных банковских дней с операциями — 87.
- `withBalances=true` проверен на пилоте: top-level `balances` содержит поля `balanceBegin`, `balanceEnd`, `credit`, `debit`, `creditAuthorizations`, `debitAuthorizations`, `operationsCount` и вложенный список `balances[]` с такими же дневными полями плюс `date`.

## Категории операций и контрагенты

- Параметр `categories` фильтрует по справочнику категорий операций T-Банка. На целевой выгрузке без фильтра найдены категории: `budget`, `cardOperation`, `contragentOutcome`, `contragentPeople`, `creditPaymentOuter`, `depositFullWithdrawal`, `fee`, `income`, `incomeLoan`, `incomePeople`, `refundIn`, `selfTransferOuter`, `tax`.
- Справочник категорий с агрегатами сохранён в `research/processed/tbank/operation_categories.csv`.
- Сводка контрагентов сохранена в `research/processed/tbank/counterparty_summary.csv`: полные названия, счета, назначения платежей и полные ИНН туда не перенесены; используются `counterparty_id`, hash ключа, masked-INN и агрегаты.
- Дневные итоги сохранены в `research/processed/tbank/cashflow_daily.csv`.
- В ответе операции присутствуют блоки `payer` / `receiver`; наблюдаемые поля: `acct`, `bankName`, `bicRu`, `corAcct`, `inn`, `kpp`, `name`.
- Направление операции определяется по `typeOfOperation`: `Debit` / `Credit`. В целевой выгрузке: 501 debit-операция и 83 credit-операции.
- Входящие движения T-Bank нельзя считать выручкой автоматически. Аналогичное правило действует для Sber: входящие движения обоих банков нужно классифицировать по признакам операции. В T-Bank среди входящих могут быть внутренние переводы, эквайринг, кредиты, возвраты и прочие поступления.

## Риски и неизвестные

1. **Подтверждено:** промышленный read-only контур работает для `GET /api/v1/statement`, авторизация `Bearer` успешна, `X-Request-Id` передаётся скриптом.
2. **Подтверждено:** sandbox URL в публичной документации не выделен; пилот выполнен на промышленном контуре коротким периодом и read-only scope.
3. **Подтверждено:** справочник категорий снят на целевой выгрузке и сохранён в `research/processed/tbank/operation_categories.csv`.
4. **Подтверждено:** raw-выписка содержит чувствительные `payPurpose`, реквизиты, карты/эквайринговые поля и операции; raw держать только в `research/private/tbank/`.
5. **Требует проверки:** входящие T-Bank движения есть и местами существенные; не считать их выручкой без классификации по описанию/контрагенту и сверки со Sber/iiko.
6. **Требует проверки:** срок жизни токена на практике не истекал; при `401`/`403` не ретраить циклом, проверить scope/IP/token.
7. **Требует проверки:** отдельный endpoint списка счетов не вызывался; он может понадобиться для идентификации внутренних переводов между своими счетами.
8. **Решено:** webhook «Операция по счёту» не подключать, для текущего контура достаточно polling через выписку.

## Что получено от владельца

1. Токен T-API с доступом к счетам и операциям; сохранён только в `.env`.
2. Номер расчётного счёта; сохранён только в `.env` как 20 цифр.
3. ИНН организации/ИП; сохранён в `.env`; КПП отсутствует.
4. Решение по webhook: не подключать, работать через polling.
