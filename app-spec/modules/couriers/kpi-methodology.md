# Курьеры — методология KPI для MVP

Дата фиксации: 2026-06-04.
Статус: утверждено владельцем в чате с оркестратором.
Следующий уровень детализации: формальная спека модуля (`app-spec/modules/couriers/spec.md`) и UI-страницы.

## 1. Скоуп MVP

В MVP включены **4 KPI**:

- Скорость
- Дисциплина (только для основных курьеров)
- Производительность
- Помощь (информативный счётчик)

Не входят в MVP, отложено:

- Оценки клиентов из iiko
- Жалобы / претензии клиентов
- Оценки админов (отдельный продуктовый блок, прорабатывается с нуля после KPI)
- Бонусы и штрафы курьерам (заглушка в payroll, не MVP)
- Cверка данных приложение vs iiko (не требуется при polling-подходе, см. §6)

## 2. Категории курьеров

Курьер на каждый момент времени имеет одну из двух категорий.

| Категория | Поведение | Влияние на дисциплину |
| --- | --- | --- |
| `primary` (основной) | Полный день: утро до закрытия. Развоз персонала, закупки, присутствие на точке даже при отсутствии доставок. | Дисциплина считается ТОЛЬКО по primary |
| `secondary` (второстепенный) | По вызову. Дома на телефоне, выходит по звонку администратора. | Не пенализируется за отсутствие. Статистика выходов ведётся информативно |

Категория привязана к курьеру **с эффективными датами** (`effective_from`, `effective_to`) — курьер может перейти из secondary в primary и обратно.

Источник истины на момент фиксации: лист `Курьеры` в Google Sheets «График курьеров». Перенос в БД требуется отдельной задачей.

## 3. Матчинг план ↔ факт смены

Базовая операция, на которой стоят дисциплина, опоздания, no-show и помощь.

### Сущности

- **План**: запись в графике курьера на конкретный день. Поля: `courier_id`, `work_date`, `planned_start_at`, `planned_end_at`.
- **Факт**: открытие/закрытие смены курьера в iiko. Поля: `courier_id`, `opened_at`, `closed_at`.

### Алгоритм

Для каждого календарного дня и каждого курьера сопоставляем плановую запись с фактической сменой:

1. Если **есть план и есть факт** → смена сматчена. Считаем опоздание (`opened_at - planned_start_at`).
2. Если **есть план, но факта нет** → no-show.
3. Если **есть факт, но плана нет** → кандидат на «помощь». Проверяем правило в §5.4.
4. Если **нет ни плана, ни факта** → день не учитывается.

### Считается явка

Смена считается отработанной (засчитывается в дисциплину как явка), если:

- Курьер открыл смену в iiko, И
- Длительность смены (`closed_at - opened_at`) **≥ 2 часов**.

Меньше 2 часов = неявка (для дисциплины) и не считается помощью.

## 4. Источник данных

Принято решение тянуть данные через **iikoServer Resto API через polling** (а не через iiko Transport + webhook). Причины:

- Нет потерь из-за пропущенных webhook
- Не нужны webhook secret/signature/auth на нашей стороне
- Проще debug и backfill

Минусы (приемлемы для MVP):

- Задержка дашборда на интервал polling (15–30 мин)
- `/reports/delivery/couriers` отдаёт `AVERAGE`/`MAXIMUM`/`TARGET`, не факт заказов — для факта дополнительный endpoint

### Endpoint смен курьеров (подтверждён 2026-06-04)

```
GET /resto/api/employees/attendance
   ?key=<auth_key>
   &from=YYYY-MM-DD
   &to=YYYY-MM-DD
   &withPaymentDetails=false
```

Возвращает XML с записями смен. Поля:

| Поле | Содержимое |
| --- | --- |
| `employeeId` | id сотрудника |
| `roleId` | id роли (для фильтра «Курьер» client-side) |
| `dateFrom` | open_at, ISO с таймзоной (`2026-05-29T11:05:00+03:00`) |
| `dateTo` | closed_at, пусто у незакрытых смен |
| `attendanceType` | `P` для Present (другие значения — для отпусков/больничных, изучить отдельно) |

**Фильтр по роли «Курьер»**: на сервере не поддерживается. Сначала `/employees/roles` → достать `roleId` курьера → фильтровать выборку client-side по `roleId`.

**Открытые смены** определяются по отсутствию `dateTo` — обработка отдельно (cap по времени / forced close).

**НЕ работают** (зафиксировано, чтобы не пробовать снова): `/employees/shifts`, `/employees/attendances`, `/reports/work_time`, OLAP `SHIFT`/`SHIFTS`/`ATTENDANCE`/`LABOUR`.

## 5. Метрики

### 5.1. Скорость

Среднее время **в пути** доставки — от момента, когда курьер взял заказ, до момента, когда отдал клиенту.

```
скорость = avg(delivered_at - taken_at)
   по доставкам курьера за период
```

Период: день / неделя / месяц.
Применяется: ко всем курьерам (primary и secondary).
Источник: iikoServer Resto delivery data (точный endpoint — фиксируется в integration spec).

**Светофор**:

| Среднее время | Цвет |
| --- | --- |
| ≤ 22 минут | Зелёный |
| 22–35 минут | Жёлтый |
| > 35 минут | Красный |

### 5.2. Дисциплина (только primary)

Процент явок относительно запланированных смен за период.

```
дисциплина = (отработанных смен в свой график / запланированных смен) * 100%
```

Где «отработанная смена» = §3, явка (открыта в iiko, длительность ≥ 2 часов, попадает в плановую смену по графику).

Период: месяц.
Применяется: только к курьерам категории `primary`. Для `secondary` не считается (показывается «–»).

**Светофор**:

| % явок | Цвет |
| --- | --- |
| ≥ 80% | Зелёный |
| 65–80% | Жёлтый |
| < 65% | Красный |

### 5.3. Производительность

Среднее количество доставок за смену.

```
производительность = total_deliveries / shifts_worked
   за период
```

Где `shifts_worked` — количество смен, попавших в §3 как «явка» (включая помощь у secondary).

Период: месяц.
Применяется: ко всем курьерам.

**Светофор**:

| Доставок/смена | Цвет |
| --- | --- |
| ≥ 16 | Зелёный |
| 10–16 | Жёлтый |
| < 10 | Красный |

### 5.4. Помощь

Информативный счётчик: сколько раз курьер выходил **не в свою смену** за период.

Выход засчитывается как помощь, если:

- Открыта смена в iiko, И
- На этот день у курьера НЕТ плановой записи в графике, И
- Длительность смены ≥ 2 часов **от открытия в iiko**, И
- За смену выполнена ≥ 1 доставка.

Если хотя бы одно условие не выполнено → не помощь.

Период: месяц.
Применяется: ко всем курьерам.
**Без светофора**, просто число. Не входит в общую оценку курьера, но видна в карточке.

## 6. Сверка данных (не KPI)

Снято со scope KPI: polling-подход исключает потери. Health интеграции (последний успешный запуск, ошибки, gap-detection) — отдельный технический мониторинг, не часть курьерского KPI-дашборда.
