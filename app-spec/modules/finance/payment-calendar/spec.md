# Спецификация модуля Платежный календарь

Дата сборки: 2026-05-24.

## Назначение

Модуль `Платежный календарь` должен превратить текущий Google Sheets шаблон недельного план-факта в системный прогноз денежных разрывов для веб-приложения «Тепло».

Календарь отвечает не за хранение банковского факта, а за:

- планирование поступлений и выбытий на ближайшие недели;
- прогноз остатка денег по неделям;
- раннее обнаружение кассового разрыва;
- сравнение плана с фактом из DDS;
- перенос незакрытых планов в будущие периоды без потери истории;
- связку планового платежа с документом, договором, регулярным правилом, supplier/AP контуром или owner decision.

Граница с DDS фиксируется жестко: **cash-fact живет в `cashflow_transaction` DDS**, а календарь хранит план, прогноз и матчинг план-факт. Это продолжает решение 11.2 из [database.md](/app-spec/architecture/database.md): УДКЗ и календарь не заводят свой платежный факт.

### Регламент и периодичность

Регламент описывает календарь как инструмент планирования и сбора фактических данных по движению денежных средств в разрезе недель. Цель - контролировать кассовые разрывы и заранее определять действия при угрозе разрыва.

Периодичность из шаблона:

| Блок | Периодичность |
| --- | --- |
| План | еженедельно, с планированием на 1-4 недели вперед |
| Факт | ежедневно или еженедельно |
| План-факт встреча | раз в неделю |
| Календарный вид | недели, не декады |
| Supplier-helper `Поставщики` | месячные колонки по поставщикам |

Декадной модели в шаблоне не найдено. Месячность появляется как агрегирующая ось в supplier-helper и как derived поля `Год/Месяц` в реестрах.

### Формулы план-факт

Главный лист `Календарь` построен как последовательность недельных пар `план` / `факт`.

Ключевые формулы:

```text
План поступления по статье =
SUMIFS(Плановый Реестр поступлений.Сумма,
       Плановый Реестр поступлений.Дата >= Начало недели,
       Плановый Реестр поступлений.Дата <= Конец недели,
       Плановый Реестр поступлений.Статья = строка календаря)

План выбытия по статье =
-SUMIFS(Плановые Реестр выбытий.Сумма,
        Плановые Реестр выбытий.Дата >= Начало недели,
        Плановые Реестр выбытий.Дата <= Конец недели,
        Плановые Реестр выбытий.Статья = строка календаря)

Факт по статье =
SUMIFS(Факт ДДС.Сумма,
       Факт ДДС.Статья = строка календаря,
       Факт ДДС.Дата >= Начало недели,
       Факт ДДС.Дата <= Конец недели)

Изменение за неделю = Поступления + Платежи
Остаток на конец = Остаток на начало + Изменение за неделю
```

Особенно важная production-идея шаблона - строка `Ответственные` с `TRUE` над неделями. Она работает как недельный close flag: если предыдущая неделя закрыта, будущий план берет стартовый остаток из фактического closing balance; если не закрыта, из планового closing balance.

```text
Остаток на начало следующей недели =
если previous_week.closed = TRUE
то previous_week.fact_closing_cash
иначе previous_week.plan_closing_cash
```

Это надо сохранить в приложении как отдельное состояние `calendar_week.close_status`, а не как ручной checkbox.

Owner decision 2026-05-24: закрытие недели работает по гибридному процессу. Базовое переключение на фактический opening будущих недель происходит после DDS close / работы финансового менеджера, а собственник подтверждает только спорные отклонения, `needs_owner_review`, крупные расхождения и reopen закрытой недели.

### Источники факта

`Факт ДДС` импортирует данные из внешнего DDS-листа через `IMPORTRANGE`:

- дата и сумма из диапазона `ДДС: месяц!c5:d`;
- контрагент, назначение, статья из диапазона `ДДС: месяц!g5:i`;
- тип движения подтягивается через `VLOOKUP` по `Справочник`.

`Справочник` импортирует статьи из `ДДС: статьи!a4:b`, `Контрагенты` импортирует список из `Контрагенты!A1:A`.

В приложении эта связка заменяется прямым чтением:

```text
cashflow_transaction
  -> dds_article
  -> counterparty
  -> payment_actual_match / weekly_calendar_view
```

### Источники плана

В шаблоне план не генерируется автоматически. Он ведется строками в двух реестрах:

- `Плановый Реестр поступлений`: контрагент, статья поступления, сумма, дата планируемого получения, комментарий, derived год/месяц/неделя.
- `Плановые Реестр выбытий`: контрагент, статья, номер счета, сумма, дата планируемой оплаты, комментарий, derived год/месяц/неделя.

По данным processed-снимка:

| Реестр | Строки с датами | Период | Основные статьи |
| --- | ---: | --- | --- |
| План поступлений | 71 | 2024-01-02..2024-12-31 | `Поступление денег с торг. точек`, `Получение овердрафта` |
| План выбытий | 1017 | 2024-01-01..2024-12-31 | `Оплата поставщикам`, содержание точек, ФОТ, курьерская служба, эквайринг, аренда, телеком, кредиты, подписки |
| Факт ДДС | 7015 | 2024-01-01..2025-06-04 | банковский/кассовый факт DDS, включая внутренние переводы |

Практическая методика из вкладки `Как настроить`: если плановое поступление или выбытие не произошло либо произошло частично, старую строку не удаляют. Нужно создавать новую скорректированную строку на будущую неделю. В приложении это означает versioned план и `reschedule` события.

## 6. Связь с другими модулями

### DDS и платежный контур

Платежный календарь является подмодулем DDS, но не владеет фактом.

```text
payment_plan_item
  -> payment_actual_match
  -> cashflow_transaction
  -> dds_article / counterparty / wallet
```

Правило 11.2 сохраняется: все фактические оплаты, включая supplier payments, payroll cash, налоги, аренду, подписки и owner movements, приходят из `cashflow_transaction`. Календарь может создать план, прогноз, заявку или ожидание, но не создает оплаченный факт.

### УДКЗ, авансы и prepayment_kind

Для поставщиков и префиксных платежей календарь должен согласоваться с решением 11.5 и уточнениями 2026-05-25:

- УДКЗ даёт supplier-based авансы и КЗ: отрицательный closing balance поставщика может создавать плановую строку или expected settlement в календаре;
- внешние регулярные префиксы, которые не являются обычным supplier balance (аренда, рекламные кабинеты, Mango/телефония, подписки, налоговые переплаты при появлении), приходят из своих источников и агрегируются в Balance как `Выданные авансы поставщикам`;
- `prepayment_kind` на плановой строке обязателен только для регулярных/известных предоплат: `rental_prepayment`, `subscription_prepayment`, `ad_budget_balance`, `phone_balance` и аналогичных заранее классифицированных платежей; `tax_prepayment` зарезервирован на будущее, но в MVP не используется, потому что налоговых предоплат нет.

Календарь может показывать плановый платеж с `prepayment_kind`, но не должен становиться первичным prepaid ledger. Например, аренда 28-30 числа за следующий месяц попадает в forecast как outflow и одновременно создаёт/обновляет expected advance в Balance view из договорного/ручного источника, а не расширяет УДКЗ за пределы supplier-based авансов.

### Единый реестр поставщиков

Owner decision 2026-05-25, block C12:

- в приложении должен быть единый реестр контрагентов, из которого поставщики выбираются во всех отчётах: платежный календарь, DDS, УДКЗ и баланс;
- это реализуется через общий `counterparty` и роль/profile `supplier`, а не через независимые справочники поставщиков в каждом модуле;
- выпадающие списки в платежном календаре, DDS и УДКЗ фильтруют один и тот же master по роли `supplier`;
- `supplier_counterparty` хранит профильные настройки поставщика: aliases, default P&L article, статус, условия оплаты/ожидаемый cadence, но не становится отдельным master.

Риски и предохранители:

- не все контрагенты DDS являются поставщиками, поэтому DDS использует общий `counterparty`, а supplier views фильтруют только роль `supplier`;
- один контрагент может иметь несколько ролей, поэтому роль поставщика не должна стирать роли `bank`, `customer`, `owner`, `employee` и т.д.;
- названия из банка, iiko, УДКЗ и документов должны сводиться через aliases к каноническому `counterparty_id`;
- поля, специфичные для УДКЗ или прогноза оплат, живут в supplier-profile/forecast entities, а не в базовом `counterparty`.

### P&L

Календарь показывает cash timing. P&L признает расход или доход по accrual-правилам. Поэтому `payment_plan_item` может ссылаться на `expense_accrual`, `source_document`, `contract` или `pnl_line`, но не подменяет P&L.

Пример: полугодовая оплата сервиса `Реви` в календаре является одним cash outflow, а в P&L расход признается по 1/6 в месяц. Остаток предоплаты идет в `Выданные авансы поставщикам`.

### Balance

Баланс читает денежные остатки и авансы на дату:

- факт денег - через DDS/wallet snapshots;
- supplier AP/advances - через УДКЗ;
- прогнозный календарь может дать warning о будущей ликвидности, но не является balance snapshot.

### Payroll

Payroll-выплаты в календаре должны идти агрегированно, через `payroll_payment_batch` или защищенный `cashflow_transaction` match. Индивидуальные выплаты сотрудникам не раскрываются в календаре без payroll-роли.

### Taxes и financial activity

Налоги, кредиты, овердрафт, дивиденды и owner movements видны в календаре как cash schedule. Для MVP они берут методологию из DDS/Balance decisions:

- овердрафт в DDS `Овердрафт` - комиссия/проценты, тело кредита отдельно;
- кредиты - график/остаток из financial activity/Sber API, факт через DDS;
- дивиденды и owner payable - DDS financial articles;
- налоги - ручной structured source до полноценного tax module; налоговых предоплат по owner decision 2026-05-25 нет.

Owner decision 2026-05-25: cash gap считается по всем денежным движениям календаря, включая операционные, финансовые, кредиты/овердрафт, дивиденды и owner movements. Минимальный threshold кассового разрыва - общий остаток total cash меньше 0. Wallet-specific остатки могут быть отдельным liquidity view, но не являются базовым определением cash gap.

Owner decision 2026-05-25, block B10: в MVP основной вид платежного календаря строится по `total cash`; разрез по wallet (`Sber`, `T-Bank`, `Сейф`, `ТК Черникова`) доступен как раскрытие/фильтр. Внутренние переводы между кошельками не показываются в платежном календаре как плановые строки. Их wallet-effects остаются в DDS и сверке wallet balances, а в расчёте `total cash` они неттируются и не создают отдельный управленческий cash gap.

## 7. Методология прогноза

Прогноз строится на ближайший месяц. Owner decision 2026-05-24: месячный горизонт для production пока достаточен; более длинные горизонты остаются расширением после MVP.

### 7.1 Генерация недель

1. Система генерирует `calendar_week` на год: `week_no`, `date_start`, `date_end`, `period_id`, `short_week_flag`.
2. Неделя может быть `draft`, `open`, `fact_loaded`, `closed`, `locked`.
3. После закрытия недели будущий прогноз берет opening cash из фактического closing balance. До закрытия - из планового closing balance.
4. Закрытие недели - гибридный процесс: DDS close / финансовый менеджер закрывает базовый факт, собственник подтверждает только спорные отклонения и reopen.

### 7.2 Источники плановых поступлений

| Источник | Метод |
| --- | --- |
| Выручка торговых точек | iiko OLAP отчёт `Выручка по направлениям`: month-over-month / year-over-year анализ одноимённого месяца по всем периодам с начала ведения OLAP-учёта выручки, плюс тренд, планируемая маркетинговая активность и ручные управленческие корректировки |
| Партнерские/прочие поступления | ручной план или договор/ожидаемая дата |
| Возвраты от поставщиков | supplier/УДКЗ expected settlement или ручной owner-approved item |
| Кредиты/овердрафт | approved financing schedule, не смешивать с операционной выручкой |
| Owner contributions/returns | financial activity / owner decision |

Production-источник прогноза выручки - iiko OLAP `Выручка по направлениям`, а не банк. Например, май 2026 планируется на основе мая 2025, мая 2024 и всех доступных майских периодов с момента ведения выручки в OLAP-отчёте. Расчёт должен учитывать не только same-month history, но и текущий тренд выручки, календарные особенности, планируемую маркетинговую активность и прочие owner-approved корректировки.

Важно: это источник плановой выручки. Cash-fact остаётся в DDS / `cashflow_transaction` по архитектурному решению 11.2; iiko OLAP не становится cash ledger.

### 7.3 Источники плановых выбытий

| Категория | Как строить план |
| --- | --- |
| Поставщики | открытые неоплаченные поставки/КЗ из УДКЗ и iiko integration source + исторический DDS/supplier cadence + заявки ответственных + agent/owner-approved seasonal adjustments |
| Аренда | договор, anchor day 28-30, `prepayment_kind = rental_prepayment` |
| Подписки | `contract` / billing schedule: iiko, Реви, Лемма, Доксинбокс; multi-period cash vs monthly P&L |
| Payroll | payroll run / expected payroll batch, без персонального drill-down |
| Налоги | `tax_charge.due_date` или manual structured tax schedule |
| Банковские комиссии/эквайринг/РКО | прогноз по истории DDS или банковскому тарифу |
| Кредиты/овердрафт | loan schedule: тело, проценты, комиссии отдельными статьями |
| Маркетинг и рекламные бюджеты | договор/кабинет/owner plan, `ad_budget_balance` для неиспользованных бюджетов |
| ОС и ремонты | approved capex plan или `fixed_asset_candidate` |

Owner decision 2026-05-25, block C12: план оплат поставщикам строится гибридно. Для ближайших известных платежей primary source - неоплаченные поставки/КЗ: УДКЗ и целевой iiko integration endpoint/source для неоплаченных поставок и ожидаемого времени оплаты. Для горизонта на месяц, когда точная сумма будущих поставок ещё неизвестна, прогноз строится по предыдущим периодам: rolling average по поставщику, исторический weekly cadence оплат из DDS и сезонные/операционные корректировки. Финансовый агент, который заполняет отчёты, может получать в prompt дополнительные условия: например, ожидаемый всплеск заказов в конце мая из-за последних звонков, партнёрские активности и динамику аналогичного периода прошлого года. Такие корректировки должны сохраняться как `source_reference` / `manual_action` / `agent_run`, а не как неаудируемая правка суммы.

### 7.4 Правила plan vs fact

Матчинг факта к плану:

1. Кандидаты подбираются по `counterparty_id`, `dds_article_id`, направлению, сумме и окну дат.
2. Owner decision 2026-05-24: для auto-match должны совпадать контрагент и статья ДДС; сумма факта может отличаться от плана в пределах ±10%; дата не критична, если факт находится внутри того же календарного месяца, что и план.
3. Если найден ровно один уверенный кандидат по этим правилам, создается `payment_actual_match(status=matched)`.
4. Если сумма частичная, совпадений несколько, контрагент/статья не совпали или операция вне месяца плана, строка уходит в `needs_owner_review`.
5. Если факт пришел без плана, создается `unplanned_actual` для owner review.
6. Если план не исполнен, он получает `missed`, а агент должен уточнить дальнейшее действие при составлении/закрытии платежного календаря. Перенос не выполняется молча.
7. После закрытия недели variance фиксируется: `amount_variance`, `date_variance_days`, `status_reason`.

Статусы отклонений:

| Статус | Значение |
| --- | --- |
| `matched_on_time` | факт совпал с планом в tolerance |
| `matched_late` | факт пришел позже плановой даты |
| `matched_early` | факт пришел раньше плановой даты |
| `partial_paid` | факт покрывает только часть суммы |
| `overpaid` | факт больше плана |
| `missed` | план не исполнен к закрытию недели |
| `rescheduled` | план перенесен на будущую неделю |
| `unplanned_actual` | факт есть, плановой строки не было |
| `article_mismatch` | сумма/контрагент похожи, но статья отличается |
| `needs_owner_review` | недостаточно уверенности для автоматического match |

## 8. Сущности веб-приложения

| Сущность | Назначение | Ключевые поля |
| --- | --- | --- |
| `calendar_week` | недельная ось календаря | `id`, `week_no`, `date_start`, `date_end`, `period_id`, `short_week_flag`, `close_status`, `closed_at` |
| `payment_plan_item` | плановая строка поступления или выбытия | `id`, `direction`, `due_date`, `amount_planned`, `currency`, `counterparty_id`, `dds_article_id`, `wallet_hint_id` optional, `source_type`, `status`, `quality_status`, `source_reference_id` |
| `payment_plan_revision` | история изменения плана | `plan_item_id`, `revision_no`, `old_due_date`, `new_due_date`, `old_amount`, `new_amount`, `reason_private`, `manual_action_id` |
| `payment_recurrence_rule` | правило регулярного платежа/поступления | `frequency`, `anchor_day`, `week_offset`, `amount_policy`, `counterparty_id`, `dds_article_id`, `contract_id`, `active_from`, `active_to` |
| `payment_actual_match` | связь плана с фактом DDS | `payment_plan_item_id`, `cashflow_transaction_id`, `matched_amount`, `match_method`, `amount_variance`, `date_variance_days`, `quality_status` |
| `weekly_calendar_view` | расчетная витрина plan/fact по неделям | `week_id`, `dds_article_id`, `direction`, `plan_amount`, `fact_amount`, `variance`, `opening_cash`, `closing_cash`, `cash_gap_flag` |
| `cash_gap_alert` | предупреждение о разрыве | `week_id`, `wallet_scope`, `projected_min_cash`, `threshold`, `severity`, `status`, `owner_review_log_id` |
| `payment_plan_source` | audit origin плановой строки | `source_type`, `source_entity_type`, `source_entity_id`, `source_reference_id`, `confidence` |
| `planned_prepayment_component` | связь planned cash с prepayment logic для регулярных/известных предоплат | `payment_plan_item_id`, `prepayment_kind`, `service_period_start`, `service_period_end`, `balance_policy` |
| `supplier_payment_forecast` | supplier-specific прогноз поверх УДКЗ/iiko/DDS и агентских корректировок | `counterparty_id` с ролью `supplier`, `week_id`, `method`, `base_ap_amount`, `rolling_average_amount`, `seasonal_adjustment_amount`, `planned_payment_amount`, `agent_run_id`, `quality_status` |

Инварианты:

- `counterparty_id` всегда ссылается на единый master `counterparty` по решению 11.1.
- Фактическое движение денег всегда ссылается на `cashflow_transaction`; calendar не хранит собственный cash ledger.
- `prepayment_kind` обязателен на плановой строке только для регулярных/известных предоплат: аренда, подписки, рекламные кабинеты, Mango и аналогичные заранее классифицированные платежи. Налоговые предоплаты не планируются в MVP, потому что владелец подтвердил их отсутствие. УДКЗ остаётся ledger только для supplier-based авансов; остальные prepayment components приходят из своих источников.
- Текстовые статьи из Google Sheets не становятся ключами. Нужен `dds_article_id` и aliases.
- Закрытая неделя не пересчитывается молча. Исправление идет через revision/reopen с audit trail.
- Платежный календарь не создаёт платёжные поручения или `payment_order_candidate`; это отдельный платежный процесс DDS/платежного контура.
- Основной календарный view показывает `total cash`. Wallet-разрез (`Sber`, `T-Bank`, `Сейф`, `ТК Черникова`) доступен как раскрытие/фильтр, но не меняет базовый threshold cash gap.
- Внутренние переводы между wallet скрыты из платежного календаря; их учет, классификация и влияние на остатки кошельков остаются в DDS, а в `total cash` они неттируются.
- Поставщики выбираются из единого `counterparty` master с ролью `supplier`; платежный календарь не заводит отдельный справочник поставщиков.
- Supplier forecast не должен превращать историческую среднюю оплату в подтвержденную КЗ. История DDS и rolling average - forecast signal; подтвержденный долг живет в УДКЗ/iiko/source documents.

## 9. MVP

### MVP-экраны

| Экран | Что делает |
| --- | --- |
| `Платежный календарь` | недельная сетка plan/fact, opening/closing cash, cash gap по `total cash`, wallet-разрез как раскрытие/фильтр |
| `Месячная сводка` | агрегат над недельным календарем: поступления, выбывания, supplier forecast, cash gap и closing cash по месяцу |
| `Планы платежей` | список плановых поступлений/выбытий, фильтры по неделе, статье, контрагенту, статусу |
| `Регулярные платежи` | аренда, подписки, payroll, налоги, кредиты, повторяющиеся suppliers |
| `План-факт отклонения` | missed, partial, late, unplanned actual, article mismatch |
| `Закрытие недели` | загрузка факта DDS, сверка, переход future forecast на fact opening |
| `Owner review` | спорные matches, новые правила, переносы и unplanned facts |

### MVP-функции

1. Импортировать структуру текущего шаблона как source snapshot.
2. Завести `calendar_week` и weekly view системно.
3. Создавать ручные `payment_plan_item` для поступлений и выбытий.
4. Генерировать recurring план для аренды, подписок, payroll batches, налогов и кредитных платежей.
5. Строить supplier forecast из УДКЗ/iiko open supplies, historical DDS cadence, rolling average и agent/owner-approved корректировок.
6. Читать факт только из `cashflow_transaction` DDS.
7. Матчить план с фактом и показывать отклонения.
8. Считать opening/closing cash с переключением на факт после закрытия недели.
9. Показывать cash gap по `total cash`; threshold разрыва = общий остаток меньше 0. Wallet-разрез (`Sber`, `T-Bank`, `Сейф`, `ТК Черникова`) входит в MVP как раскрытие/фильтр основного вида.
10. Показывать недельный вид и месячную сводку поверх недельных данных.
11. Сохранять переносы планов как revision, не удаляя исходный план.
12. Не раскрывать payroll personal rows и private назначения платежей в общем календаре.

### Не входит в MVP

- автоматическая подпись платежей в банке;
- создание платёжных поручений или `payment_order_candidate`;
- внутренние переводы между wallet как строки платежного календаря; они остаются в DDS;
- fully autonomous supplier AI forecast без УДКЗ/iiko/source review и audit trail;
- полноценный tax module;
- сложная scenario simulation по нескольким revenue curves;
- декадный view, пока владелец не подтвердит потребность.
