# Спецификация модуля Прогнозирование доходов и расходов + финансовая деятельность

Дата сборки: 2026-05-24.  
Режим discovery: read-only; исходные Google Sheets не изменялись.

## Назначение

Модуль `Прогнозирование доходов и расходов` строит управленческий прогноз на базе фактических P&L, ДДС и баланса, а также учитывает финансовую деятельность: кредиты, займы, лизинг, дивиденды и вклады собственников.

Цель модуля не заменить фактический monthly close, а дать слой планирования:

- прогнозный P&L по месяцам и сценариям;
- прогнозный ДДС / payment calendar по операционной, инвестиционной и финансовой деятельности;
- прогнозный баланс на конец периода;
- план-факт после закрытия месяца и пересчёт следующих периодов;
- явные допущения по сценарию вместо неявных ручных формул в Google Sheets.

Важный результат discovery: ссылка, переданная как возможный документ про «учёт финансовой деятельности и планирование прибыли», открывается как `2025 Учет Основных Средств 2.0 [PII_FILTERED]`. Это **другой документ**, не УФД и не модель прогноза прибыли. Он полезен только как вход для амортизации, остаточной стоимости ОС и возможных замен оборудования.

## 4. Методология прогноза

### 4.1 Входы

| Вход | Источник | Как использовать |
| --- | --- | --- |
| Исторический фактический P&L | `2026 ОПиУ` и правила [pnl-build-methodology.md](/business-docs/finance/pnl-methodology.md) | База строк P&L, фактические месячные суммы, источники и статусы |
| Выручка, скидки, food cost | iiko OLAP `Отчет о выручке по направлениям` | База для тренда и сезонности по направлениям `Роллы`, `Пицца`, `ГЦ`, `Бар` |
| ДДС-факт | DDS-модуль / `ДДС: Сводный` и операции | База cash timing, регулярных платежей и план-факт cash |
| Payroll | Зарплатная ведомость / payroll-модуль | ФОТ, налоги с ЗП, депозиты, накопительный фонд |
| Документные и договорные расходы | P&L document pipeline, УДКЗ, vendor schedules | Accrual-расходы по периоду услуги; cash lag через ДДС |
| ОС и амортизация | `1GK6...`: [uchet_os.csv](/research/processed/financial_planning/uchet_os.csv), [svod.csv](/research/processed/financial_planning/svod.csv) | Амортизация P&L, остаточная стоимость ОС, сценарии замены/CAPEX |
| Кредиты | Sber API по решению 11.9 | Остаток тела на дату, план тела/процентов при наличии графика |
| Дивиденды и owner payments | ДДС-лист, статьи финансовой деятельности | Cash-факт выплат, прогноз выплат после закрытия P&L |
| Налоги | Ручной structured form по решению 11.9 | Начисления, платежи, liabilities/prepayments |

### 4.2 Выходы

| Выход | Содержание |
| --- | --- |
| Прогнозный P&L | Выручка, скидки, food cost, валовая прибыль, ФОТ, операционные расходы, амортизация, below-EBITDA, чистая прибыль |
| Прогнозный ДДС | Cash-in/cash-out по операционной, инвестиционной и финансовой деятельности, включая кредиты, дивиденды, вклады собственников |
| Прогнозный баланс | Денежные средства, ДЗ/КЗ, запасы/авансы, ОС по остаточной стоимости, кредиты, owner balances, налоги, капитал |
| План-факт | Отклонения по строкам P&L, статьям ДДС и ключевым балансовым строкам |

### 4.3 Горизонт

В найденном источнике горизонт прогноза не задан. Для MVP предлагается:

- основной горизонт: rolling 12 месяцев помесячно;
- агрегаты: квартал и год как производные от месячных периодов;
- пересчёт: после закрытия каждого фактического месяца и при ручном изменении ключевых assumptions.

Это предложение требует owner-review, потому что владелец мог ожидать иной горизонт: месяц, квартал, год или сценарный cash gap на 4-8 недель.

### 4.4 Расчётные правила

1. Выручка прогнозируется по направлениям, а не одной общей строкой: база из iiko OLAP, затем коэффициенты сценария и сезонности.
2. Переменные расходы привязываются к драйверам: food cost к выручке/себестоимости, комиссии партнёров к партнёрской выручке, агрегаторы к соответствующему обороту.
3. Фиксированные расходы берутся из договоров, vendor schedules и последних подтверждённых фактов; пустая строка не считается нулём.
4. Документные расходы признаются по периоду услуги, а не по дате оплаты; cash timing берётся через ДДС или график платежей.
5. Амортизация берётся из ОС-реестра; новые покупки ОС в сценарии создают CAPEX cash-out и будущую амортизацию.
6. Кредиты в MVP читаются через Sber API по остатку тела; проценты и комиссии идут в P&L/ДДС по графику или ручному вводу, если API не даёт график.
7. Дивиденды прогнозируются после расчёта чистой прибыли и cash availability; факт выплат сверяется с ДДС-статьями финансовой деятельности.
8. Налоги остаются manual structured form до отдельной налоговой спеки.

## 5. Сценарии

В `1GK6...` сценарное моделирование не найдено. Для продуктовой модели нужны как минимум три сценария:

| Сценарий | Смысл | Пример assumptions |
| --- | --- | --- |
| `base` | Ожидаемый план | текущий тренд выручки, подтверждённые договорные расходы, known obligations |
| `optimistic` | Верхняя граница | рост выручки, стабильный food cost, без внепланового CAPEX |
| `pessimistic` | Нижняя граница | снижение выручки, рост переменных затрат, задержки оплат, внеплановые ремонты/CAPEX |

Сценарий должен хранить именно допущения, а не только итоговые суммы. Иначе план-факт после закрытия месяца не объяснит, что ошиблось: база факта, драйвер, сезонность, ручное assumption или cash timing.

## 7. Связь с фактом и план-факт

`forecast_run` должен быть immutable: после публикации сценария факт не перезаписывает исходный прогноз, а создаёт actualization layer.

После закрытия месяца:

1. Фактический P&L закрывается по правилам [pnl-build-methodology.md](/business-docs/finance/pnl-methodology.md).
2. Фактический ДДС закрывается по DDS-модулю; unclassified операции закрытого месяца не допускаются без owner-approved suspense.
3. Фактический balance snapshot фиксирует остатки на конец месяца.
4. Для каждой строки считается:
   - `variance_amount = actual_amount - forecast_amount`;
   - `variance_pct = variance_amount / abs(forecast_amount)`, если база не нулевая;
   - `variance_reason_code`: volume, price/rate, timing, source_missing, manual_override, classification_change.
5. Следующие forecast periods пересчитываются новым `forecast_run`, где закрытый факт становится новой базой.

Правило качества: если источник факта отсутствует или остановился, прогноз не должен автоматически считать факт нулём. Статус периода становится `source_not_loaded`, `requires_review` или `manual_pending`.

## 8. MVP

MVP должен уважать решение 11.9 и не пытаться построить полноценный модуль ФД раньше источников:

| Область | MVP | Отложено |
| --- | --- | --- |
| Выручка | Forecast по направлениям на базе iiko/P&L monthly fact | Сложный demand forecasting и маркетинговые драйверы |
| Расходы | Fixed/variable rules, vendor schedules, payroll, DDS classic lines | Автоматический СБИС full matching без credentials |
| ОС | Импорт амортизации и остаточной стоимости из ОС-реестра; ручные CAPEX assumptions | Полная инвентаризация/амортизационная политика после owner approve |
| Кредиты | Sber API: остаток основного долга; ручной/полуручной график процентов при необходимости | Полная модель всех банковских продуктов и covenants |
| Дивиденды | ДДС-лист: факт выплат; прогноз выплат как manual assumption после P&L close | Автоматическое решение о распределении прибыли |
| Займы собственников | `owner_loan_register` manual/review | Сложные проценты и графики без подтверждения владельца |
| Налоги | Ручной structured form | ЛК ФНС / авто-сверка |
| Сценарии | Base/optimistic/pessimistic с коэффициентами и ручными overrides | Многофакторная оптимизация и probabilistic forecast |

Cutover criteria: один закрытый месяц может быть пересчитан в прогнозе из факта, план-факт сходится по P&L и ДДС без необъяснённых material-разрывов, а все manual assumptions имеют владельца и дату актуальности.
