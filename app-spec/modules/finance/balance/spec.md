# Спецификация модуля Баланс

Дата сборки: 2026-05-24.  
Последнее обновление: 2026-05-27 (закрыты 6 вопросов по дате snapshot, КФВ, SLA закрытия, ответственности, ОС-кандидатам и расследованию задолженности сотрудников).

## Назначение

Модуль `Баланс` — третий продуктовый модуль единого управленческого веб-приложения после `Зарплата и кадры` ([payroll engine spec](/app-spec/modules/staff/payroll/00-engine.md)) и `ДДС и платежный контур` ([21-dds-module-spec.md](/app-spec/modules/finance/dds/spec.md)).

Цель модуля: заменить текущую связку Google Sheets `Баланс • [ИП Шокина]` и ручных сверок на управляемый web-процесс ежемесячных snapshot'ов активов, капитала и обязательств с автоматическим подтягиванием остатков из подключённых модулей (Payroll, DDS, P&L, ОС, Учёт ФД, Учёт налогов) и контролируемым ручным fallback на статьи, где автоматического источника пока нет.

Документ фиксирует не исторические суммы, а правила учёта и будущую продуктовую модель. Текущие Google Sheets `2024 Баланс` и `2025 Баланс` используются как прототип структуры, справочника статей и регламента; цифры внутри них являются read-only материалом для проверки методологии.

## Статусы подтверждения

| Статус | Значение |
| --- | --- |
| `подтверждено владельцем` | правило явно зафиксировано со слов владельца |
| `подтверждено формулами/документами` | правило видно в Google Sheets-шаблоне, справочнике статей или регламенте |
| `подтверждено данными` | правило проверено на live-выгрузках iiko/банков/payroll без раскрытия строк |
| `гипотеза / owner review` | правило вероятно, но требует решения владельца перед автозакрытием |

Главное правило источников: **баланс показывает остатки на дату, ДДС показывает потоки за период, P&L показывает результат за период**. Из ДДС нельзя реконструировать остатки активов и обязательств без инвентаризации и реестра. Это закреплено в [old-os-and-balance-discovery.md](/research/archive/old-os-and-balance-discovery.md) и применимо ко всему модулю.

## 2. Структура баланса

Три уровня иерархии. Знаки активов и пассивов положительные; уменьшающие капитал строки (дивиденды) хранятся со знаком минус.

```
АКТИВЫ
├── Внеоборотные активы
│   └── Основные средства  (строки ОС; неработающее оборудование = статус внутри исходной категории)
└── Оборотные активы
    ├── Запасы              (5 строк)
    ├── Денежные средства   (2 строки)
    ├── Дебиторская задолженность  (4 строки)
    ├── Краткосрочные финансовые вложения  (2 строки)
    └── Прочие активы       (1+ строки)

ПАССИВЫ
├── Капитал
│   ├── Уставный капитал
│   ├── Накопленная прибыль/убыток (прошлых + текущих)
│   ├── Дивиденды (прошлых + текущих)
│   ├── Вложения от собственников (прошлых + текущих)
│   ├── Добавочный капитал
│   └── Резервы переоценки
└── Обязательства
    ├── Долгосрочные (свыше 12 мес): кредиты банков, займы, лизинг
    ├── Краткосрочные (менее 12 мес): кредиты банков, займы, овердрафт
    └── Кредиторская задолженность: авансы клиентов, поставщики, сотрудники, депозиты сотрудников, налоги, собственники, накопительный фонд

КОНТРОЛЬ
└── Проверка: Активы = Пассивы (расхождение)

ФИНАНСОВЫЕ ПОКАЗАТЕЛИ
├── Оборотный капитал
├── Текущая ликвидность
├── Абсолютная ликвидность
├── Финансовая устойчивость
├── Финансовая независимость
├── Рентабельность собственного капитала (ROE)
└── Рентабельность активов (ROA)
```

## 3. Сводная таблица статей × источники × статусы

Поле `pnl_status` = статус источника на 2026-05-24 по той же логике, что и для ОПиУ ([feedback_source_coverage_definition](../../../../.claude/projects/-Users-grigorii-Documents-Projects-Teplo-all-for-business/memory/feedback_source_coverage_definition.md)):

- `full` — источник определён + методология подтверждена; способ доставки (API/ручной/AI-агент) не влияет;
- `partial` — источник есть, но методология/реестр требует доработки;
- `pending` — источник не подключён;
- `not_applicable` — не используется (ИП, исторический контур).

## 4. Сводка по статусам источников

После owner-уточнений 2026-05-24..2026-05-27:

| Статус | Кол-во статей | Доля от активных |
| ---: | ---: | ---: |
| `full` | 20 | 56% |
| `partial` | 13 | 36% |
| `pending` | 3 | 8% |
| `not_applicable` | 6 | — |
| **Всего** | **42** | |

Активные строки (без `not_applicable`) = 36. Из них 56% полностью обеспечены источником, 36% требуют доработки методологии/реестра, 8% не подключены.

**Что закрылось 2026-05-24:**
- Прочая задолженность в нашу пользу — `pending` → `partial` (источник определён: реестр займов собственникам в УФД).
- Выданные авансы поставщикам — методология закрыта как единая категория префиксных платежей; строка остаётся `partial` по источникам до manual opening register и отдельных источников рекламных кабинетов/Mango.
- Расходы будущих периодов — `partial` → `not_applicable` (объединено в Авансы поставщикам).
- Дивиденды (оба) — `pending` → `full` (источник переключён с УФД на ДДС).
- Задолженность перед собственниками — `pending` → `full` (источник ДДС).
- Долгосрочные кредиты банков — `pending` → `full` (источник переключён с УФД на Sber API).
- Займы и Лизинг (долг./кратк.) — `pending` → `not_applicable` (фактически 0 в 2024-2025).

**Что закрылось 2026-05-25:**
- Касса / `Сейф`: физические остатки есть по всем счетам; для opening нужен снимок сумм на 2026-02-01.
- `ГарантФонд`: это депозиты курьеров, хранящиеся в Т-Банке, а не нерасшифрованный резерв.
- Payroll opening: источник дебиторки/кредиторки сотрудников - зарплатная ведомость; долги сотрудников на 2026-02-01 есть.
- УДКЗ 2025/2026: найденный файл использовать только как пример структуры; для MVP разрешен manual opening register поставщиков.
- Кредиты/овердрафты: кредит Сбера и возможный овердрафт Т-Банка проверять по банковским API/выпискам.
- Налоги: источник - WorkMail налогового агента `askad02@mail.ru`; MVP через structured manual form; налоговых предоплат нет.
- ОС: Balance MVP может запускаться с `requires_review` по ОС до инвентаризации, если статусы и источник явно показаны.

**Что закрылось 2026-05-27:**
- Дата snapshot: последний календарный день месяца, `draft → final` после закрытия источников.
- КФВ / депозиты — `pending` → `full` по методологии: читать Sber и T-Bank, подтверждать вручную; `ГарантФонд` не включать в КФВ.
- Регламент закрытия: целевой SLA до 7 числа следующего месяца.
- Ответственность: владелец финализирует, ИИ-агент готовит отчётность.
- ОС-кандидаты: отдельный candidate/control слой из крупных платежей T-Bank; основной источник остаётся `Учёт ОС`.
- `Задолженность сотрудников = 0` за апрель 2025: расследование отложено до post-MVP.

## 6. Методология snapshot'а на дату

Балансовый snapshot формируется на **последний календарный день месяца** (`yyyy-mm-31` или эквивалент). Для текущего месяца — на дату запроса с пометкой `MTD`. Решение владельца 2026-05-27: если банковские проводки, iiko-данные или ручные источники за последний день ещё не закрыты, snapshot остаётся `draft`; после закрытия источников переводится в `final`.

### Активы

| Группа | Метод сбора |
| --- | --- |
| Внеоборотные | реестр ОС, расчёт остаточной стоимости на дату по графику амортизации |
| Запасы | iiko `/reports/storeOperations INCOMING_INVENTORY` или iiko OLAP остатков на конец дня; suma по whitelist в разрезе категорий |
| Денежные средства / р/счета | Sber `GET /v2/statement/summary?date=YYYY-MM-DD` + T-Bank `/api/v1/statement?to=YYYY-MM-DD` — поле `closingBalance` |
| КФВ / депозиты | Sber API + T-Bank API на дату; ручное подтверждение перед `final`; исключить `ГарантФонд`, потому что это депозиты курьеров |
| Денежные средства / касса | iiko OLAP `TRANSACTIONS` корсчёт `Главная касса` остаток на дату + сейф (ручной ввод снимка) |
| Дебиторка партнёров | iiko OLAP `Отчёт о партнёрах` — непогашенные счета на дату |
| Дебиторка поставщиков | supplier-based авансы из manual opening register/УДКЗ structure seed; внешние префиксы (аренда, подписки, рекламные кабинеты, Mango) добавляются из своих источников; старый УДКЗ использовать как пример структуры, не как current truth |
| Дебиторка сотрудников | Payroll-модуль агрегат по `employee_account` |
| Прочая дебиторка | ручной snapshot с указанием контрагента и основания |

### Пассивы

| Группа | Метод сбора |
| --- | --- |
| Капитал / накопленная прибыль | P&L cumulative как `Σ (EBITDA − below-EBITDA)` за все закрытые годы + MTD текущего |

## 9. MVP

### Что в первой итерации

1. **Импорт исторического шаблона**: загрузить структуру 2024-2025 из снимков [balance_2024_readonly.csv](/research/processed/balance/balance_2024_readonly.csv) и [balance_2025_readonly.csv](/research/processed/balance/balance_2025_readonly.csv) в `balance_line` (42 строки) + справочник.
2. **Snapshot на дату для строк со статусом `full`**: 20 строк, которые сейчас полностью обеспечены источниками. Это позволит на любую дату собирать **базовый ~56% активных строк баланса** автоматически.
3. **Ручной ввод для строк `partial` и `pending`**: для остальных строк форма с указанием суммы, источника, основания и owner review.
4. **Контрольная строка `Активы = Пассивы`** с автоматической подсветкой расхождения.
5. **Финансовые показатели**: 7 коэффициентов из таблицы выше, автоматический расчёт.

### Что отложено за пределы MVP

- Учёт ОС и амортизация — отдельный модуль; до его готовности 11 строк внеоборотных активов вводятся вручную с пометкой «реестр устарел». Параллельно T-Bank даёт кандидатов в ОС из крупных платежей для review, но не заменяет инвентаризацию.
- Полноценный Учёт ФД (сложные графики займов, лизинг, проценты по owner loans) — отдельный модуль; в MVP известные строки идут через Sber API, ДДС-лист и `owner_loan_register`, а спорные остатки вводятся вручную с source/status.
- Учёт налогов — отдельный модуль; до его готовности строка «Задолженность по налогам» вводится вручную.
- Расследование расхождения 147 759 ₽ за апрель 2025 — отложено по решению владельца 2026-05-24.
- Расследование причины `Задолженность сотрудников = 0` за апрель 2025 — отложено до post-MVP по решению владельца 2026-05-27.
- Сложные методологии «авансы поставщикам» и «прочая дебиторка» — owner review требуется до автоматизации.
- Графики и аналитика — после стабилизации основной таблицы.

### Цель MVP

К моменту выхода MVP владелец при поддержке ИИ-агента должен иметь возможность за **15 минут** собрать корректный snapshot на конец месяца: автоматические строки подтягиваются, для остальных открывается форма ручного ввода с подсказками по источнику. Целевой срок финализации — до **7 числа месяца, следующего за отчётным**.
