# Payroll decisions

Дата фиксации: 2026-05-29.
Источник: owner decisions из бывшего гибридного payroll-документа + уточнения владельца к Wave 2B.

## 1. Owner decisions 2026-05-20

1. Строки из `Калькулятор` попадают в `Выгрузка` через **Apps Script**. Для веб-приложения это не нужно копировать буквально: целевая логика должна создавать immutable `payroll_ledger_lines` внутри `payroll_run`.
2. Категория `Внештат` / категория 6 нужна для внештатных подмен: бывший сотрудник, сотрудник другого заведения или другой временный человек, который выходит на один-два дня при ЧП. Он не числится в штате, не участвует в проценте от выручки и по нему не удерживаются депозиты.
3. `Пиццерист / 4` и `Сушист / 4` — стажеры. Для целевого приложения правило: они получают только оклад, без процента от выручки. Логику приложения можно сделать чище, чем текущие Google Sheets-формулы.
4. Накопительный фонд выплачивается строго **15 января**.
5. `Депозит списание` не показывается в персональном отчете сотрудника. Персональный отчет предназначен для передачи сотруднику; если депозит списан, сотрудник, как правило, уже уволился. Списание должно жить во внутреннем audit trail / депозитном счете.
6. `Депозит возврат` отображается в фактических выплатах.
7. `Выплата накоплений` отображается как обычная выплата. В персональном отчете есть ячейка накоплений, которая после выплаты обнуляется.

## 2. Owner decisions 2026-05-24/25

**Решение владельца 2026-05-24 (11.7):** `payroll_payment` в целевом приложении является обязательством/ведомостью payroll-модуля, а не первичным cash-fact. Денежный факт хранится в DDS: индивидуальная банковская выплата матчится 1:1 с `cashflow_transaction`, кассовая ведомость закрывается через `payroll_payment_batch`. Доступ к индивидуальным суммам и drill-down до сотрудника есть только у payroll-роли; DDS видит агрегаты и приватные ссылки.

## 3. Закрытые вопросы из owner-review

| Вопрос | Решение |
| --- | --- |
| Как технически оформлять выплату накопительного фонда 15 января? | `payroll_payment` фиксирует обязательство payroll-модуля; cash-fact закрывается через 1:1 `cashflow_transaction` или `payroll_payment_batch`. |
| Как показывать сотруднику обнуление накоплений после выплаты? | С 1 января показывать отдельный информационный блок с суммой выплаты 15 января за прошлый год; выплата 15 января обнуляет фонд прошлого года и не затрагивает начисления нового года. |
| В какой управленческий отчет попадет `Депозит списание`? | Нужна отдельная управленческая статья `Списание депозитов`; источник — payroll ledger. |
| Значение `Не выдавать` полностью покрывает кейс увольнения и невыполненных обязательств? | `Списание накоплений` в 99% случаев связано с увольнением до 15 января; редкая дисциплинарная причина допустима только ручным решением с причиной. |

## 5. Minute rounding policy

**Решение владельца:** production payroll считает явку по точным минутам. Legacy-правило Google Sheets, где минуты `>= 40` округляли длительность на 1 час вверх, считается previous behavior и не переносится как целевая методология.

Целевое правило:

```text
worked_minutes = точная длительность интервала явки в минутах
hours_exact = worked_minutes / 60
capped_hours = min(hours_exact, 12)
adjusted_coeff = full_coeff * capped_hours / 12
```

Если `hours_exact >= 12`, сотрудник получает полный коэффициент участия в проценте. Если интервал через полночь, open shift, пустой или нестандартный, расчёт должен получить status `requires_review` / validation error вместо молчаливого округления.

Previous behavior из старой таблицы: интервалы парсились из текста, а минуты `>= 40` округляли длительность на 1 час вверх. Это хранится только как migration context для сверки старых результатов.
