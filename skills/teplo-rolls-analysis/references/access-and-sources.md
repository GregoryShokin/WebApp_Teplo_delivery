## Минимальный маршрут к iiko

1. В окружении приложения открой `AsyncSessionLocal` из `app.db.session`.
   В отдельной транзакции установи `SET TRANSACTION READ ONLY` до SELECT и разумный
   `statement_timeout`. После чтения — rollback, затем dispose engine.
2. `app.services.iiko_sync._load_source_credential_env(session)` читает активный
   SourceCredential и загружает существующие настройки iiko в текущий процесс.
   Эта функция не возвращает каталог и не запускает sync.
3. `app.services.pnl.iiko_sync._fetch_raw(endpoint, params)` выполняет GET через
   существующий IikoClient. В проверенной реализации результат — bytes;
   JSON разбирай через `json.loads`, XML — соответствующим парсером, сохраняя raw.
4. Для каталога и рецептуры используй точные endpoints/параметры из
   [справки техкарт](recipes-and-weights.md). Например, getTree требует строковые
   `date`, `productId`, `departmentId`; реквизиты добавляет существующий клиент.
5. Для продаж сначала GET metadata/presets. Канонический контроль P&L —
   `REVENUE_PRESET_ID` из pnl/iiko_sync.py и его актуальные фильтры.
   `_fetch_preset(id, start, end_exclusive)` возвращает разобранные строки;
   raw того же запроса можно сохранить через `_fetch_raw` с
   `/v2/reports/olap/byPresetId/{id}`, `summary=false`, `dateFrom`, `dateTo`.
6. Для своей детализации SALES используй образец POST в
   `iiko_revenue._fetch_daily_revenue_sync`: IikoClient и
   `_request_iiko_with_incomplete_read_retry(..., method="POST", json_body=body)`.
   Тело собери из наблюдённой metadata и подтверждённых фильтров по
   [справке продаж](sales-and-sets.md). Дневной пример тела не содержит всей нужной
   детализации SKU и всех фильтров P&L; его нельзя просто объявить готовым запросом ABC.

Проверяй status/структуру каждого ответа, ошибки и пропущенные chunks.
Не вызывать `sync_month`, `sync_iiko_products`, запись техкарт или inventory import.
`fetch_products_catalog(session=...)` может писать кэш даже при refresh=false;
для этого анализа предпочтителен прямой GET каталога.

## Что проверяет manifest

`scripts/check_sources.py --repo <repo>` сверяет SHA-256 перечисленных локальных
исходников с [source-manifest.json](source-manifest.json). Код 0 — совпадают;
1 — изменились/отсутствуют, надо перечитать; 2 — проверка не выполнена.
Исторические файлы в manifest подтверждают только форму и происхождение старых данных.
Совпадение хешей не подтверждает живые продажи, текущие рецептуры, ставки или полноту.

В `external_sources` отдельно записаны использованные файлы установленного
`iiko-inventory-from-scans`; checker их не проверяет. Если опираешься на его helper,
найди текущий skill в каталоге навыков и сравни нужную реализацию с описанием.
Сырые исторические iiko ответы могут быть ignored и отсутствовать в новом worktree.
Они перечислены как примеры в справках; это не причина считать текущие данные нулевыми.

Если source изменился, обновляй справку и хеш после предметной проверки,
а не просто ради зелёного статуса. Дополняй навык устойчивыми правилами поиска,
формулами, единицами и контролями; разовые значения продаж оставляй в материалах задачи.
