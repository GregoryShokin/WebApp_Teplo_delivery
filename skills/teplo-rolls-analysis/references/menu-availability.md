# Базовое меню, публикация и доступность

Для вопроса «стоит ли ролл в продаже» показывать несколько отдельных признаков.
Запись складского каталога, базовое меню iiko, публикация сайта и возможность заказа
в эту минуту не эквивалентны. Нулевые продажи не заменяют ни один из этих признаков.

## 1. Признак базового меню iikoServer

Источник — прямой GET `/resto/api/v2/entities/products/list` из
[маршрута чтения каталога](recipes-and-weights.md#2-каталог-и-поиск-guid).
Сохранять GUID `id`, тип, группу, исходные `deleted` и `defaultIncludedInMenu`, время snapshot.
Для истории читать также удалённые записи, не отбрасывая их до сверки продаж.

| deleted | defaultIncludedInMenu | Интерпретация текущего базового меню |
| --- | --- | --- |
| false | true | Включён |
| false | false | Не включён |
| true | любое | Удалённая запись; не текущий ассортимент |
| отсутствует/не распознано | любое | Статус удаления неизвестен |
| false | отсутствует/не распознано | Включение в меню неизвестно |

Текущий подтверждённый базовый ассортимент: **явные `deleted=false` и
`defaultIncludedInMenu=true`**, затем предметный отбор роллов по GUID/группе/роли.
Не превращать отсутствующее поле в false и не применять `bool("false")`.
Если формат boolean изменился, сохранить raw и разобрать только известные значения.
Конфликтующие поля удаления или повторяющиеся GUID требуют проверки, а не выбора удобной строки.

Опорный код: `apps/api/app/services/pnl/goods_classifier.py::build_menu_usage_snapshot`,
строки 215–216 в проверенной версии: `active=_truthy(row.get("defaultIncludedInMenu"))`
и отдельное вычисление deleted. Это подтверждает используемый приложением признак.
Однако поведение helper при пустом значении не отменяет unknown в аналитическом реестре.
Модель `IikoProduct` не содержит полного флага базового меню; её кэш не заменяет raw products/list.

Снимок говорит о текущем базовом меню, а не о доступности по дням или во всех каналах.
`defaultSalePrice` не доказывает цену на сайте или фактическую цену продажи.

## 2. Подтверждение клиентской публикации

В проверке сайта 07.10.2026 каталог обнаружен в hydration-данных страницы как queryKey
`products/list` с параметрами `shopId`, `light`, `with-stop-list`.
Это **ключ запроса клиентского приложения**, не подтверждённый URL HTTP API.
Точный API URL/метод по этой проверке не установлен; не конструировать его из queryKey.
При повторении использовать доступный read-only ответ/состояние сайта и записать
фактически наблюдённый источник, точку, параметры, время и охват ответа.

Связь товара сайта с Server — `analyticId` сайта = `products[].id` Server.
Не склеивать по названию: внутренний ID сайта и GUID Server могут различаться.
Наблюдённая запись с `status='active'` подтверждает публикацию в этом каталоге/точке
на момент снимка. Сохранять исходный status, присутствие GUID и результат сопоставления.
Отсутствие означает «не найден в полученном каталоге»; утверждение об отсутствии
публикации требует полного ответа, проверки фильтров, страницы/пагинации и правильной точки.

`mainMeal` не использовать как флаг продажи: в проверенном каталоге он был true у всех товаров.
`products/quick` — рекомендации; это не полный каталог и не источник для исключения SKU.
Наличие `with-stop-list` в параметрах не раскрывает само состояние стоп-листа.
В проверенном ответе отдельного stop-поля товара не обнаружено; active и присутствие
не доказывают возможность положить товар в корзину/заказать сейчас.
Для «доступен сейчас» нужен отдельный подтверждённый статус/проверка интерфейса;
без него возвращать unknown, не «в продаже без ограничений».

Вес сайта хранить отдельно как заявленный вес меню, с проверкой единицы по UI.
Он не доказывает смысл `unitWeight` Server, API-выход техкарты или фактический вес на кухне.

## 3. Применение к ABC и сетам

Для текущего ассортимента сначала построить universe по явным флагам, затем присоединить
продажи, включая нулевые. Для исторического ABC сохранить проданные тогда GUID,
даже если сегодня они сняты/удалены; сверка общего факта не должна терять такие строки.
Статус текущей публикации хранить отдельной колонкой, а не исправлять им факт прошлых продаж.
При unknown не считать SKU автоматически снятым; вынести в список проверки охвата.

Ролл вне самостоятельного меню может входить в реально проданный сет. Сохранять его
в производственном реестре компонентов по [правилам сетов](sales-and-sets.md),
без приписывания самостоятельной публикации, цены и коммерческого ABC.
Отсутствие продажи в периоде не доказывает слабый спрос, пока неизвестны доступность,
дата появления и роль блюда в сетах.

Датированный пример 07.10.2026: у «Бостона», «Вулкана» и «Маку» были deleted=false,
defaultIncludedInMenu=false; они не вошли в текущий ассортимент ABC и не нашлись
в полном полученном каталоге сайта. «Невада» имела true-флаг, нулевые продажи
за исследованный период и присутствовала на сайте. Это проверка метода, не постоянный
список исключений. Полученный каталог содержал 212 записей status='active';
количество и ассортимент при следующем чтении проверять заново.

## 4. Минимальные поля результата

`server_guid`, name, type/group, `deleted_raw`, `defaultIncludedInMenu_raw`,
`baseline_menu_status`, `site_analytic_id`, `site_present`, `site_status`,
`site_publication_status`, `orderable_now_status`, snapshot/source/shop, match_status.
Добавить период продаж и отдельную роль `standalone`/`set_component` при наличии доказательств.
Хранить живой каталог и raw-ответы в материалах задачи, а не внутри навыка.
