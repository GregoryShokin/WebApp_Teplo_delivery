# ABC роллов: три независимых рейтинга

## Единица анализа и исходный реестр

Задай одну сопоставимую популяцию на запуск: точка × период × согласованный SKU/размер
и режим продаж. Для первоначального ассортимента — роллы; коммерческие сеты считать
отдельно, не перемешивать «один сет» с «одной порцией ролла» в ABC количества.
Не смешивай штуки, порции, кусочки и килограммы в одном рейтинге объёма.

Сначала реестр номенклатуры/меню, затем LEFT JOIN продаж. Так позиции без продаж
не пропадают. Но ставить им 0 можно только при подтверждённой полноте выгрузки;
иначе значение неизвестно. Отдельно сохраняй даты ввода, доступность, стоп-листы
и продажи по месяцам. `deleted=false` не подтверждает доступность в меню весь период.
Новые, временно недоступные и выведенные позиции покажи отдельно от постоянного меню.

Разрезы, которые нельзя сложить дважды:
- самостоятельные продажи ролла — отдельный коммерческий спрос;
- продажи ролла как строки комбо — фактическое количество, со своей выручкой/стоимостью;
- количество ролла по рецептуре проданного сета — физическая нагрузка, не новая продажа.
Для полного физического объёма складывай только непересекающиеся способы наблюдения.
Если невозможно исключить пересечение строк комбо и раскрытия техкарты, показывай их
раздельно; не публикуй ложное «эффективное количество».

## Метрики

| Рейтинг | Мера | Интерпретация |
|---|---|---|
| ABC количества | Σ подписанных порций | Объём в пределах сопоставимой единицы |
| ABC выручки | Σ продаж после скидок | Роль в обороте выбранной популяции |
| ABC вклада после продуктов | Σnet revenue − Σfood cost | Вклад до остальных расходов |

Классифицируй абсолютные суммы, не foodcost% или процент рентабельности.
Средняя цена реализации = revenue/quantity; foodcost на порцию = cost/quantity;
при quantity≤0 эти средние не определены. Доля foodcost = cost/revenue при revenue>0.
Нельзя выдавать среднюю реализованную цену за действующую цену меню.

Для сравнения новой рецептуры используй её расход сырья и подтверждённые цены закупки
на согласованную дату. Исторический OLAP cost/порция отражает смесь старых рецептур,
периодов закупки и корректировок; не является автоматически будущей себестоимостью.

## Порог и одинаковые значения

Рабочий default — A до достижения 80%, B до 95%, C — остаток. Это параметр анализа,
не подтверждённый норматив «Тепла». Запиши выбранные пороги и правило границы.

Реализованная конвенция скрипта:
1. Для каждой метрики отдельно выбрать известные положительные значения eligible SKU.
2. Отсортировать по убыванию; одинаковые Decimal-значения объединить в группу.
3. Класс группы определяется накопленной долей **до** группы: <A → A; <B → B; иначе C.
   Таким образом, позиция/группа, пересекающая порог, остаётся в предыдущем классе.
   A может занимать больше 80%; это явно выбранное правило, а не ошибка округления.
4. Доля SKU = value/Σpositive; накопленная доля одинакова для связанной группы и
   включает всю группу. Для вывода порядок равных значений стабилен по sku_key.
5. Нули, отрицательные и неизвестные не участвуют в положительном знаменателе.
   Для них показываются `ZERO`, `NEGATIVE`, `UNKNOWN`, а не маскирующий класс C.
   Отрицательный вклад — отдельный список потерь; общий signed total сохранить.

Нельзя считать накопленные доли по смеси положительных и отрицательных вкладов:
доли могут выйти за100%. В metadata показывай положительную базу, отрицательную
сумму, общий известный итог, число неизвестных и исключённых позиций.
При неполноте данных рейтинг предварительный, даже если арифметически считается.

## Воспроизводимый helper

`scripts/abc_analysis.py` использует только Python stdlib и локальный CSV.
Не подключается к iiko/БД, не меняет каталог. Один ряд — один согласованный `sku_key`.
Дубли ключей — ошибка, агрегацию надо сделать явно до классификации.

Обязательные колонки:

```csv
sku_key,name,quantity,revenue,food_cost,cost_status,eligible
guid|size|standalone,Название ролла,100,40000,14000,verified,true
```

- quantity/revenue/food_cost — подписанные числа с точкой, без пробелов и разделителей тысяч.
- Пустое поле — неизвестное, не 0. Числа NaN/Infinity запрещены.
- `cost_status`: `verified` только после сверки покрытия стоимости и сетов,
  `unresolved` иначе. При unresolved вклад/ABC вклада не вычисляется, даже если есть число.
- `eligible`: true или false. Исключение из рейтинга не удаляет строку из результата.
- Дополнительные колонки сохраняются; имена выходных колонок, `_values` и `_eligible`
  зарезервированы и отклоняются. Состав/граммовки, наборы и доступность можно
  присоединить по sku_key после расчёта; helper сам не доказывает корректность связи.

```bash
python3 <skill>/scripts/abc_analysis.py --input rolls.csv --output rolls_abc.csv \
  --population "Черникова; роллы отдельно; 2026-07-01..2026-09-30; порции" \
  --coverage complete --a 0.80 --b 0.95
```

`--coverage complete` допустим только после сверки; при сомнении `partial`.
Скрипт сохраняет CSV и `<output>.meta.json` с правилом, SHA256 входа, параметрами,
границами, статусом данных и контрольными итогами. Выходные файлы должны быть новыми.
Проверяет форму данных и арифметику; полнота продаж и корректность foodcost остаются
ответственностью этапа сбора. Положительная база сама по себе не означает полный расход.

## Как использовать выводы

Сопоставь ABC количества, выручки и вклада с граммами ключевых ингредиентов,
заявленным выходом, составом сетов, трудоёмкостью и отзывами/возвратами, если они есть.
Ищи проверяемые гипотезы: востребованный дорогой в продуктах ролл; высокий вклад при
слабой видимости; слабая розница при высокой роли в сете; сложная операция при малом
вкладе. Не превращай ABC в причинный вывод об отношении клиентов к цене или качеству.
Финальный эффект изменения цены/рецептуры считай по всем переменным и добавленным
сменным затратам через `teplo-unit-economics`, с каннибализацией текущих заказов.
