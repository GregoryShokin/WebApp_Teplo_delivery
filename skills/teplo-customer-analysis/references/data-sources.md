# Карта источников клиентского анализа

Аудит 11.10.2026. Читай только нужную справку:

- [Starter](starter-sources.md): клиенты, заказы, корзины, RFM, бонусы, отзывы, коммуникации.
- [iiko](iiko-sources.md): iikoCard через Cloud, бонусные операции, короткая история
  доставки, OLAP для длинной истории и старые расчёты RFM.
- [Revvy](../../teplo-customer-research/references/revvy-access.md): внутренние
  оценки/диалоги и публичные отзывы. Там действующий помощник чтения и SignalR.

Обозначения доказательств: **live** — проверен датированный ответ с данными;
**schema** — текущая официальная схема; **code** — прочитанная реализация;
**archive** — локальный исторический снимок. Live одной карточки доказывает путь
доступа, но не полноту базы, поля или всех организаций. Schema не доказывает права.

## Источник каждого признака

| Нужный признак | Основной путь | Правило/ограничение |
|---|---|---|
| Клиентские ключи | Starter customer; Cloud delivery customer; iikoCard customer/info | Сохранять разные source ID. Live проверка показала несовпадение delivery и loyalty ID |
| Контакты для связи источников | Собственная CRM / order.phone / iikoCard customer/info | Нормализация и проверка связи; маскированные/чужие/общие номера не гарантируют человека |
| Выполненные заказы за длинный период | iikoServer SALES OLAP; сверка с Starter orders | Уникальный заказ, корректные статусы/возвраты, полнота клиентского ключа и каналов |
| Позиции и корзины | Starter order detail; iiko orders/OLAP по блюдам | Модификаторы/наборы/подарки не удваивать; исторические цены и наличие |
| Нынешний платформенный RFM | Starter customer/clusters (schema) | Неизвестны окно/пороги, monetary-фильтр описан как средний чек |
| RFM до снижения | Собственный пересчёт датированных заказов | Текущую метку не переносить в прошлое; сохранять as_of и версию |
| Фактическая выручка и денежная оплата | OLAP SALES + Starter order payments + iiko payments | Раздельные величины, сверить семантику, бонусы и возвраты; не считать попытки платежа выручкой |
| Баланс бонусов | iikoCard customer/info walletBalances (live); Starter balance (schema) | Снимок на дату чтения; общий баланс не заменяет историю |
| Начисления/списания/сгорание | iikoCard customer/transactions (live 1 строка); Starter transactions (schema) | Тип/статус/кошелёк, paging, правильный loyalty ID; origin +100 проверять по событию |
| Предложения и контакты | Starter history/distribution details (schema); текущие правила по teplo-promotions | Получил/увидел/применил — разные признаки; настройка триггера не доказывает доставку |
| Оценки и жалобы | Starter feedback с order IDs; Revvy private chat/history | Нет ответа ≠ доволен; public reviews отдельная выборка; клиентские реплики отдельно от шаблонов |
| Обещания/доставка | Starter deliveryTimeStamps; Cloud completeBefore/whenDelivered; рассказ клиента | Учитывать предзаказ и дисциплину отметок; timestamp не гарантирует физический факт |
| Сотрудник/тест/служебная выдача | Подтверждённый служебный список/тип операции/проверенный контекст | Не выводить из 100% бонусов или нулевой оплаты |
| Переменные расходы | teplo-unit-economics + teplo-rolls-analysis | По дате, каналу, зоне, составу; неизвестное не равно нулю |
| Причина ухода/повод/альтернатива | Персональный опрос; уже полученная обратная связь | Заказы показывают поведение, не заполняют эти поля автоматически |

## Доступ и актуальность

- Starter: публичная OpenAPI прочитана 11.10.2026 (373 paths, версия 0.1.0).
  В проверенном in-app браузере кабинет перенаправляет на страницу входа.
  Свежая клиентская выгрузка Starter в этом аудите **не выполнена**.
  Используй разрешённый вход/штатный экспорт; не считай старую сессию действующей.
- iiko: существующий environment-backed OAuth-клиент; live проверены customer/info
  и одна бонусная транзакция, метаданные OLAP. Точные пути и пределы — в справке iiko.
  Не копируй ключи/токены/сырые клиентские ответы в skill.
- Revvy: кабинет и чтение API проверены 11.10.2026 в отдельной справке. Полные259
  публичных отзывов по тогдашнему фильтру проверены экспортом; одна история из17
  сообщений проверяет механизм, а не весь корпус внутренней обратной связи.
  Старый `data-channels.md` ошибочно называет агрегированный список GET; фактически POST.
- Старые заметки июня полезны как указатели. Их метрики/выводы не становятся
  текущими, даже если рядом стоит «зафиксировано» или «финализировано».

## Как проверять перед расчётом

1. Выбери короткое окно и несколько реально существующих записей из источника.
   Проверь форму ответа, null, единицы денег и связь идентификаторов, не выводя контакты.
2. Пройди все страницы этого окна и сверь итог; для большого периода дели запросы
   по подтверждённым ограничениям источника. Пустой ответ по неверному ID не доказывает отсутствие данных.
3. Сопоставь несколько заказов между системами: ID/точка/дата/статус/итог/оплаты/позиции.
   Покажи несвязанные записи. Не устанавливай массовое правило склейки из одного совпадения.
4. Отдельно проверь заказ с бонусами/подарком и возвратом, когда такие случаи найдены.
   Если нет подтверждения денежной формулы — R/F можно считать при полной истории,
   M и вклад оставить предварительными.
5. Сохраняй только нужную аналитическую проекцию, дату, фильтр и сведения о полноте.
   Клиентские ответы могут содержать токены/карточные/контактные поля, не нужные анализу.

Для выборки клиентов и связанных заказов достаточно читающих методов. Не создавай
CRM-сегмент, не меняй профиль и не начисляй бонус ради проверки источника.
