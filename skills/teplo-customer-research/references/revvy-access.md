# Revvy: доступ, отзывы и программное чтение

Дата проверки: **2026-10-11**. Назначение — исследование клиентского опыта Тепла.
Кабинет: `https://admin.revvy.ru/auth`; базовый адрес внутреннего API: `https://revvy.ru`.
Не записывать пароль, JWT, клиентские телефоны или полные диалоги в этот скилл.

## Уровни доказательств

- **HTTP подтверждено** — запрос выполнен и ответ проверен в аккаунте Тепла.
- **UI подтверждено** — настройка или число непосредственно видны в кабинете.
- **Frontend подтверждено** — метод/схема извлечены из текущего публичного JavaScript; успешный ответ сервера этим не доказан.
- **Не проверено** — неизвестны публичные гарантии API, лимиты, срок хранения, SLA и webhook-контракт.
- Ни ссылка меню, ни наличие кода не доказывают включение функции в данном аккаунте.

Программное чтение первой страницы и Excel агрегатора подтверждены; прохождение всех JSON-страниц отдельно не проверено.
История одного проверочного чата получена через SignalR: 17 сообщений, включая клиентское уточнение и ответы компании. Сверены соответствие chatId, уникальность id и наличие текста из UI. Это доступная история конкретного чата, не доказательство бессрочного хранения всех данных.
Новый HTTP-тест дописывать с датой, фильтрами, кодом ответа, схемой и количеством; не подменять им старое наблюдение молча.

## Авторизация: контракт текущего frontend

`POST https://revvy.ru/api/authentication`, JSON `{"name":"<login>","password":"<password>"}`.
Frontend использует ответ `{userId,userName,jwtToken}`; авторизация HTTP 200 проверена в аккаунте.
Общий interceptor добавляет `Authorization: Bearer <jwtToken>` и `Accept-Language: ru-RU`.
UI проверяет `exp` токена. Refresh-механизм и гарантированный срок жизни не установлены.
Для скриптов передавать секреты через окружение/защищённый ввод; не в argv, журнал, skill или Git.
При 401 остановить выгрузку и восстановить авторизацию; не считать ответ пустым набором отзывов.

## Чтение чатов и истории

`POST /web/adminChat/chats` — чтение списка, несмотря на HTTP-метод POST.

```json
{"placeIds":[],"daysLimit":"30","search":"","pageOffset":"0","pageSize":"25","chatsCategories":[0],"sortType":2}
```

Ответ ожидается `{chats:[],chatsCount:N}`; этот вариант проверен HTTP в Тепле.
Для чатов `placeIds:[]` сработал; не переносить эту семантику на агрегатор.
`pageOffset` — смещение записей. UI сначала получает 25, затем порции 75; увеличивать offset на фактически пройденную порцию.
Категории: `0=All`, `1=NegativeReviews`, `2=PositiveReviews`, `3=InProgress`, `4=Unread`, `5=AnswersOnMassMailings`, `6=OrderStatus`.
Сортировка: `1=Asc`, `2=Desc`. Не складывать пересекающиеся категории в число уникальных клиентов.

Связанные методы:

- `POST /web/adminChat/chats-by-messages` — такое же тело; результаты по сообщениям, в том числе негатив; HTTP 200 проверен.
- `GET /web/adminChat/messages?chatId=<id>&messageChannel=<value from chat>` — инициирует получение истории; HTTP 200 с пустым телом наблюдался, см. SignalR ниже.
- `GET /web/adminChat/chat-info?chatId=<id>&messageChannel=<value>` — сведения о чате; HTTP 200, поля id/точка/имя/телефон проверены.
- `GET /web/places/places?withDeleted=false&withClassicForMaster=true` — точки; frontend.

UI при обновлении вызывает **оба** списка; каждый раздел показывает только при непустом результате.
Поэтому заголовок «Сообщения» и его 16 результатов относятся к `chats-by-messages`, а не `chats`.
В проверенных негативных результатах `uniqueIndex` заполнен, у общего списка чатов он null.
Не дедуплицировать негатив по телефону или одному chat ID: сохранять `uniqueIndex`, `lastMessageId`, канал и дату каждого наблюдения.

Пара `chatId + messageChannel` нужна для запроса и дедупликации; значение канала брать из ответа.
Критично: `/messages` **не подтверждён как HTTP JSON-выгрузка**. Для чата с видимой историей получено HTTP 200, 0 байт.
Frontend игнорирует тело этого GET и принимает историю через SignalR: `https://revvy.ru/hubs/admin_chat`, событие `SendMessagesToRevvyFront`.
Настройки соединения из кода: `accessTokenFactory` возвращает JWT, `skipNegotiation:true`, `transport:WebSockets`; слушатель получает массив сообщений, фильтрует по `chatId` и передаёт в `messages$`.
Подключать слушатель до GET. Программный приём SignalR проверен 11.10.2026: 17 уникальных сообщений одного чата за 09.02–18.09.2026, текст жалобы совпал с UI. Помощник ниже реализует этот порядок; пустое HTTP-тело не считать нулём сообщений.
При выборе результата по сообщениям UI всё равно передаёт его `id` как `chatId`; подменять его на `lastMessageId` нельзя.
В UI открытый чат содержит историю старше выбранных 30 дней. Поэтому фильтр списка чатов **не ограничивает даты всех сообщений внутри чата**.
Отбирать сообщения повторно по `dateReceivedUtc`/подтверждённому полю даты; сохранять исходную дату.
Frontend получает историю и отображает её локальными порциями по 100: 100 видимых сообщений не доказывают полноту истории.
Один человек может дать несколько оценок по разным событиям. Разделять «клиенты», «чаты», «оценки», «сообщения» и «заказы».

## Агрегированные публичные отзывы

Сначала получить допустимые значения, методы frontend:

- `GET /web/aggregatedreviews/reviews-{rating,status,source,place,date}-filters` — пять отдельных URL.
- `GET /web/aggregatedreviews/check_is_enabled`, `/check_is_configured`, `/check_is_ready` — три отдельные проверки.

Список: `POST /web/aggregatedreviews` с телом:

```json
{"pageNumber":1,"pageSize":20,"startDate":"<ISO UTC>","endDate":"<ISO UTC>","placeParams":["<values>"],"sourceParams":["<values>"],"ratingParams":["<values>"],"statusParams":["<values>"],"offset":0,"sortingType":2}
```

Четыре массива заполнять значениями и типами, полученными из соответствующих фильтров. Для «все» frontend перечисляет все значения.
HTTP подтвердил `{reviews:[],totalReviews:N}`. Переходить по `pageNumber` и сверять число уникальных отзывов с `totalReviews`.
Проверенные фильтры: `sourceParams:[0,3]` (Google, Яндекс), `ratingParams:[1,2,3,4,5]`, `statusParams:[0,1]`.
Точка: `placeParams:["28eb6c59-3555-4aa1-6633-08ddcf6afd49"]`. Это датированная привязка; при новом сборе обновить фильтры.
Проверенные границы: `2021-12-31T21:00:00.000Z`–`2026-10-11T20:59:59.999Z` соответствуют местным датам из UI при UTC+3.
Поля строк: `place{value,title,address}`, `platform`, `status`, `rating`, `userAvatarUrl`, `authorName`, `replyUrl`, `updatedAtUtc`, `platformUrl`, `text`, `photoUrls`, `videoUrls`, `organizationAnswer`, `answerCreationDateUtc`.
`updatedAtUtc` не переименовывать в дату первоначальной публикации без проверки семантики; явный review ID в проверенном наборе полей не подтверждён.
Границы выбранного локального дня frontend переводит в ISO UTC: начало 00:00:00.000, конец 23:59:59.999.
Не переносить сюда правило исключающей верхней границы iiko OLAP; сохранять фактические границы Revvy.

Экспорт: `POST /web/aggregatedreviews/excel` — те же даты и четыре массива, плюс `clientTimezoneOffset:3`, без пагинации.
Frontend ожидает blob `.xlsx`; HTTP 200 и файл с 259 отзывами + строкой заголовка проверены под указанными фильтрами.

## Журнал сообщений и ловушка Excel

Frontend: `POST /web/journalmessages/messages` с `pageNumber`, `pageSize` и фильтрами
`phone,sender,messageDateUtc,message,type,place[],state[],channel[],vkProviders[],startDate,endDate`.
Ожидаемый ответ `{messages:[],totalMessages}`. Журнал отправок не является списком клиентских отзывов.
Excel: `GET /web/journalmessages/excel?startDate=<UTCString>&endDate=<UTCString>`.
**В этом экспорте frontend передаёт только даты**, без остальных фильтров таблицы. После скачивания проверить область выгрузки.
Это отличается от `/web/aggregatedreviews/excel`, где передаются все четыре массива фильтров.

## Полнота, интерпретация и безопасная граница исследования

- Сохранять период, часовой пояс, точки, каналы, категории, сортировку, размер страницы и итоговые счётчики.
- При пагинации проверять дубли и пропуски; изменяющиеся данные могут сдвигать offset. Не объявлять первую страницу полной выгрузкой.
- Одинаковый текст наблюдался в Google и Яндексе: сохранять площадки, но помечать возможный кросспост и не считать его независимыми мнениями.
- Внутренний негатив и публичный позитив могут быть результатом маршрутизации запроса. Оценивать обе выборки отдельно.
- «Возвращённый клиент»/заказ после сообщения не доказывает дополнительный заказ или прирост прибыли. Нужны сравнение/контроль и полные издержки.
- HTTP POST может быть чтением отчёта; HTTP GET сам по себе не гарантирует отсутствие побочного действия.
- Не вызывать при сборе `/web/feedbacks/request_feedback`, `/batch_request_feedbacks`, `/web/adminChat/send/message`.
- Не менять `/mark-chat-as-read`, `/mark-all-chats-as-read`, `/change-chat-inprogress`; не запускать `/llm-hint` для простой выгрузки.
- Не менять интеграции, шаблоны, каналы, расписание и пороги оценок при исследовании; рассылка/ответ клиенту — отдельное действие.
- Публичные гарантии API и rate limits неизвестны: использовать последовательные умеренные запросы, остановку на ошибках/429 и ограниченный retry.

## Как собрать корпус за период

1. Задать местные даты/UTC+3, точку и дату среза. Для публичных отзывов выбрать весь диапазон оценок и статусов, получить все страницы либо полный Excel; сверить число строк с totalReviews. Не соединять публичную оценку и внутреннюю в один средний рейтинг.
2. Получить обе выдачи `/chats` и `/chats-by-messages` с согласованными фильтрами, пройти пагинацию каждой до собственного счётчика. Общий список чатов не равен списку оценок. Для закрытого исторического периода проверить семантику относительного daysLimit; при сомнении расширить выборку чатов и фильтровать сами сообщения по абсолютным датам.
3. Для объединения уникальных пар chatId+messageChannel прочитать историю через SignalR. Сохранить слова клиента (`isClient`) отдельно от исходящих шаблонов и ответов сотрудников; применить абсолютные границы к dateReceivedUtc. Связанные вопросы и ответы можно сохранить как контекст с собственной датой, не добавляя их в число оценок периода.
4. Категории негатив/позитив использовать как дополнительную сверку, сохраняя оценки, включая нестандартные значения, и сам текст. Один чат может иметь несколько отзывов; не удалять их как повторы клиента. В публичных отзывах кросспосты помечать отдельно от технических дублей пагинации.
5. Отчёт полноты: фильтры, total и полученные строки каждой выдачи, страницы, уникальные пары чатов, успешные/ошибочные истории, дубли, минимальная/максимальная дата сообщений. Если часть истории недоступна, назвать пробел и не подписывать результат «все отзывы». Событие SignalR — полученный серверный снимок истории; гарантии бессрочного хранения не установлены.

## Проверенный помощник чтения

Используй `scripts/revvy_read.py --plan /absolute/path/plan.json`. Python 3 использует стандартную библиотеку; для истории сообщений нужен Node.js с встроенным WebSocket (проверен Node 24). Путь задаётся `REVVY_NODE` либо берётся `node` из PATH. При необходимости найти установленный runtime через `load_workspace_dependencies`. `revvy_history.mjs` должен лежать рядом с Python-скриптом.

Авторизация: `REVVY_EMAIL`, `REVVY_PASSWORD` или интерактивный ввод. Пароль запрашивается без эха, JWT живёт только в процессе и передаётся Node через stdin. Не писать значения секретов в plan.

Пример плана для 30-дневной выборки негативных сообщений:

```json
[
  {
    "method": "POST",
    "path": "/web/adminChat/chats-by-messages",
    "body": {"placeIds":[],"daysLimit":"30","search":"","pageOffset":"0","pageSize":"25","chatsCategories":[1],"sortType":2},
    "output": "/private/tmp/revvy-negative-page1.json"
  }
]
```

Это одна страница, а не автоматическая выгрузка всего корпуса. Для последующих страниц составить план с обновлённым offset. Для истории взять id и messageChannel из строки результата, добавить GET `/web/adminChat/messages?chatId=<id>&messageChannel=<channel>` с отдельным output: помощник сам подключит SignalR, выполнит GET и сохранит массив из события. Безадресное пустое событие не объявляется пустой историей — помощник остановится с ограничением полноты.

Для агрегатора сначала получить пять фильтров, затем построить POST с заполненными массивами. Excel — отдельный POST по контракту выше с output, оканчивающимся на `.xlsx`. Помощник принимает только перечисленные методы чтения, валидирует весь план до входа, не перезаписывает существующие файлы, сохраняет ответы с правами 0600 и печатает только метаданные. Он не ставит чаты прочитанными. `--validate-only` проверяет план без сети. HTTP-ошибка останавливает план; уже сохранённые ответы остаются.

Проверка 11.10.2026: этим помощником получены 16 негативных результатов и 17 сообщений одного чата. Общая пагинация нескольких страниц самим помощником не автоматизирована. Полный XLSX агрегатора проверен отдельным HTTP-запросом: 260 строк вместе с заголовком.

Схема сообщений, подтверждённая в SignalR: `id, chatId, message, sender, isClient, dateReceivedUtc, dateCreatedOnServer, type, fileType, fileUrl, fileIcon, status, messageStatus, messageChannel, isMessageSendingAllowed`. `isClient` отделяет слова клиента от шаблона/оператора; наличие messageStatus не превращает исходящее сообщение в отзыв. Для аналитики фильтровать дату и направление; исходные файлы с контактами хранить вне skill и Git.
