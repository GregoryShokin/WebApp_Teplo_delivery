# Направление акций и граница модернизации — решение владельца 15.10.2026

> Исторический вариант. [Уточнение16.10](owner-offer-policy-2026-10-16.md) отменяет
> денежную шкалу, самовывоз10% и рефералов; возвращает прежнее начисление5/7/10%.
> Акционные наборы и пицца-комбо теперь исключаются только из списания.

Статус: **входы следующего предварительного расчёта; не свидетельство изменения продакшена**.
База и проверка: `business-docs/finance/unit-economics/kitchen-modernization/snapshots/2026-10-15/owner-offer-v2/`.

- **Только роллы:** новая начинка, качество сырья и целевой FC относятся к роллам,
  а не всему меню. Пицца, шаурма, горячие блюда сохраняют рецептуру/стоимость на
  единицу. Обязательна [разбивка по цехам](department-margins.md), в том числе наборы.
- **Удвоение убрать.** По пояснению владельца промо-цена обычно примерно вдвое выше
  обычной цены единицы. Сопоставлять одинаковое число порций при честной новой цене:
  две порции поP/2 вместо пары поP не дают сами по себе экономию продуктов.
  НЕ зачитывать12,1тыс.₽ подарочной себестоимости как автоматическую прибыль.
  Новую цену каждого SKU и поведение корзины считать отдельно.
- **День рождения неприкосновенен:** не уменьшать существующую скидку и не финансировать
  другие изменения её урезанием. При одной выгоде клиент может выбрать более выгодную,
  но сама возможность скидки дня рождения остаётся.
- **Первый заказ — обычная скидка15%.** Отдельную реферальную скидку первого заказа
  не сохранять как вторую механику. Но реферальный новичок вправе воспользоваться
  обычной15%, поэтому не объявлять всю прежнюю реферальную скидку возвращённой выручкой.
  Это не распоряжение молча отменить все остальные реферальные начисления/обязательства.
- **Самовывоз:** оставить текущие условия для расчёта до проверки до/после. Сравнить
  одинаковые окна по дням недели, количество/долю самовывоза, Starter и все каналы,
  средний чек/вклад. Первое применение ID не обязательно запуск: проверить старые ID,
  миграции и наличие истории. Простое до/после не доказывает причинность.
- **Подарочную шкалу убрать; денежная шкала — гипотеза:** от3000₽10%, от5000₽15%,
  от7000₽20% на корзину. Считать стоимость по фактическим корзинам; проверить пороговую
  базу, исключения, преимущество перед уже выбранной выгодой, эффект добора/слияния
  заказов. Скидка может стоить больше сэкономленной доставки/продуктов подарка.
- **Скидка большой корзины ИЛИ бонусы**, прямой ответ владельца: одна выгода на выбор,
  без суммы скидки и списания. Сохранить дневной налоговый/комиссионный/ФОТ пересчёт.
- **Бонусное списание сохранить:** общий лимит50% не менять на ранее предложенные20%.
  **Акционные наборы и комбо-наборы с пиццами** исключить и из начисления, и из списания.
  Прочие сеты автоматически не исключать. Нужны актуальные meal/category IDs и проверка
  смешанной корзины; товарное исключение не равно запрету бонусов на весь заказ.
- **Начисление**: накопленные покупки в рублях (рабочая интерпретация порогов, не число
  заказов): [0,5000) —0%; [5000,15000) —3%; [15000,35000) —5%; от35000 —7%.
  10% больше нет. Период накопления/переход уровней/учёт скидок отдельно уточняются
  перед настройкой. Остатки ранее заработанных баллов не аннулировать по умолчанию.

## Новые проверенные методы

- `GET /api/v1/frontend/loyalty_program/bonus-restriction` возвращает
  restrictAward, restrictRedeem, meals, categories. На15.10 обе настройкиfalse,
  списки пусты. Контракт/чтение подтверждены; исполнение с внешним iikoCloud и выбор
  товарных ID проверяются отдельно. Объявленные в OpenAPI combo-GET дали404 в текущем
  контуре; это не доказательство отсутствия товарного ограничения бонусов.
- Для first/last скидки: GET orders с `discount_ids=<ID>`, shop_ids=3, statuses=done,
  order_by=delivery_time / -delivery_time, limit1, затем detail подтверждает событие.
  Текущее ID самовывоза впервые найдено24.03.2026; старое выключенное ID найдено,
  но done-заказы точки3 по нему не вернулись. promotions/history по текущему ID
  total0: дату создания не утверждать. Последующие окна — наблюдение, не эксперимент.
- В старых Starter-строках после изменений POS поле item.price бывает суммой строки,
  а не ценой единицы. **Не умножать price×quantity без проверки.** Для новой корзины
  использован item.totalPrice положительных строк до скидки уровня заказа; нулевые
  подарки исключены. Проверять paid-lines сумму против price/totalPrice и iiko:
  поздние добавления специй/приборов расходятся с исходным price. Статический replay
  этих полей не подтверждает все сегодняшние правила корзины.
- Снижение начисления уменьшает будущие бонусные обязательства, а не мгновенно
  возвращает все старые списания. Исключение SKU из списания тоже может отложить
  погашение на другие товары/заказы. В расчёте первого месяца не зачитывать будущую
  экономию начисления без ledger/cohort. Нужны уровень на дату заказа, подходящая
  оплаченная сумма, начислено/списано/истекло/остаток и повторные покупки.
- Проверять «ступеньки»: корзина4999₽ со скидкой10% даёт4499,10₽ оплаты, корзина
  5000₽ со скидкой15% —4250₽. Это условие акции, а не арифметическая ошибка.
  При одном добавленном товаре денежная оплата может уменьшиться. Учитывать это
  в экономике добора, не предполагать прибыльность любого большего заказа.
