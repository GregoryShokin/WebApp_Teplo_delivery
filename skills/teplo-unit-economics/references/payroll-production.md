Срез кода: `170833b8`, ветка `codex/teplo-unit-economics-skill`.

Короткие имена сервисов означают `apps/api/app/services/<имя>.py`.

## 1. Граница расчёта и входы

В production входят должности из `position_registry.production_payroll_positions()`; тестовый реестр — Повар и Кассир.
Роли кухни и сменного администратора внутри этого контура не равны должностям офисной администрации.
Курьер, окладники и посудомойка имеют отдельные контуры; не переносить на них эту формулу.
Ядро: `payroll_calculator.py:495 calculate_payroll_lines_from_inputs`; загрузка источников — `:172 calculate_payroll_lines`.
Нужны минуты/дата/роль/station, историческая категория и должность, активные надбавки, выручка дня, версии правил, корректировки, отпуска.
Период production: вторник–понедельник, выплата во вторник (`payroll_runner.py:95 compute_next_payroll_period_dates`).
Отсутствующая обязательная настройка, ставка, роль, категория или неготовый сотрудник блокируют расчёт (`payroll_calculator.py:1421`).
Missing не равно нулю: сначала проверять полноту входов, затем считать сценарий.

## 2. От фактических интервалов к минутам

`attendance_loader.py:255 build_attendance_entry`: work_date — дата открытия в Europe/Moscow; секунды отбрасываются вниз.
Закрытый интервал >720 минут ограничивается 720 с записью `capped_to_12h_from_*`; фактическое время окончания сохраняется.
Незакрытая явка получает расчётное окончание по настройкам закрытия/лимита и `is_open=True`; это предположение, не закрытый факт.
`payroll_calculator.py:72 merge_attendance_minutes` объединяет пересекающиеся и смежные интервалы, ограничивая каждый кластер 720 минутами.
Раздельные кластеры суммируются: 8 часов + перерыв + 6 часов дают 840 минут; общего суточного cap в этой функции нет.
Для отсутствующего/вырожденного интервала fallback = max(0, minutes_worked), без дополнительного cap720.
Начисления группируются по (сотрудник, роль, день, station); минуты для пт/сб объединяются отдельно по (сотрудник, день) (`:515–557`).
Пересечения внутри разных ролей/station не объединяются в единую группу базового оклада; входы должны корректно разделять работу.
`shift_pay_ratio` (`:2227`) = минуты/720 без собственного cap; cap веса процента применяется отдельно.
Тесты: объединение/сплит — `apps/api/tests/test_payroll.py:1174`, 13 часов — `apps/api/tests/test_payroll.py:2270`.

## 4. База, Старший/Зам и пт/сб

`base_shift_pay` (`payroll_calculator.py:2007`): S_g = rate_g × m_g/720.
`seniority_allowance_details_for_payroll_entry` (`:2040`): A_g = amount(position, senior/deputy, date) × m_g/720.
Seniority здесь означает роль Старший/Зам, а не стаж в месяцах; при двух флагах Старший приоритетнее Зам.
Сумма A — PayrollSeniorityPremium по должности/роли/from,to), latest from; не hardcode 500/300 (`seniority_allowance_service.py:56`).
Для поваров надбавки независимы; для кассиров выбирается один получатель на день (`seniority_allowance_resolver.py:47`).
Кассир: ручное назначение/none приоритетно; единственный Старший/Зам; при Старшем и Зам — приоритет плана, иначе Старший.
`weekday_premium_for_employee_day` (`payroll_calculator.py:2184`): D=amount один раз/сотрудник/день в пт или сб, если общие минуты ≥threshold_hours×60.
Источник D — AppSetting `payroll.weekday_premium`; defaults amount=200, threshold_hours=8; threshold может приходить из widget_options (`:2199`).
D не умножается на m/720; применяется к первой подходящей группе дня. Стажёр не исключён; freelancer исключён.
Итог `base_pay_g = S_g + A_g + D_g` (`:710`); A и D уже внутри base_pay — не добавлять их второй раз.
В текущем ядре нет отдельного автоматического +1 часа и нет множителя ×1.5; доплата может поступить как отдельная явная корректировка.
Тесты: [8ч в пятницу: 2200×8/12+200=1666.67 — `apps/api/tests/test_payroll.py:3436`, история Старшего: 2200→2700 — `apps/api/tests/test_payroll.py:4145`.

## 6. Общий процентный пул и его распределение

Источник ставок — RevenueTier по дате; коэффициентов — CategoryCoefficient (`payroll_percent.py:97`, `:122`).
Default effective_from=2026-01-01; ниже 50 000 ставка отсутствует; 50 000,140 000) 3.5%; [140 000,190 000) 4.5%.
Default продолжение: [190 000,550 000) 5.5%; [550 000,∞) 6.5% (`payroll_percent.py:18`); это не подтверждение текущей БД.
`revenue_tier_rate` (`:201`) применяет [min,max), [from,to), latest from; rate_percent хранится долей (.045), не числом 4.5.
`compute_daily_percent_pool` (`:149`): P_d = R_d × r(R_d,d); ставка применяется ко ВСЕЙ дневной выручке, не только превышению порога.
`shift_weight` (`:257`): w_g = k_g × min(m_g/60,12)/12; при k≤0 или m≤0 вес0.
Default k: category_1=10, category_2=7.5, category_3=5, category_4=2.5, intern=0, freelancer=0 (`:49`).
category_4 и intern — разные категории; не обнулять category_4 по старой таблице «категория4=стажёр».
`distribute_percent_pool` (`:161`): percent_g = floor(P_d×w_g/Σw), целые ₽; при Σw≤0 всем0; остаток не распределяется.
Production передаёт ключ (сотрудник, роль, день, station), поэтому floor происходит по этим группам (`payroll_calculator.py:597`).
Часы входят только в вес; повторно умножать полученную долю на m/720 нельзя.
Начислено процентом = Σpercent_g, а не автоматически P_d; при положительных весах округление оставляет <числа положительных групп ₽.
Добавление людей не создаёт ещё один пул: меняются доли и округление; отдельные базовые оклады и надбавки растут.
Если нет положительных весов, даже положительный рассчитанный P_d не начисляется; не заменять этот случай выплатой всего пула.
Пустой список tier/coeff использует defaults; непустой список с дырой по дате/выручке даёт no_rate/коэф0 (`payroll_percent.py:209`, `:241`).
Тесты: [пороги — `apps/api/tests/test_payroll.py:3114`, 6750→3000/2250/1500 — `apps/api/tests/test_payroll.py:3129`, 11ч без второго prorate — `apps/api/tests/test_payroll.py:3387`.

## 7. Скачки затрат на порогах

При default tiers и росте R на 1 ₽: 49 999→50 000 даёт ΔP=1750 ₽; 139 999→140 000 — ΔP=1400.035 ₽.
189 999→190 000 даёт ΔP=1900.045 ₽; 549 999→550 000 — ΔP=5500.055 ₽.
Это изменения теоретического пула; изменение начисленного процента считать через Σfloor с фактическим составом дня.
Внутри одного tier при том же составе ΔP=r×ΔR; при пересечении порога пересчитывать оба полных дневных пула.
Средний % ФОТ/выручка не заменяет эту функцию; распределение прироста продаж по дням существенно.

## 8. Накопительный фонд

`fund_accrual_for_day` (`payroll_calculator.py:2296`): F_g=floor(base_pay_g×f(полные месяцы стажа на work_date)), целые ₽.
База F включает S+A+D; не включает процент с выручки, ручные премии, отпуск и lump-отпускные.
Источник ставок f — AppSetting payroll.fund_rates_by_tenure; hardcoded актуальной сетки в функции нет.
`_fund_rate_for_months` (`:2314`) поддерживает min_months/min_years; последняя подходящая строка побеждает, сортировки нет.
Тестовая сетка: <6м 0%, ≥6м 5%, ≥12м 10%, ≥18м 15%; не выдавать её за прочитанную production-настройку.
Стаж: tenure_started_at, иначе hire_date; полные календарные месяцы, до дня годовщины месяц не засчитан (`:2286`).
F=0 при исключении фонда, базе≤0, непроизводственной текущей должности, freelancer или substitute (`:713`, `:2296`).
Проверка должности фонда использует employee.position сейчас, хотя надбавки используют историческую должность; учитывать при ретрорасчёте.
fund_excluded_until включительно; округление F идёт по группе дня, не раз за неделю (`:2375`).
F отражается отдельно в PayrollLine.fund_accrual, не входит в total_payable; расход/обязательство не исчезает из-за отсрочки выплаты.
`payroll_runner.py:1054 accrue_fund` записывает accrual, предварительно снимая предыдущие начисления этого run; год = period.end_date.year.
Выплата прошлого года — отдельное движение: policy 15 января; runner проверяет попадание 15 января в неделю (`:1165`), не начисляет F заново.
При выплате сервис исключает уволенных/неактивных и списывает их остатки (`accumulation_fund_service.py:130`); это отдельная корректировка обязательства.
Тесты: стаж 5→6м и фонд0→110 — `apps/api/tests/test_payroll.py:4449`, 8ч пт: floor(1666.66…×5%)=83 — `apps/api/tests/test_payroll.py:4483`.

## 10. Отпуска и корректировки

`vacation_service.py:378`: отпуск без payout_date оплачивается подневно; daily amount из vacation.daily_amount, default1000.
Для такого дня калькулятор заменяет смену отпускными, S/A/D/процент/F=0, даже если явка существует (`payroll_calculator.py:654`).
Отпуск с payout_date исключён из подневного начисления; amount=days_count×daily amount попадает один раз в ведомость этой даты (`vacation_service.py:399`).
В строке lump включён в vacation_pay, но исключён из базы НДФЛ и депозита; F=0 (`payroll_calculator.py:774`, `:836`, `:865`).
Это описание реализации, не налоговое заключение; не начислять отпуск повторно по дням плюс тем же lump-траншем.
В текущем P&L lump имеет `components.days[].kind=vacation_payout` и `date=payout_date`; проектор использует эту дату, а не дни отпуска.
При границе месяца дополнительно проверить охват: отбор runs идёт по периоду работы, а payout_date может быть за его пределами; возможен пропуск транша.
Для сверки отчёта сохранять его методику и отдельно показать расхождение; перенос на дни отпуска допустим только как явно названная отдельная модель, не молчаливая правка факта.
`apply_adjustments_to_line_totals` (`:1296`): bonus→premium, penalty→manual_deduction; обе даты периода включительно.
При нескольких ролях корректировка прикладывается только к primary line; admin-roles исключены штатной загрузкой (`:282`, `:1319`).
Премия не увеличивает F: корректировки добавляются после расчёта фонда; отдельной автонадбавки за мойку/допчас ядро не создаёт.
Ревизионные штрафы входят через корректировки/DeferredAuditCharge; runner может распределить/свернуть удержания и пересчитать строки (`payroll_runner.py:501`).
Штраф не считать заранее гарантированным снижением затрат; его P&L treatment и законность не выводятся из payable-кода.

## 12. Начислено, удержано, к выплате

G = base_pay + premium + percent_pay + vacation_pay (в последнем поле подневные+lump).
Первичный total_payable = max(G−НДФЛ−manual_penalties−deposit_withholding,0) (`payroll_calculator.py:827–906`).
Общей гарантии минимальной суммы «на руки»/доплаты до МРОТ в этом production-ядре не найдено; нулевой floor payable не отменяет начисленные компоненты.
Депозит: min(стандартное удержание, max(цель−баланс,0), положительная база); источник — override карточки, затем payroll.category_rules (`:2330`).
Депозит удерживается один раз на primary role; исключения run/сотрудника/substitute/полностью собранного планового вывода учитываются отдельно.
База депозита не включает lump; дата проверки личного исключения по умолчанию date.today(), не work_date (`:2344`).
Выдача депозита — отдельное поле deposit_payout_scheduled; депозитное удержание создаёт обязательство, не экономию ФОТ.
Runner далее учитывает авансы, уже выданную наличную оплату freelancer, банковские выплаты и округление payable (`payroll_runner.py:555–569`).
`payroll_rounding.py:19/28`: итог сотрудника по всем ролям округляется вниз до5 ₽; base/premium/percent/fund не уменьшаются.
Одинаковый труд нельзя учесть расходом при начислении, затем повторно при выплате/возврате аванса/выдаче фонда или депозита.

## 13. Прирост затрат для сценария

Рассчитывать два полных состояния по дням и группам: штат/часы/роли/категории/ставки/выручка/корректировки до и после.
ΔPayroll_accrual = ΔΣ(base_pay + premium + percent_pay + vacation_accrual + fund_accrual); работодат. начисления — отдельным подтверждённым источником.
vacation_accrual здесь — начисление в явно выбранной методике периода без повторного lump; при сверке использовать правила текущего P&L и отдельно показать пробелы покрытия.
Подтверждённые уменьшения обязательств/расхода учитывать отдельной сверенной строкой, не смесью всех deduction из ведомости.
При неизменных сменах S/A/D/F обычно не растут от заказа; добавочный заказ меняет процент через R и возможный переход tier.
Новая смена добавляет S/A/D/F и перераспределяет существующий процентный пул; не добавлять её процент поверх неизменённого старого пула.
Новый час до cap увеличивает S/A и потенциально F; достижение действующего threshold_hours в пт/сб добавляет D целиком; процентный вес меняется до12ч.
Пересечение стажевого порога, смена ставки/категории/получателя надбавки — отдельные скачки; кадровые обещания не моделировать по среднему ФОТ/заказ.
Нулевой payable или выплаченный аванс не означает нулевой предельный расход; «резерв» не добавлять поверх уже включённого fund_accrual.
