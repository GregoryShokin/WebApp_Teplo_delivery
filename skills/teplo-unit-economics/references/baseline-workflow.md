# Рабочая база экономики: сбор и сверка без изменения учёта

Используй для запроса «посчитай экономику последнего закрытого месяца» и перед сценариями роста.
Пути ниже относительны корню репозитория. Формулы незарплатных статей — в [nonpayroll-sources.md](nonpayroll-sources.md), ФОТ — в [sources-and-reconciliation.md](sources-and-reconciliation.md).
Результат состоит из исходного P&L, проверок его полноты и отдельного слоя доказанных аналитических поправок — reconciliation overlay.

## 1. Зафиксируй задачу и границы чтения

- Определи организацию/подразделение, валюту, локальную часовую зону, период и нужную единицу: месяц, день, заказ или товар.
- Для первого базового расчёта сначала установи состав и качество месячного факта; не подставляй старые проценты маржи, тарифа канала или ФОТ.
- Найди актуальный worktree и запусти `scripts/check_sources.py --repo ...`. Совпадение хешей подтверждает только проверенные исходники, не текущие настройки БД или полноту учёта.
- Используй уже разрешённый read-only доступ и готовые снимки. Не запускай sync, recognize, calculate/finalize или закрытие месяца для получения факта.
- Прямой DB-доступ: отдельная транзакция `BEGIN READ ONLY` и `ROLLBACK`; точечные SELECT. Перед незнакомым GET проверь реализацию: некоторые GET пишут очередь или разрешают явки.
- Производственные данные сохраняй в приватный рабочий каталог, а не в skill. В выводе — агрегаты и необходимые идентификаторы источников без персональных сведений и реквизитов.

## 2. Выбери период по покрытию, а не по названию

Собери небольшую матрицу последних завершённых месяцев:

| Проверка | Что подтвердить |
|---|---|
| Закрытие | Запись `AccountingPeriodClose`; отдельно факт окончания календарного месяца |
| P&L | Статусы источников, компоненты, missing_lines, warnings, cash reconciliation |
| iiko | Полный месяц, нужное подразделение, актуальность sales/foodcost/couriers/partners отдельно |
| ФОТ | Все пересекающие месяц production/admin периоды, finalized, календарная нарезка дней |
| Налоги | Фактическая оборотка нужного месяца; непокрытые компоненты и прогноз отдельно |
| Документы | Признание услуг периода, поздние документы, нерешённые предоплаты, пропущенные начисления |
| Потери и ОС | Ревизии/списания, товарная разметка, амортизация и выбытие |
| Контрольная таблица | Реальный год и месяц вкладки, формулы и полнота заполнения |

- Проверенный read-only список закрытий: `GET /api/v1/accounting/suppliers/periods`; DB `accounting_period_close(period_month,created_at)`.
- Поле API `closed_at` формируется из DB `created_at`; наличие замка не подтверждает полноту всех расходов.
- `GET /api/v1/accounting/suppliers/periods/readiness?month=YYYY-MM-01` — только вспомогательная проверка зависших начислений услуг. Она не заменяет матрицу выше и может вернуть проблему другого месяца.
- Если закрытых месяцев нет, прямо сообщи это и выбери наиболее подтверждённый завершённый месяц как **незакрытую рабочую базу**. Не останавливай полезный расчёт и не закрывай период сам.
- Если последний завершённый месяц хуже покрыт, объясни выбор более раннего месяца. Свежий месяц можно показать отдельно как частичный, без смешения их данных.
- Для Google Sheets сначала прочитай список вкладок, затем ячейки периода и заголовки внутри нужной вкладки. Сопоставь год, месяц, даты документов/операций и формулы.
- Название файла с годом, вкладка с номером месяца, заголовок «Факт» и наличие суммы по отдельности не доказывают, что это нужный период. Старый год в заголовке может означать копию шаблона либо чужой факт — проверяй содержимое.
- Отсутствующая вкладка не подтверждает нулевой месяц. Не создавать и не заполнять её в рамках read-only расчёта.

## 3. Сними исходную проекцию и первичные ключи

- `GET /api/v1/reports/pnl?month=YYYY-MM` либо `projector.build_report(session, month)` — исходная версия P&L.
- Сохрани ответ целиком: lines с components, missing_lines, warnings, quality и reconciliation. Сумма net_profit без этих полей не является проверяемой базой.
- Зафиксируй время извлечения, HEAD, период, полученные источники и версии DB-правил. Параметр `today` проектора меняет ожидания документов; он не восстанавливает исторические суммы на ту дату.
- Прочитай текущий каталог `pnl_line`, активное разнесение `pnl_article_rule`, применимые manual entries. Seed-миграции не заменяют текущую конфигурацию.
- Расшифровка спорной строки: `GET /api/v1/reports/pnl/lines/{line_code}?month=YYYY-MM` либо `drill.build_drill`.
- Дополнительные чистые чтения: `/reports/pnl/ledgers/payroll`, `/ledgers/partners`, `/ledgers/goods`, `/ledgers/recognition`; параметры и ограничения см. в справках источников.
- Не читать `/reports/pnl/workup-review` в строгом read-only режиме: route достраивает очередь и делает commit.

## 4. Подтверди iiko без ошибочного вывода из timestamp

- `pnl_iiko_fact` хранит ключ `(period_month,metric_code,direction)`, amount, previous_amount, rows_count и source_ref.
- `synced_at` существующей строки не обновляется адаптером: это дата INSERT, не время последнего успешного чтения и даже не последнего изменения amount.
- Общий максимум synced_at по месяцу может принадлежать другой метрике. По нему нельзя ни признать выручку свежей, ни объявить месяц неполным.
- Проверь журнал успешного полного прогона и/или получи разрешённый независимый read-only ответ того же preset за полный период. При отсутствии подтверждения обозначь неизвестную свежесть, не обнуляй сумму.
- Сохранённые preset-фильтры, организация/Department.Code, группировки, исключения удалённых/возвратных и границы дат входят в описание контрольного источника.
- `aggregate_revenue_rows` не фильтрует `Department.Code`; неизвестные CookingPlace пропускает из total. Проверяй оба условия до сравнения.
- Для preset интервал `[первое число месяца; первое число следующего месяца)`; для каждого другого endpoint используй его проверенную семантику конца периода.
- Сверь gross/net revenue, foodcost и направления. «Суши» и «Специи» могут относиться к общему rolls; total и направления могут различаться на копейки из-за отдельного округления.
- Одинаковая выручка при отличающемся foodcost совместима с поздним уточнением себестоимости, но сама не объясняет причину. Не называй заметную разницу «округлением» без расчёта максимального возможного эффекта.
- Отдельно сверяй courier expense и партнёрские начисления; поля разных зеркал могут иметь разную семантику timestamp.
- Для результата на заказ используй согласованный знаменатель учтённых продаж и тот же охват каналов/подразделения/дат. Завершённые доставки — отдельная операционная популяция. Количество строк агрегированного OLAP не является количеством заказов.
- Если используешь дневной preset с `OpenDate.Typed` и агрегатом `UniqOrderId`, проверь, что поле действительно содержит число уникальных заказов, а не ID; проверь NOT_DELETED-фильтры и сверку дневных gross/net с канонической месячной выручкой. Дневной accounting date может отличаться от календарной даты закрытия; положительность/оплату и возвраты такой счётчик сам по себе не доказывает.

## 5. Сверь ФОТ и независимые расходы

- Факт ФОТ — finalized runs, пересекающие календарный месяц; включаются дни внутри месяца, а не целые недели по дате выплаты. Следуй `pnl/sources/payroll.py::build_payroll_month`.
- Production, admin, обычные курьеры и налоговая оборотка — разные контуры. Проверь, не входит старший курьер уже в admin.
- Авансы, выплата фонда, депозиты, платежи зарплаты и резервы не добавляются поверх начислений. Премии проверяй между line и adjustments, НДФЛ — между gross/net и налоговой строкой.
- Не пересчитывай прошлый факт по текущим ставкам; не превращай ShiftCostEstimate или средний ФОТ/выручка в полный фактический расход.
- Для услуг проверь период, status=recognized, документы/самоакты и разнесение. Предоплата не закрывает пробел признания автоматически.
- Foodcost, закупки, списания, проработка и инвентаризационные потери — разные движения. Пройди правила против двойного счёта в nonpayroll-sources.
- Удержанная банковская комиссия, комиссия партнёра, агрегатора и сайта/приложения требуют собственных оснований; не переносить ставку одной на остальные.
- Для эквайринга и банковских услуг отдельно найди доплату до минимального месячного платежа, фиксированные части и пороги тарифа. Они делают предельные затраты отличными от среднего месячного процента; при сценарии пересчитай полный тариф канала до/после.
- Пустая налоговая оборотка или амортизационные entries — неизвестное покрытие; модельный налог приложения не подтверждает окончательные вычеты, дополнительный взнос и НДС.

## 6. Разбери неполноту в порядке влияния на результат

| Сигнал | Read-only проверка | Что нельзя делать |
|---|---|---|
| `missing_lines` | Источник отсутствующей строки и первичный документ | Считать отсутствующий расход нулём |
| `recognition_unattributed` | `recognition.build_recognition_layer(...).details`, article_id=None; accrual→invoice/draft line | Брать полную сумму многомесячного accrual вместо доли месяца |
| `unmapped_cash` | `_classify`/`build_context` либо SELECT отсутствующих активных article rules; отдельно in/out | Вычитать общую сумму модулей из прибыли |
| `cash_alongside_accrual` | `cashflow.explain_line` + признанные документы той же статьи; период, предмет и первичная связь | Объявлять все совпадения статьи/суммы дублями |
| `cash_proxy` | Определить период и природу платежа, его документ/контрагента | Выдавать дату денег за подтверждённое начисление |
| `unparsed` acquiring | Первичные назначения входящих банковских операций | Принимать отсутствие распознанной комиссии за нулевой тариф |
| iiko difference | Тот же preset, фильтры, полный месяц, направления и precision | Перезапускать sync ради перезаписи зеркала |
| Неизвестные проценты | Раздельные тело/проценты по выписке/графику кредитора; уже учтённый overdraft_fee | Считать всё погашение кредита расходом |

- Для банковской первички используй связь `bank_operations.cashflow_transaction_id`; для кассы — `source_kind/source_id`. Совпадение суммы и даты не является надёжной связью.
- Для непривязанного признания используй `accrual_id`, `invoice_id`, `expense_draft_line_id` и период услуги. Только после проверки исключи второй учёт той же первички в других слоях.
- Mixed warning — причина проверить, не величина готовой поправки. Подтверждённый дубль отменяет повторный расход; разные реальные расходы оставляются оба.
- Долгового автоматического источника процентов может не быть. Если платёж не разделён и графика нет, оставь `loan_interest` неизвестным; не трать бесконечное время на угадывание.
- Проверяй components и warnings даже при `line.status=ok`: `_collapse` признаёт строку известной при одном известном компоненте, хотя второй отсутствует.
- Cash reconciliation с drift=0 и missed_count=0 подтверждает разбор загруженных движений. Дополнительно нужны unmapped_count=0 и независимое подтверждение полноты загрузки; нулевой drift не закрывает прочие источники.

## 7. Оформи отдельный reconciliation overlay

Исходный app-P&L не переписывай. Для каждого аналитического изменения сохраняй:

| Поле | Содержание |
|---|---|
| Статья и исходная сумма | Ссылка на исходный snapshot и компонент |
| Новое свидетельство | Документ/контрольный ответ, период, дата чтения |
| Поправка к расходу/доходу | Знаковая сумма и формула без смешения знаков |
| Поправка к прибыли | Отдельная Δ: рост расхода отрицателен, отмена дубля положительна |
| Причина | Обновлённый foodcost, пропущенное признание, доказанный дубль и т. п. |
| Статус | Подтверждено, условно или не определено; что осталось проверить |

- `Рабочая известная прибыль = исходная сумма известных статей + Σ подтверждённых Δ прибыли`.
- Если остаются неизвестные расходы/доходы, это не полная чистая прибыль. Условные поправки вынеси в отдельный сценарий, не смешивай с подтверждёнными.
- Разницу foodcost из полного сопоставимого контроля можно показать отдельной корректировкой с датой; причину изменения не выдумывать.
- Непопавшее в каскад признание можно включить аналитически только после проверки природы расхода, месячной доли и отсутствия дубля.
- Неразнесённые out/in могут быть расходом, возвратом, переводом, кредитом или расчётом по уже признанному документу. До классификации оставляй их неопределёнными.
- Погашение, уведомление, начисление, долг и резерв по одной обязанности не суммируются в несколько расходов.

## 8. Заверши полезным результатом и переноси только устойчивые знания

- Укажи выбранный месяц и его статус; исходные выручку/EBITDA/известную прибыль; подтверждённые поправки; рабочий результат; существенные неизвестные и границы применимости.
- Если пользователь просит только базу, не требуй модель роста для завершения. Если нужны сценарии, переходи к [growth-model.md](growth-model.md) с датированными драйверами затрат.
- Средняя себестоимость/комиссия/доставка на заказ — характеристика состава базы, не автоматически предельная стоимость будущего заказа.
- В skill сохраняй пути, методы, формулы, ключи, правила покрытия/знаков и подтверждённые ловушки. Разовые суммы, персональные ведомости, секреты и копии первички оставляй в приватных материалах задачи.
- Manifest дополняй только реально проверенными исходниками; проверку полноты бизнеса не подменяй совпадением хешей.

## 9. Проверенный способ доступа в текущем окружении

На 07.10.2026 read-only сбор выполнен через уже настроенный SSH alias `teplo-prod`,
репозиторий `/opt/teplo`, контейнер `teplo-api`, рабочая директория приложения `/app/apps/api`.
Это ориентиры обнаружения, не гарантия текущей инфраструктуры и не разрешение обходить доступ.
Перед повторением проверь alias, контейнер, HEAD и права; не выводи env или секреты.

В существующем Python окружении приложения используй `AsyncSessionLocal` и отдельную
транзакцию `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`, затем
`SET LOCAL statement_timeout='30000ms'`. Вызови проверенные функции чтения:
`projector.build_report(session, month_start)`,
`payroll.build_payroll_month(session, month_start, month_end_inclusive)`,
`recognition.build_recognition_layer(...)`, `drill.build_drill(...)`.
После чтения `await session.rollback()`, в конце `await engine.dispose()`.
Не использовать commit и helpers ensure/sync.

Для зарплатной структуры агрегируй поля `breakdown_by_employee` на сервере и выводи
только суммы base_pay, percent_pay, vacation_pay, bonuses, fund_accrual,
other_penalties, audit_penalties. Начисленный ФОТ с фондом **до сторно и налогов** =
первые пять сумм минус other_penalties. Для совпадения с расходом P&L отдельно учти
допустимое сторно накопительного фонда `fund_forfeited` через `projector._apply_releases`
и остальные компоненты соответствующих строк. audit_penalties уже уменьшают
ревизионные потери отдельно.
Фраза «без курьеров» неоднозначна: iiko-расход обычных курьеров выделен отдельно,
но оклад старшего курьера может оставаться внутри административной ведомости.

Для iiko проверенные функции находятся в `pnl/iiko_sync.py`: `_fetch_preset`,
`aggregate_revenue_rows`, `courier_salary_from_rows`, `fetch_partner_commissions`.
Настроенные реквизиты читает `_load_source_credential_env` из `services/iiko_sync.py`;
значения не печатать. `_fetch_raw('/v2/reports/olap/presets', {})` возвращает bytes:
перед разбором metadata выполнить `json.loads`. Не вызывать `sync_month`.
