# Источники акций и повторная проверка

## Найти источники и зафиксировать охват

Сначала определи дату проверки, точку, организацию и каналы: сайт, приложение,
доставка, самовывоз. Текущие настройки, клиентский текст и факт применения — разные слои.
Старый snapshot использовать с его датой; его нельзя молча выдавать за сегодняшние правила.

Найди checkout Teplo через контекст проекта и `git rev-parse --show-toplevel`;
все пути к коду ниже считаются относительно найденного корня `repo`.
Проверь HEAD и инструкции репозитория. Постоянный main можно читать, выгрузки туда не писать.
При наличии `graphify-out/graph.json` начни поиск связей через graphify, затем проверь код.
Исторические `business-docs/marketing/data-channels.md` и `diagnostic.md` — ориентиры,
а не текущий контракт или доказанное соответствие Starter ↔ iiko.

## Starter: интерфейс и официальный контракт

В существующей разрешённой сессии открой раздел маркетинга
[CRM Тепла](https://crm.starterapp.ru/fmteplo/admin/marketing/promotions).
Пройди скидки, промокоды, подарки/шкалу, бонусную программу, рефералы и триггеры.
В бонусной программе проверь все вкладки: уровни, welcome, сгорание, правила,
ограничения меню и активацию. Список не заменяет карточку с ограничениями.
Используй наблюдённые ссылки интерфейса; не угадывай ID карточек и приватные маршруты.

Текущий контракт: [Starter OpenAPI](https://crm.starterapp.ru/fmteplo/api/v1/openapi.json).
Сначала проверь `servers`, актуальные paths и response-схемы: старые DTO/PUT из документов
могут отличаться от текущих. Для этого tenant схема давала base `/fmteplo`.
Успешное чтение OpenAPI доказывает форму контракта, а не текущие значения настроек.
Схемные `default`, `null`, отсутствие поля и фактическое `false` не взаимозаменяемы.
Авторизация/роль может запрещать маршрут, хотя он описан в публичной схеме.

Предпочти документированный GET в существующей разрешённой сессии с последующим локальным разбором.
В Chrome это может быть обычная навигация на точный API URL через доступный CUA
и чтение отображённого JSON либо штатное Save As: браузер сам использует сессию,
cookies не экспортируются. При недоступности прямого API используй обычные карточки
CRM: поиск → нужная строка → «Настройки» → «Ограничения». Сверяй ID в заголовке.
В сводке ограничения «Изменить / Применяется к выбранным» раскрывают выбранные
категории/блюда; «Настроить» сохраняй как подпись UI, не как доказанное API-null.
Открывшиеся по умолчанию пустые поля редактора не означают сохранённое ограничение.
Состояния switches, выбранные options и лимиты считывай из DOM/AX, не только текста.
У двух одинаковых кодов выбирай конкретную строку и проверяй UUID карточки.
Проверь, что сохранён именно JSON ожидаемой схемы, а не страница входа/challenge под расширением .json.
Этот путь проверен для promotions/promocodes; не обобщай доступность на все settings или роли.
Save As целого ответа используй лишь для заранее проверенной безопасной схемы: ответы loyalty/settings
с credential-полями нельзя так сохранять целиком; для них нужен whitelist или безопасный экран UI.
Если GET недоступен, читай карточки UI через CUA и фиксируй ограничения полноты.
Если браузерный адаптер недоступен, допустим native CUA для той же разрешённой сессии.
Ошибка конкретной Chrome extension — ограничение окружения, не вечный запрет браузеров.
Не извлекай cookies/токены из браузера и не обходи запреты доступа ради API-чтения.
В read-only проверке не сохраняй изменения форм CRM и не нажимай включить/выключить,
тестовый push или отправить. Локальное Save As прочитанного безопасного JSON — отдельное
действие сохранения файла, не изменение настроек CRM.

### Пагинация и полнота списков

GET-пути далее добавляются к подтверждённому Starter base, без повторного `/fmteplo`:

- `/api/v1/frontend/promotions/discounts`, `/{starter_id}` — список и карточка скидки.
- `/api/v1/frontend/promotions/promocodes`, `/{starter_id}` — промокоды.
- `/api/v1/frontend/promotions/increases`, `/{starter_id}` — надбавки.
- `/api/v1/frontend/promotions/stamp-cards`, `/{starter_id}` — штамповые механики.
- `/api/v1/frontend/promotions/history` — история настройки, не применения в чеках.

Списки используют `offset`, `limit` (наблюдённый default **50**), поиск, сортировку,
`shop_id` и массив `status`: `active`, `not_active`, `archived`.
Имя параметра в OpenAPI — `status`; не подменяй его буквальным `status[]` без контракта.
У промокодов есть `is_massive`; отдельно учитывай массовые и ограниченные серии.
Для полного реестра явно охвати все статусы и нужные магазины, очисти случайный поиск.
Обходи страницы до `total`, сверяя уникальные `id`; короткая первая страница не доказательство полноты.
Фиксируй параметры и `total` каждой страницы. При меняющемся total/дублях повтори сверку,
а при недоступном разделе запиши «не проверено», не ноль и не «акций нет».
`shop_id` в этом CRM-контракте — integer/null; UUID магазина публичной витрины сюда не подходит.
`starter_id` — UUID объекта Starter; это не автоматически GUID скидки/блюда iiko.

### Карточки: статус, даты и исключения

Сохраняй `id`, `name`, `status`, `type`, `value`, `settings`, доступные лимиты и linked IDs.
`status=active` означает включённую настройку: отдельно проверь срок и остальные условия.
Помечай как минимум: включена и проходит проверенные условия; выключена; архивная;
срок истёк/ещё не наступил; применимость не установлена. Unknown не заменять active.
`dateTimeRestriction` содержит `date[{from,to}]`, `time[{fromHour,fromMinutes,toHour,toMinutes,isDayOff}]`,
`daysOfWeek` и `choice`. `toChosen`/`exceptChosen` — включение/исключение выбранного;
для временных исключений нельзя свести правило к одной первой/последней дате.
Сохрани исходные интервалы, режим и UI-подпись; часовой пояс, нумерацию дней недели,
границы интервалов и поведение через полночь подтверждай, не выводи из названий полей.
Такие же `choice`/`entityIds` используются у блюд, категорий, магазинов и способов получения.
Пустой список в режиме «только выбранные» нельзя без подтверждения переводить в «все» или «никто».

Проверь `placeActivation` (app/web/all), `fieldToApply` (price/totalPrice/deliveryPrice),
`minOrderPriceSettings` по common/deliveryType и all/chosen, первую покупку,
`birthdayOptions`, индивидуальные/общие лимиты, повторяемость и реферальную связь.
`sortIndex`, `lastApplicable` и текст о прекращении следующих акций сохраняй отдельно;
их поведение и исключения для баллов сверяй по UI/движку, не переноси по сходству имён.
`doubleMeal` — тип награды блюдом; это не доказательство удвоения бонусов.
Счётчик `usages` без подписанного периода не превращай в месячную частоту или эффективность.


### Названия блюд, категорий и массовые кампании

Дополнительные GET-контракты найдены в OpenAPI 07.10.2026; live API-чтение этих
маршрутов в снимок не входит:

- `/api/v1/frontend/catalog/combo/slot-targets?limit=500&offset=0&includeInactive=true`:
  `items`, `totalCount`, `type` meal/category, `id`, `name`, `status`, `sku`.
  Лимит 1–500, default 50; также `search`, `offset`, `shop_id` integer/null.
  Это selector комбо, поэтому не объявляй его универсально полным каталогом:
  сверяй покрытие каждого GUID из ограничений. Public `analyticId` не заменяет Starter mealId.
- `/api/v1/frontend/promocodes/discounts/bulk?limit=100&offset=0`:
  массив `id`, `title`, `status`; `/api/v1/frontend/promocode/total` — агрегаты
  `all`, `active`, `used`, `disabled`.
- Новый список `/api/v1/frontend/promotions/promocodes?is_massive=true` описывает
  правила массовых кампаний. Старый `/api/v1/frontend/promocodes` содержит экземпляры
  кодов и не нужен для обычного реестра условий; не смешивай его DTO с новым.

В этом снимке UI-фильтр «Массовый», статусы активная/неактивная, пустой поиск
показал «Ничего не нашлось». Архивные массовые записи отдельно не проверены.
Контракт stamp-cards существует, но вкладка штампов не была доступна в просмотренном
разделе CRM и сам список не прочитан. Не записывай нулевое число stamp-cards без источника.

### Остальная лояльность Starter

- GET `/api/v1/frontend/loyalty_program`: provider (`clientType`), `selfRefill`, `selfWithdraw`,
  уровни, лимит списания, совместимость с промокодом/скидками, база начисления и каналы.
- GET `/api/v1/frontend/loyalty_program/bonus-restriction`: ограничения начисления/списания.
- GET `/api/v1/frontend/loyalty_program/bonus-program-accounts`, `/total`, `/{account_id}`:
  отдельные счета, магазины, статусы и ограничения; не ограничивайся одним общим экраном.
- GET `/api/v1/frontend/referral/program` и `/api/v1/frontend/referral/settings`: обе стороны,
  linked promotion, минимальная сумма, момент награды; не сохраняй личный реферальный код.
- GET `/api/v1/frontend/welcome_bonuses` и `/api/v1/frontend/bonus_burning`: отдельные
  welcome-триггеры, enabled-флаги и сроки; проверь, к какому provider применим экран.
- GET `/api/v1/frontend/server-settings/push`: retention, birthday, feedback и balance reminders.
  Единицу задержки читай в текущем UI: разные поля могут означать минуты и дни.
  Порог существующего баланса не равен новой выдаче баллов; шаблон сообщения не доказывает отправку.

Provider iikoCloud и отключённые selfRefill/selfWithdraw требуют проверки внешнего движка.
Starter всё ещё может ограничивать канал, видимость и совместимость. Не объявляй его настройки
ни единственным авторитетом, ни полностью неработающими без проверки конкретного контура.
Текст правил/виджета/активации — обещание клиенту; расхождение с настройкой сохраняй явно.

## Где искать факт начисления и отправки

В публичном OpenAPI 07.10.2026 найдены следующие GET-контракты; live-чтение этих
журналов в данном аудите не выполнялось. Это маршруты дальнейшей проверки,
**не подтверждённый журнал успешного исполнения retention**:

- `/api/v1/frontend/customers/{customer_id}/main-bonus-program-transactions`
  (`offset`, `limit`, `shop_id`) и `/customers/{customer_id}/bonus-program-transactions`
  (`restaurant_account_id`, `shop_id`, тот же frontend base). Ответ `transactions`:
  `id`, `createdAt`, `type`, `amount`, `balanceAfter`, `comment`, `bonusProgramAccount`;
  `total.balance`, `selectedBonusProgramAccount`, `totalCount`.
  Схема не гарантирует отдельный rule ID или происхождение баллов: не приписывать
  любую операцию +100 возврату клиента только по сумме.
- `/api/v1/frontend/distributions` и `/distribution/{distribution_id}`;
  `/distribution/{distribution_id}/counts` (тот же frontend base) содержат состояния
  и счётчики `all`, `done`, `error`, `visitsCount`, `ordersCount`.
  В настройке рассылки есть `attributionWindowHours`. Заказы в окне атрибуции не равны
  дополнительным заказам. Не обещать покрытие автоматических trigger-push этим API,
  пока это не подтверждено конкретной записью/источником.
- `/api/v1/frontend/distribution/{distribution_id}/{message_type}` возвращает
  `messages[].customer`: ответ персональный, для общего реестра не нужен.

Для отдельной задачи диагностики используй минимально необходимые записи в
авторизованном контуре и сохраняй обезличенную проекцию. Для экономического анализа
предпочитай агрегаты и когорты. Не добавляй клиентские ID, контакты, личные балансы
или комментарии с персональными данными в переносимый skill.

## iikoCloud: действующая конфигурация движка

Официальная [OpenAPI iikoCloud](https://api-ru.iiko.services/api-docs/docs) задаёт текущий контракт.
Найди `apps/api/app/services/iiko_cloud_client.py`: `iiko_cloud_call` — общий транспорт,
не гарантия read-only любого POST. Используй только подтверждённые справочные операции:

- POST `/api/1/loyalty/iiko/program`, тело `{organizationId}` — программы/кампании/правила.
- POST `/api/1/payment_types`, `{organizationIds:[...]}` — способы оплаты и связи с кампаниями.
- POST `/api/1/discounts`, `{organizationIds:[...]}` — типы скидок/надбавок и категорийные ставки.
- POST `/api/1/loyalty/iiko/customer_category`, `{organizationId}` — справочник категорий.
- POST `/api/1/loyalty/iiko/coupons/series`, `{organizationId}` — лишь серии с неактивированными
  купонами по описанию API; это не полная история всех серий и не чтение личных купонов.

Сохраняй status, тело/ошибку и время отдельно. HTTP200 без сохранённого содержимого
не подтверждает названия справочника; timeout/400 не означает пустой реестр.
Не вызывай create/update/topup/chargeoff, не создавай тестовый заказ для проверки механики.

Сохрани все Programs, campaign IDs, даты, active, wallet, appliedOrganizations и все четыре
массива bindings: order, periodic, overdraft, guestRegistration. Порядок обязателен.
У action/condition сохрани `typeName`, `settings` как исходную JSON-строку и её разбор,
не теряй неизвестные поля/enum. `stopFurtherExecution` по официальной схеме останавливает
дальнейшую обработку после успешного binding; перестановка меняет смысл.
Неизвестные числовые enum, пустой actions/conditions и appliedOrganizations не расшифровывай догадкой.
Программа без действий не доказывает работающую награду, даже если isActive=true.
У скидок сначала читай `mode`: FlexibleSum с percent не является постоянной процентной ставкой.
При `isCategorisedDiscount=true` изучи `productCategoryDiscounts`, не только общий percent.
`paymentTypes.combinable` описывает совместимость способов оплаты, не всех скидок и промокодов.

## iikoServer OLAP: факт применения

Для проверенного доступа и популяции используй доступный `teplo-rolls-analysis`, его
`references/access-and-sources.md`, `references/sales-and-sets.md` и source checker.
В repo: `apps/api/app/services/iiko_sync.py::_load_source_credential_env` читает действующий
SourceCredential; при необходимости БД — `SET TRANSACTION READ ONLY`, timeout, затем rollback.
`apps/api/app/services/pnl/iiko_sync.py::_fetch_raw` — GET через существующий IikoClient;
`apps/api/app/services/iiko_revenue.py::_fetch_daily_revenue_sync` — образец read POST OLAP.
`integrations/iiko/scripts/export_orders_delivery.py` помогает найти metadata/клиент;
весь export CLI не запускать как безвредный reader: он пишет raw/processed в checkout.

Сначала GET `/v2/reports/olap/columns?reportType=SALES` и `/v2/reports/olap/presets`.
Проверь grouping/aggregation/filteringAllowed, актуальные фильтры `REVENUE_PRESET_ID` и точку.
Затем POST `/v2/reports/olap` для отчёта: учётный день, Department, `OrderDiscount.Type`,
`OrderDiscount.Type.IDs`, `ItemSaleEventDiscountType`, `OrderType`; агрегаты выбирай из metadata.
`ItemSaleEventDiscountType` включает надбавки; список только OrderDiscount.Type может их потерять.
Соответствие одиночного имени и ID подтверждай одиночной записью; не zip списки через запятую
без доказательства общего порядка. Имена iikoCard и Скидка iikoCard могут быть разными GUID.
Поле даты/полуоткрытые границы и удалённые/возвраты согласуй с canonical preset;
старый SessionID.OperDay не подставляй в custom OLAP при Unknown field.
Месячные chunks сверяй с отдельным canonical-контролем; пропуск chunk — missing, не ноль.
Число строк/дней/агрегатных чеков не одно и то же: один заказ входит в несколько скидочных событий.
Без подтверждённого ключа и дедупликации не суммируй UniqOrderId по событиям как число применений.
OLAP-тип и канал не доказывают клиентскую акцию: нужен mapping Starter ID → iiko rule/type ID.
Акционные сеты/фиксированные цены/бесплатные компоненты могут не иметь отдельного типа скидки.

## Безопасное сохранение и обновление

В whitelist: бизнес-ID, названия/правила, статусы, даты, ограничения, суммы настройки,
шаблоны без персональной подстановки, категории/товары, время чтения, endpoint, фильтры и SHA-256.
Не сохраняй cookies, access_token, Authorization, пароли, env, clientSecret или credential clientId.
Не выгружай целиком Starter settings: LoyaltyProgramData/SettingsFrontend содержат секреты.
В истории настроек оставляй изменения правил и время; имена/контакты администраторов для реестра не нужны.
Не собирай клиентов, телефон/email, гостевые карты, личные промокоды, адреса получателей,
балансы конкретных людей, order IDs или персональные примеры для обычного реестра акций.
Визуальное доказательство кадрируй/выбирай так, чтобы секретные и персональные блоки не попадали.

Snapshot хранить отдельно от evergreen-правил: as_of, точка/канал, источник по каждому полю,
статус полноты, unresolved, время чтения, схема/версия, safe raw/hash и отдельно интерпретация.
Для переносимости используй относительные имена файлов и repo-relative пути, без /tmp-зависимостей.
При обновлении **полного реестра** повторно прочесть все списки/страницы и нужные
карточки, затем внешний движок, затем
при необходимости факт OLAP. Сравнить по устойчивым ID, показать новые/исчезнувшие/изменённые
условия и источники; существование в старом списке не продлевает срок действия.
Финансовые формулы и оценка эффекта находятся в отдельной справке: этот маршрут их не заменяет.

Для узкого вопроса обновляй только относящиеся к нему объекты и зависимости;
полный обход остальных акций для такого ответа не требуется.
