# Правила работы над проектом

## Изучение кода — всегда через Graphify

В корне проекта собран граф знаний: `graphify-out/graph.json`. **Любое изучение проекта начинай с него, а не с прямого чтения файлов.**

Это правило действует для задач вида: «как устроено X», «что вызывает Y», «где считается Z»,
«разберись в модуле…», «проследи поток данных», «какие файлы связаны с…» — то есть для любого
вопроса про архитектуру, связи файлов или содержание проекта.

### Порядок действий

1. **Сначала спроси граф.** Запусти запрос из корня проекта:
   ```
   graphify query "<вопрос своими словами>"
   ```
   Для трассировки конкретного пути — `graphify query "<вопрос>" --dfs`;
   кратчайший путь между сущностями — `graphify path "A" "B"`;
   объяснение узла — `graphify explain "ИмяУзла"`.
   Полезны также `graphify-out/GRAPH_REPORT.md` и `graphify-out/manifest.json`.
2. **Потом уточняй файлами.** Граф даёт карту и точки входа — конкретику (текущий код,
   свежие строки) добавляй прицельным `Read`/`Grep` по файлам, которые указал граф.

### Когда можно идти сразу в файлы (без графа)

- Правка/чтение одного уже известного файла — тривиальные точечные задачи.
- Вопрос про то, чего в графе заведомо нет (новые файлы, конфиги, свежие миграции).

### Важно про актуальность графа

Граф — снимок на момент сборки, он может отставать от текущего кода. Если запрос к графу
противоречит тому, что в файлах, **истина — в файлах**. Если видно, что граф устарел или не
покрывает нужную область, — скажи об этом и дострой картину чтением файлов.

Охват: `.graphify_root` — **корень проекта**, а не `apps/`. В индексе весь репозиторий (~1200 файлов):
`apps/`, `docs/`, `app-spec/`, `business-docs/`, `integrations/`, `research/`, `deploy/`. Тесты
`apps/api/tests` тоже в графе, и это не шум: докстринги тестов дают ~38 % всех «почему так»
(`rationale`) — на многие вопросы отвечают именно они. Дата сборки видна по `graphify-out/GRAPH_REPORT.md`.

Две ловушки при чтении отчёта:

- **`God Nodes` начинай со 2-го пункта.** Первый — `async_session_factory()` из
  `apps/api/tests/conftest.py` (845 рёбер): рёбра настоящие, но это pytest-фикстура и
  направленный сток, никакие модули он не связывает. Подпись «cross-community bridge» и
  betweenness у него — артефакт ненаправленной проекции. Из тех же тестовых лесов
  `make_counterparty()` и `make_invoice()`.
- **`HTTPException` (236 рёбер) — пустой узел.** Символ из fastapi, в репозитории его определения
  нет; граф произвольно заякорил его на `routes/counterparties.py:70` и стянул туда 222 ребра
  из чужих файлов. Так ведёт себя любой уникальный в индексе label, который вызывают по имени.
  (Остальные три узла `HTTPException` — по 9–16 рёбер, они честные и не мешают.)

Цифры — по снимку от 26.07.2026; после пересборки они поплывут, суть ловушек — нет.

### Обновление графа — обязательный шаг после деплоя

Граф — общий инструмент всех агентов. Если после выкатки его не обновить, следующий агент
получит карту прошлой недели и будет уверенно исследовать код, которого уже нет.

**Когда обновлять:** после того как работа влита в `main`, ушла на `origin` и выкачена на прод —
то есть новый модуль, фича, правка или пачка миграций уже в чистовике. Не в середине работы над
ветками: снимок должен соответствовать `main`, а не чьей-то незакоммиченной правке.

**Как:**

1. Перейди в **главную папку** `Teplo-all-for-business` (она держится на `main`), не в свой worktree —
   иначе граф соберётся по чужой ветке. Сверь, что `main` свежий: `git pull --ff-only`.
2. Запусти инкрементальное обновление — переизвлекаются только новые и изменённые файлы:
   ```
   /graphify . --update
   ```
3. Если менялся только код (`.py`, `.ts`, `.tsx`), обновление бесплатное: AST-разбор идёт без LLM.
   Изменённые `.md`/`.yml` требуют семантической экстракции субагентами — это нормально, но
   исключай из неё мусор: `graphify-out/memory/`, `tmp/`, `outputs/`, `.obsidian/`, фотографии
   и макеты. Каждая картинка — отдельный vision-агент, а карте проекта они не дают ничего.
4. Проверь итог: диф («N new nodes, M new edges»), число узлов в `graph.json` и что удалённые
   файлы выпали из графа. И убедись, что гиперрёбра из прошлого снимка не потерялись —
   `build_merge` их не переносит, их нужно вернуть вручную.
5. **Перепроверь метки сообществ — совпадение их номеров ничего не гарантирует.** Louvain при
   каждом прогоне кластеризует заново: номера сообществ остаются прежними, а состав переезжает.
   30.07 после правки двух файлов `.py` все 756 номеров нашлись в старом
   `.graphify_labels.json` («новых id: 0»), но **551 метка из 756 перестала описывать своё
   сообщество** — кластер из узлов `web/src` был подписан `api/app/schemas`. Пропустишь шаг
   именования, сославшись на готовые метки, — `GRAPH_REPORT.md` и `graph.html` тихо разойдутся с
   графом. Сверять надо не номера, а состав: собрать по узлам сообщества топ-2 директории (снять
   префикс `apps/`, взять первые 3 компонента пути) и сравнить с текущей меткой. Существующие
   метки сделаны ровно в этом стиле `dir + dir`, поэтому перегенерация воспроизводится программно
   и не стоит ни одного токена.
6. Сломанные ожидания фиксируй в отчёте владельцу: если граф после обновления противоречит тому,
   что ты видел в файлах, — истина в файлах, а расхождение стоит назвать.
7. **Закоммить обновлённый граф** (через свою ветку и `--ff-only`, как любую задачу). Граф лежит
   в git специально: так он доступен из любого worktree, а пересборка с нуля стоит больше миллиона
   токенов. Бояться веса не нужно — git жмёт `graph.json` с 27 МБ на диске до ~1,7 МБ в паке.
   - **в git:** `graph.json`, `GRAPH_REPORT.md`, `graph.html`, `manifest.json`,
     `.graphify_labels.json`, `cost.json` и `cache/semantic/` — последний экономит следующему
     агенту живые LLM-токены при `--update`;
   - **не в git** (уже в `.gitignore`): `cache/ast/` — восстанавливается AST-разбором бесплатно
     за секунды; `memory/` — сохранённые ответы `graphify query`; `.graphify_python` и
     `.graphify_root` — абсолютные пути конкретной машины.

   Добавляй пути по одному, `git add -A` в общей папке захватит чужое.

**Гонка с чужим мержем — главная ловушка обновления.** Манифест (`graphify-out/manifest.json`)
пишется в конце прогона по состоянию файлов **на диске**, а не по тому, что реально попало в граф.
Если другой агент вольёт свою ветку в `main` пока ты обновляешь граф, его файлы окажутся
помечены обработанными, ни разу не попав в индекс: следующий `--update` их не увидит, и граф
будет тихо отставать. Так уже случилось 26.07 с коммитом `fcc78f2`.

Поэтому:

1. Зафиксируй `git rev-parse HEAD` **до** прогона и сверь **после**. Сдвинулся — доиндексируй.
2. Доиндексировать точечно: взять список файлов чужого коммита
   (`git show --name-only --format='' <коммит>`) и переизвлечь их напрямую через
   `graphify.extract.extract(files)`, не полагаясь на `detect_incremental` — манифест уже врёт.
3. Проверить результат по существу, а не по числам: найди в `graph.json` символ, который этот
   коммит добавил, и символ, который он удалил.
4. Убыль узлов — не всегда ошибка. `to_json` отказывается писать граф меньше существующего
   (защита от потерянных чанков). Прежде чем передавать `force=True`, сверь список исчезнувших
   узлов поштучно: у легитимной убыли он сходится с удалёнными символами коммита, а сдвиг номеров
   строк даёт пары «исчез L311 / добавился L305» — это один и тот же узел, не потеря.

   Отказ записи срабатывает и на честной правке кода, где ничего не удалялось. Переизвлечение
   файла снимает с него якоря импортируемых имён: 30.07 после правки двух тестовых файлов из
   графа ушли метки `Wallet`, `Employee`, `PayrollLine`, `PayrollPeriod`, заякоренные на них, —
   тот же артефакт, что и с `HTTPException` выше. Каждая осталась в графе десятками узлов,
   определения в `app/models/*.py` целы. Критерий, по которому `force=True` безопасен: вся убыль
   **и узлов, и рёбер** локализована в переизвлечённых файлах (посчитай рёбра, касающиеся именно
   этих файлов, до и после — их убыль должна сойтись с убылью всего графа), ни один файл из графа
   не выпал, гиперрёбра на месте.

   Сдвиг номеров строк — заодно и лучшая проверка того, что файл **реально переизвлечён**, а не
   помечен обработанным вхолостую: символы после вставки съезжают ровно на её объём, символы до
   неё стоят на месте.

**Два прогона graphify в одной папке — вторая ловушка, и она съедает работу молча.** Гонка выше
про чужой *мерж*; эта — про чужой *прогон*. `graphify-out/` один на весь репозиторий, а Step 9
любого прогона заканчивается `rm -f graphify-out/.graphify_*`. Соседний агент, финиширующий
посреди твоей работы, уносит твои промежуточные файлы — `.graphify_ast.json`,
`.graphify_chunk_*.json`, `.graphify_old.json`, — и узнаешь ты об этом только на слиянии, по
`FileNotFoundError` на файле, который сам же записал десять минут назад. Так вышло 31.07: пока
шла доиндексация, сосед закончил свой `--update` и закоммитил граф (`452b2ef`); AST на 150 узлов
и семантика на 86 (≈148k токенов субагента) отправились в никуда.

Поэтому **перед стартом** — те же две проверки, что и перед прод-деплоем:

```
ls -l graphify-out/graph.json          # свежее твоего последнего коммита графа = сосед уже прогнал
git log --oneline -1 -- graphify-out/  # кто и когда трогал граф последним
pgrep -fa graphify                     # чужой прогон прямо сейчас
```

Если граф уже свежий — **не запускай обновление, проверь покрытие**: найди в `graph.json`
символы своих последних коммитов (`sum(1 for n in nodes if ...)` по `label`/`source_file`).
Нашлись — работа сделана, твой прогон только сожжёт токены.

Если прогон уже начат и обнаружилось, что сосед закончил первым, — **свою экстракцию поверх не
вливай**. Те же файлы уже извлечены чужим проходом, а id узлов у семантики генерируются заново:
`build_merge` не сведёт их с чужими, и в графе появится вторая копия тех же понятий под другими
именами. Правильно — выбросить промежуточные файлы, откатить перезаписанный
`graphify-out/cache/semantic/` (`git checkout -- graphify-out/cache/semantic/`) и проверить чужой
результат по существу.

И отдельно: `detect_incremental` в такой ситуации врёт вдвойне. 31.07 он показал **1**
изменённый файл там, где `git diff <коммит сборки графа>..HEAD` давал **15** — чужой прогон уже
переписал манифест. Не верь его числу: сверяй список с git, а вывод «нечего обновлять» на
заведомо изменённом коде читай как «манифест устарел», а не как «граф актуален».

Файлы с `secret`/`credential`/`password`/`private_key` в имени graphify не индексирует вовсе, а
`.claude/worktrees/` пропускает — не ищи их в графе, читай напрямую.

## Работа с ветками и worktree — как не плодить хаос

Над проектом работает несколько агентов параллельно. Чтобы они не сталкивались и не оставляли
за собой мусор из папок, веток и портов — соблюдай правила ниже.

### Золотое правило

**Никогда не работай в `main` напрямую.** `main` — это чистовик, ровно то, что крутится на
проде. Главная папка `Teplo-all-for-business` держится на `main` как эталон. Любая задача —
в отдельной ветке и отдельном worktree.

### Жизненный цикл одной задачи

1. **Ветка.** От свежего `origin/main` создай ветку с понятным именем-«фамилией»:
   `feat/<фича>` (новое), `fix/<баг>` (правка), `deploy/<что>` (готовим к выкатке).
2. **Worktree.** Заведи под неё отдельную папку через `scripts/agent-worktree.sh add <имя> <задача>`
   (создаёт `../teplo-<имя>-wt` со своей веткой). Файлы физически изолированы — чужие
   незакоммиченные правки снести нельзя.
3. **Коммить в свою ветку**, не в `main`. Не делай `git add -A` в общей папке — захватишь чужое;
   перед `git add` общего файла проверяй `git diff <файл>` или добавляй через `git add -p`.
4. **Превью — на своём фиксированном порту** (`--strictPort`, чтобы Vite не прыгал). Порты по
   формуле слота k: web `5173+10k` / api `8000+10k` / pg `5432+10k` (слот 0 — основной стек).
   Сообщи владельцу URL — он посмотрит результат вживую.

   **И тестовая база — тоже по слоту:** `TEPLO_TEST_DATABASE_URL` указывает на
   `teplo_test_<слот>`, а не на общую `teplo_test`. В compose-файлах агентов так и сделано
   (`teplo_test_b`, `teplo_test_c`), но при запуске pytest С ХОСТА переменную набирают руками —
   и вот там оба агента 31.07.2026 набрали общую. Worktree разводит ФАЙЛЫ, а не базу, и это
   единственное место, где изоляция не работает сама собой: контейнер Postgres у каждого свой,
   но порт наружу опубликован обычно у одного, а имя `teplo_test` у всех одинаковое — и два
   pytest-процесса сходятся в одну базу. Схема там пересоздаётся в начале каждой сессии,
   поэтому второй прогон сносит таблицы первому.

   Признак, что это уже случилось: прогон падает ЦЕЛИКОМ, сотнями ошибок в setup
   (`type ... does not exist`, `duplicate key ... alembic_version`). Свои правки столько не
   ломают — сначала `pgrep -fa pytest`, и только потом ищи баг у себя. Подробности и команды —
   в `apps/api/TESTING.md`.

   **Разрушительные команды на базе — только после проверки, чья она.** `DROP SCHEMA public
   CASCADE` на «повисшей» тестовой базе выглядит безобидно ровно до момента, когда в ней сидит
   чужая сессия: 31.07.2026 так был убит идущий прогон соседа, и вернуть снесённую схему
   под его сессией было нечем. Перед дропом:
   `select pid, state from pg_stat_activity where datname='<база>'`.
5. **Деплой** (только после одобрения): влей ветку в `main` через `--ff-only` → `git push origin main`
   → на проде `git pull --ff-only` → бэкап БД → `build` → **миграция новым образом**
   (`run --rm api alembic upgrade head`) → `up -d`. Порядок именно такой: пересоздать контейнеры
   раньше миграции — значит пустить новый код на старую схему (инцидент 24.07, api 9 минут отдавал
   500). А `exec api` вместо `run --rm` уходит в СТАРЫЙ контейнер, где новых файлов миграций нет
   вовсе. Подробный ранбук с проверками — `deploy/README.md`. Перед сборкой сверь
   `git show <коммит> --stat` и чужие миграции.
6. **Уборка — обязательна.** Сразу после деплоя удали свою ветку и worktree:
   `git worktree remove <папка>` + `git branch -d <ветка>`. То, что влито в `main` и уехало на
   `origin`, уже сохранено — локальная копия не нужна и только копит мусор.
7. **Обнови граф знаний.** Из главной папки на свежем `main`: `/graphify . --update`. Это часть
   деплоя, а не необязательный бонус — следующий агент начнёт работу с графа, и он должен
   описывать то, что уже на проде. Подробности и ловушки — в разделе
   «Обновление графа — обязательный шаг после деплоя».

## Превью-стенды — единая учётка и обязательные переменные

Правила ниже действуют для **любого** превью: и на чистой локальной базе, и на копии прод-БД.
Владелец заходит в превью всегда одинаково, гадать с логинами не должен.

### Единственная связка для входа

```
admin1@teplo.local / admin-password-for-smoke
```

Другие учётки для превью **не заводим** и владельцу не предлагаем. Эта связка уже объявлена
во всех `apps/docker-compose*.yml` (`TEPLO_ADMIN_EMAIL` / `TEPLO_ADMIN_PASSWORD`), но
приложение эти переменные не читает — пользователя нужно завести скриптом:

```
docker exec -w /app/apps/api -e PYTHONPATH=/app/apps/api <api-контейнер> \
  python -m app.scripts.seed_preview_admin
```

Скрипт идемпотентен: создаёт пользователя с ролью `admin`, а существующему чинит пароль и
снимает блокировку. Запускай его **после** `alembic upgrade head` — и обязательно, если база
залита из дампа прода (там этой учётки нет). Пароль публичный, поэтому скрипт сам
отказывается работать при `ENVIRONMENT` из `PRODUCTION_ENVIRONMENTS`; на прод его не носим,
боевые учётки не трогаем.

### Переменные окружения превью

`.env` стенда — это **не** копия боевого `.env`. Кладём только выключатели фона и заглушки:

- `ENVIRONMENT=local`, `SCHEDULER_ENABLED=false`, `EMPLOYEE_SYNC_ENABLED=false`,
  `COUNTERPARTY_INVOICE_SYNC_ENABLED=false`, `SBIS_SYNC_ENABLED=false`,
  `MAIL_POLL_ENABLED=false`, `TEPLO_BANK_CLIENT_MODE=mock`;
- `IIKO_SERVER_BASE_URL=http://iiko-disabled.invalid` — **обязательно**. Без переменной
  `IikoClient.__init__` бросает `SystemExit`, а он как `BaseException` пробивает обработчики
  FastAPI и убивает процесс uvicorn: один заход на «График» (`/api/v1/schedule/{id}/plan-fact`)
  кладёт весь стенд, а контейнер при этом остаётся в статусе `Up`. С заглушкой тот же запрос
  честно отдаёт 500.

Боевые ключи (Сбер, Т-Банк, Telegram, почта, iiko) на превью не переносим — стенд на копии
прод-данных не должен уметь писать во внешние системы.

### Гигиена веток и папок

- Ветку удаляем **после** мержа. Критерий безопасного сноса: ветка влита в `origin/main`
  (`git branch --merged origin/main`) **и** рабочая копия чистая (`git status --porcelain` пусто).
- `git branch -d` сам откажется удалять невлитую ветку — это защита, не борись с ней через `-D`
  без явной проверки, что работа уже в проде или забэкаплена на `origin`.
- Если ветка есть на `origin` (`git branch -r`), локальную копию удалять безопасно — работа на «складе».
- Изолированный стек второго/третьего агента — через `apps/docker-compose.agent-b.yml`
  (свой проект/порты/БД), а не копией контейнеров в общий стек.
