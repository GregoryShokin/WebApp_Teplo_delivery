# Источники данных и доступы

## Цель

Собрать данные автоматически из бэк-офиса, Google Drive и связанных систем, затем привести их к единой управленческой картине: продажи, себестоимость, зарплаты, доставка, маркетинг, ДДС, ОПиУ / P&L и баланс.

## Роли банков (подтверждено владельцем 2026-05-19)

**Денежный контур работает как цепочка `Sber → T-Bank → контрагенты` с небольшим прямым входом в T-Bank:**

1. **Sber — основная точка приёма выручки от коммерческой деятельности.** Сюда приходит большая часть денег от торгового эквайринга, интернет-эквайринга и других каналов приёма платежей. Sber используется как банк-аккумулятор выручки.
2. **Перевод Sber → T-Bank.** Деньги из Сбера регулярно переводятся на расчётный счёт в Т-Банке. По T-API такие поступления видны как `incomePeople` / внутренние переводы со счёта Сбербанка и **не являются отдельным каналом выручки**: это та же выручка, уже учтённая на стороне Sber.
3. **Прямой эквайринг в T-Bank — небольшая доля поступлений.** Часть выручки приходит непосредственно на расчётный счёт в Т-Банке через собственный эквайринг T-Bank. Это **не внутренний перевод из Сбера**, а реальная выручка, которую нужно учитывать отдельно. Доля небольшая, но не нулевая — её нужно идентифицировать по признакам операции (категория, банк-отправитель ≠ Sber, назначение платежа).
4. **T-Bank — точка распределения по контрагентам.** С расчётного счёта в Т-Банке производятся 98% исходящих операций: поставщики, выплаты сотрудникам, налоги, бизнес-карта, выводы.

Из этой цепочки следуют правила работы с банковскими данными:

- **Sber API — основной источник по выручке** (главный канал эквайринга и приёма платежей). Входящее движение в Sber не считается выручкой автоматически: нужно отделить эквайринг от возвратов, кредитов, корректировок и прочих поступлений по признакам операции.
- **T-Bank API — первичный источник по расходам и справочнику поставщиков**. Входящие в T-Bank — это **смесь двух потоков**: основная часть — внутренние переводы из Сбера (не учитывать как выручку, чтобы не задвоить); меньшая часть — прямой эквайринг T-Bank (учитывать как выручку отдельной строкой ДДС, не относя к Sber). Разделение делается по реестру правил.
- **Сверка выручки iiko vs банк** строится как `iiko = Sber-эквайринг + T-Bank-эквайринг − возвраты`, а не только vs Sber. Внутренние переводы Sber→T-Bank в выручку не входят: это движение уже учтённой выручки между своими счетами.
- **Общее правило классификации:** сначала фиксируем банк и направление операции, потом классифицируем экономический смысл по реестру признаков (`эквайринг Sber`, `эквайринг T-Bank`, `перевод средств по договору`, `внутренний перевод Sber→T-Bank`, кредит, возврат и т.д.). Шаблон правил: `research/processed/bank_operation_rules_template.csv`; реальный заполненный реестр с фрагментами назначений платежей должен жить в `research/private/`, потому что описания могут содержать персональные данные.
- Карты эндпоинтов: [12-sber-api-endpoints.md](/app-spec/integrations/sber/api-endpoints.md), [14-tbank-api-endpoints.md](/app-spec/integrations/tbank/api-endpoints.md). Подробное обоснование разделения и маппинг статей ОПиУ на T-API — в [14-tbank-api-endpoints.md](/app-spec/integrations/tbank/api-endpoints.md), раздел «Связь со строками ОПиУ и ДДС».

## 2. Что нужно от бэк-офиса API

| Вопрос | Ответ |
| --- | --- |
| Базовый URL API | Берется из `IIKO_SERVER_BASE_URL` в `ENV`; не писать значение в документы |
| Тип авторизации | `POST /resto/api/auth`, затем query-параметр `key` |
| Где лежит документация API | Локально: [08-iiko-server-api-endpoints.md](/app-spec/integrations/iiko/server-api-endpoints.md); технический источник: `GET /resto/api/application.wadl` |
| Есть ли ограничения по периодам выгрузки | Рабочее правило проекта: не больше 1 месяца за запрос |
| Есть ли ограничения по частоте запросов | Запросы выполнять последовательно; не параллелить iiko |
| Часовой пояс данных | В OLAP дата возвращалась с `MSK`; сверять при выгрузках |
| Валюта | Рубли |
| Как идентифицируются точки / кухни | Через `Department` / `/corporation/departments`; активная точка после января 2024 — Черникова, Гагарина историческая |
| Как идентифицируются каналы заказов | `OriginName`, `OrderType`, `Delivery.ServiceType`, `PayTypes` |
| Можно ли получить детализацию до заказа | Частично через OLAP-группировки по заказу/доставке; для управленческих документов использовать агрегаты |
| Можно ли получить детализацию до блюда в заказе | Да, через OLAP `DishName`, `DishCategory`, `DishGroup`, `DishAmountInt`, `DishDiscountSumInt`, `ProductCostBase.*` |

- `Таргетированная реклама`;

- `Контекстная реклама`;

Техническая проверка 2026-05-19 по официальной справке Saby/СБИС:

Минимальные параметры доступа, которые нужно получить:

| Что нужно | Для чего |
| --- | --- |
| `SBIS_APP_CLIENT_ID`, `SBIS_APP_SECRET`, `SBIS_SECRET_KEY` | сервисная авторизация внешнего приложения |

## 5.1. Mail.ru / Biz Panel для Синапса

### Контекстная реклама

Основной источник фактического расхода Яндекс Директ: Biz Panel Синапса.

Путь доступа:

1. найти свежее письмо от `hello@biz-panel.com`;
2. перейти по актуальной ссылке входа в Biz Panel;
3. открыть договор `CNTX-212566 от 25 Мар. 2021г.`;
4. для фактического расхода открыть вкладку `Яндекс`;
5. для счетов открыть вкладку `Счета`.

URL-логика отчета по Яндексу:

```text
https://biz-panel.com/node/59505/yandex?begin=YYYY-MM-DD&finish=YYYY-MM-DD
```

Проверенный пример за апрель 2026:

```text
https://biz-panel.com/node/59505/yandex?begin=2026-04-01&finish=2026-04-30
```

Для P&L-методологии важное поле отчета: `Бюджет` = фактический расход рекламных кампаний Яндекс Директ за выбранный период. Проверенный апрель 2026: `Бюджет` 23 984,77 руб., показы 36 276, клики 964, цена клика 24,88 руб.

Счета Синапса скачиваются из Biz Panel по договору `CNTX-212566`, вкладка `Счета`; URL скачивания:

```text
https://biz-panel.com/node/59505/download-invoice/{invoice_number}
```

Проверенный счет за апрель 2026: счет N `503711` от `16.03.2026`, всего 38 000 руб.; абонентское обслуживание 18 000 руб.; размещение рекламных материалов Яндекс.Директ 20 000 руб.; оплата в T-Bank `2026-03-26`, ООО «О. О», 38 000 руб.

Методологический вопрос владельцу: нужно выбрать, является ли строка P&L `Контекстная реклама` суммой `абонентское обслуживание + фактический Бюджет` или абонентское обслуживание выделяется отдельно, а строка `Контекстная реклама` берет только фактический `Бюджет` из Biz Panel. До ответа владельца это правило не финализировать автоматически.

## 5.2. Mail.ru для iiko, StarterApp и Леммы

Назначение: фиксировать расходы по документам контрагентов, у которых месяц оказания услуги может не совпадать с датой письма и датой оплаты. Для P&L / ОПиУ расход признается по периоду услуги внутри PDF-счета или УПД. Дата платежа используется для сверки оплаты и ДДС, дата письма - только как технический признак поиска документа.

Структурные файлы почтового контура:

- [mail_document_senders.csv](/research/processed/mail/mail_document_senders.csv) - реестр отправителей документов;
- [april_2026_counterparty_invoices.csv](/research/processed/mail/april_2026_counterparty_invoices.csv) - проверенный апрель 2026 по документам и оплатам;
- [april_2026_counterparty_invoices_report.md](/research/processed/mail/april_2026_counterparty_invoices_report.md) - человекочитаемая расшифровка апрельской сверки.

Общее правило обработки:

1. Найти документы по почтовому отправителю.
2. Извлечь из PDF-счета/УПД контрагента, ИНН, номер документа, сумму и период услуги.
3. Отнести расход в P&L к месяцу оказания услуги, а не к дате письма и не к дате оплаты.
4. Сверить оплату через T-Bank по номеру счета, сумме и юридическому контрагенту.
5. Если счет пришел несколько раз, дедуплицировать по номеру счета, периоду и сумме.
6. Если есть счет и УПД на один период и одну сумму, считать это одним расходом, а не двумя.

### iiko / АО «АЙКО»

Источник документов: письма от `donotreply@iiko.ru` с PDF-счетами во вложениях. Контрагент: АО «АЙКО», ИНН `1655166016`. Статья ОПиУ-кандидат: `Оплата систем автоматизации`.

Методика:

- месяц расхода брать из периода лицензии внутри PDF-счета, например `[01.04.2026-30.04.2026]`;
- дату письма не использовать как месяц расхода, потому что счета могут приходить заранее;
- оплату сверять с T-Bank по номеру счета, сумме и контрагенту АО «АЙКО».

## 6. Правила безопасности

1. Реальные токены, логины и пароли не пишем в Markdown-документы.
2. Локально храним секреты только в `.env`; пример структуры лежит в `.env.example`.
3. Сырые выгрузки с персональными и финансовыми данными кладем только в `research/raw/` или `research/private/`, эти папки исключены из git.
4. В рабочие документы переносим только агрегированные выводы, метрики и ссылки на источники.
5. Любое изменение данных в Google Drive делаем отдельно и явно, после чтения и понимания структуры файла.
6. Любое изменение данных в iiko (`POST`, `PUT`, `DELETE`, а также `GET` с side effect в названии path) делаем только по отдельному явному запросу владельца.

## 7. Первый сценарий работы

1. Получить ссылку на папку Google Drive с управленческой документацией или точные названия файлов.
2. Найти ДДС, ОПиУ / P&L и баланс.
3. Прочитать структуру таблиц: листы, периоды, статьи, формулы.
4. Определить, что актуально, а что давно не ведется.
5. Получить доступ к бэк-офис API и документации API.
6. Снять первый факт: продажи, заказы, зарплаты, курьерские выплаты за последние 3 месяца.
7. Сверить API-факт с управленческими таблицами.
8. Сформировать первую версию управленческой панели собственника.
