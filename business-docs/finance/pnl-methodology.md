# Как собирается P&L / ОПиУ

Дата фиксации: 2026-05-18.  
Последнее обновление источников: 2026-05-22.

Рабочий файл: Google Sheets `2026 ОПиУ • [ИП Шокина]`  
Ссылка: https://docs.google.com/spreadsheets/d/1XmyQghzLUzW-EpBKYP_RnNuxSWprnRDlBX0qATfgMi8/edit

Режим работы: read-only. Исходный Google Sheets не изменялся.

## Главное правило по документным расходам

Для счетов, УПД, актов и подписочных сервисов P&L / ОПиУ заполняется по **месяцу оказания услуги из документа**, а не по дате письма и не только по дате оплаты.

Правило для всех документных расходов:

- период услуги внутри счета/УПД/акта является основным основанием месяца P&L;
- дата платежа используется для сверки оплаты и ДДС;
- дата письма используется только как технический признак поиска документа;
- если счет пришел несколько раз, дедуплицировать по номеру счета, периоду и сумме;
- если есть счет и УПД на один период и одну сумму, считать это одним расходом, а не двумя;
- если период услуги в документе не найден, статус периода = `требует проверки`, не автоматический `0`.

## Главное правило по выручке, скидкам и себестоимости

Первичный источник для P&L по строкам выручки, скидок и себестоимости по направлениям - iiko OLAP `Отчет о выручке по направлениям`.

Если следующему агенту нужно понять, откуда берутся:

- выручка без учета скидок;
- выручка с учетом скидок;
- сумма скидки;
- себестоимость / food cost;
- разрез по направлениям `Роллы`, `Пицца`, `Горячий цех`, `Бар`,

сначала нужно смотреть именно этот OLAP-отчет, а не P&L preset, не ДДС и не агрегированные processed CSV. Google Sheets `ОПиУ` хранит ручной перенос и управленческую раскладку этих данных, но первичный источник чисел - `Отчет о выручке по направлениям`.

Правило показателей:

| Строка P&L | Показатель в OLAP `Отчет о выручке по направлениям` |
| --- | --- |
| Выручка без учета скидок | сумма без скидки |
| Выручка с учетом скидок | сумма со скидкой |
| Скидки | сумма скидки |
| Расход продуктов / food cost | себестоимость |

Правило направлений:

| Колонка ОПиУ | Направление в OLAP |
| --- | --- |
| Роллы | `Суши` + `Специи, роллы Черникова` |
| Пицца | `Пицца` |
| Горячий цех / ГЦ | `Шаурма` |
| Бар | `Бар` |

Если месячный лист ОПиУ не заполнен или OLAP-отчет не обновлялся, ставить статус `нет данных` / `не обновляется с указанного месяца`, а не считать пустые ячейки нулем.

## Главное правило по ДДС-строкам P&L

Для всех строк P&L, у которых источником в листе `Статьи` указан **`ДДС классический`** (целиком или как один из компонентов смешанной строки), первичный источник — **не банковская выписка T-Bank/Sber**, а **Google Sheets `2026 ДДС — Классический • ИП Шокина`**, в котором владелец ведёт ручную/полу-ручную классификацию операций по статьям ДДС.

| Параметр | Значение |
| --- | --- |
| Документ | https://docs.google.com/spreadsheets/d/1ZkyXPcotiyEeJ-NJxDxf-u2UP9tJFh27HAA_ZjpCYco/edit |
| Лист сводной таблицы | `ДДС: Сводный` |
| Структура `ДДС: Сводный` | колонка `A` = названия статей ДДС; строки 1-117; колонки `B..M` = месяцы 1..12; ячейка = подписанная сумма за месяц (выбытия отрицательные) |
| Лист построчных операций | `ДДС: месяц` |
| Колонки `ДДС: месяц` | `A`=Месяц (текст), `B`=Мсц (цифрой), `C`=Дата, `D`=Сумма (signed), `E`=Кошелёк, `F`=Направление бизнеса, `G`=Контрагент, `H`=Назначение платежа, `I`=Статья, `J`=Платёж/поступление, `K`=Вид деятельности |

**Почему банковская выписка не подходит как первичный источник для этих строк:**

1. Фактические платежи **разнесены по нескольким кошелькам**: банковские (`Тинькофф`, `Альфа`, `Сбербанк`) и наличные (`Сейф`, `ТК Черникова`, `ТК Гагарина`, `ГарантФонд`). Банковский импорт видит только банковские кошельки.
2. **Наличные операции** из кассы (мойщица, ремонт оборудования, частные подрядчики, мелкие закупки администраторов) в банке не появляются, но **есть в ДДС-листе** и являются настоящим расходом периода.
3. **Розничные мерчанты** через бизнес-карту T-Bank приходят с обезличенными названиями (магазины, бытовые расходы), которые автоматический классификатор не разнесёт корректно в управленческие статьи.
4. Владелец **уже выполнил классификацию** этих операций в Google Sheets — нет смысла пытаться её воспроизвести из сырых банковских данных, нужно прочитать готовое.

**Правило для агентов:**

Для любой строки P&L с источником `ДДС классический`:

```text
P&L расход/уменьшающая строка = signed target value по влиянию на прибыль
```

Где `X` — номер строки, соответствующей статье ДДС с тем же названием (с учётом aliases — см. ниже). Для строк, которые формулы ОПиУ вычитают, положительное значение уменьшает прибыль, отрицательное значение увеличивает прибыль. Обычное выбытие из ДДС становится положительным расходом, но возврат, компенсация, сторно или поступление внутри расходной статьи должно попасть в ОПиУ со знаком минус.

Для **смешанных строк** (например `Содержание торговых точек` = ДДС + iiko-накладные) — суммируются компоненты в целевом знаке ОПиУ: плюс, если компонент уменьшает прибыль; минус, если увеличивает прибыль.

### 2026-05-22. Правило знаков расходных строк

В месячных листах ОПиУ знак в ячейке расходной/уменьшающей строки отражает влияние на прибыль, а не только направление денежного движения:

- `+` в расходной строке = статья уменьшает прибыль, формула ОПиУ ее вычитает;
- `-` в расходной строке = статья увеличивает прибыль или компенсирует расход, формула ОПиУ вычитает отрицательное число;
- нельзя механически применять `abs()` к ревизиям, инвентаризациям, штрафам, возвратам, сторно и другим подписанным источникам;
- строка `Результаты ревизии` состоит из двух компонентов: подписанный результат продуктовых инвентаризаций из iiko и штрафы по ревизиям из зарплатной ведомости;
- штрафы по ревизиям берутся из Google Sheets `2026 Зарплатная ведомость • [ИП Шокина]`, лист `Свод`, строка 16, за соответствующий месяц;
- компонент штрафов записывается со знаком минус в ОПиУ, потому что компенсирует потери по ревизиям и увеличивает прибыль.

**Aliases в `ДДС: Сводный`:**

Имена статей в листе `Статьи` ОПиУ могут отличаться от имён в `ДДС: Сводный`. Известные расхождения, требующие явного маппинга:

| Имя в ОПиУ | Имя в ДДС: Сводный |
| --- | --- |
| `Налоги с ЗП` | `Налоги с з/п` |
| `Услуги ФД и НК` | `Услуги ФД и НК` (но в `ДДС: месяц` встречается алиас `Услуги ФД`) |
| `Оплата систем автоматизации` | `Оплаты систем автоматизации` |
| `SEO - оптимизация` | `SEO-оптимизация` |

Полный реестр алиасов — будущая сущность `dds_article_aliases` в DDS-модуле (см. [21-dds-module-spec.md](/app-spec/modules/finance/dds/spec.md)).

**Список строк P&L, для которых `ДДС: Сводный` является первичным источником** (или одним из компонентов): см. [research/processed/dds_discovery/pnl_lines_from_dds_sheets.csv](/research/processed/dds_discovery/pnl_lines_from_dds_sheets.csv).

**Замечание о приоритете источников:**

- Если у строки в листе `Статьи` источник = `айко OLAP …` или `iiko …` — первичный источник iiko, не ДДС.
- Если источник = `зарплатная ведомость` — первичный источник Google Sheets `2026 Зарплатная ведомость`, не ДДС.
- Если источник = `ДДС классический` (одиночный) — первичный ДДС, банк не нужен.
- Если источник смешанный (`ДДС классический + iiko`, `Mango Office + iHC + Микроэл`, `Зарплатная ведомость + банк`) — суммируются компоненты в порядке, описанном в карточке строки.

### 2026-05-19. Исторический контур Гагарина

Уточнение владельца: точка `Гагарина` не работает с 2024 года.

Строки `Выручка без учета скидок Гагарина`, `Выручка с учетом скидок Гагарина`, `Расход продуктов (фудкост) Гагарина`, `Аренда торговой точки Гагарина` и `Коммунальные платежи Гагарина` остаются в справочнике ОПиУ как исторические строки, но для P&L 2026 не рассчитываются как активная операционная точка. Их статус в карте источников: `не используется; точка не работает с 2024`.

Если в iiko, ДДС, договорных расчетах или черновых P&L после 2024 года встречаются суммы с признаком `Гагарина`, их нельзя автоматически относить в действующую операционную модель и нельзя считать подтвержденным нулем. Такой период/сумма получает статус `требует проверки` как возможный исторический хвост или ошибка классификации.

### 2026-05-19. ФОТ через `Из Отчетов` и `IMPORTRANGE`

Уточнение владельца: ФОТ автоматически попадает в ОПиУ из Google Sheets `2026 Зарплатная ведомость • [ИП Шокина]` через `IMPORTRANGE`.

Техническая проверка read-only 2026-05-19: в ОПиУ лист `Из Отчетов` содержит формулу:

```text
=IMPORTRANGE("https://docs.google.com/spreadsheets/d/1gQy-qb8DTVC1kAhaHaeF_xBo3CIYu1_Ka2teHwuOeC0/edit?gid=1129510116#gid=1129510116";"'Свод'!A1:o20")
```

Источник: Google Sheets `2026 Зарплатная ведомость • [ИП Шокина]`, ID `1gQy-qb8DTVC1kAhaHaeF_xBo3CIYu1_Ka2teHwuOeC0`, лист `Свод`, диапазон `A1:O20`.

Импортированный блок `Свод` используется как staging-источник для строк ОПиУ:

| Строка ОПиУ | Источник в `Зарплатная ведомость -> Свод` | Связь в месячном листе ОПиУ |
| --- | --- | --- |
| `Зарплата поваров (оклады и удержания)` | строки 7-9: `Роллы`, `Пицца`, `Горячий цех` | месячный лист, строка 24: `LOOKUP($B$1; 'Из Отчетов'!C1:N1; 'Из Отчетов'!C7:N7/C8:N8/C9:N9)` |
| `Зарплата администраторов` | строка 10 | месячный лист, строка 36: `LOOKUP(... 'Из Отчетов'!C10:N10)` |
| `Зарплата администрации` | строка 11 | месячный лист, строка 57: `LOOKUP(... 'Из Отчетов'!C11:N11)` |
| `Премии поваров, шеф-повара, администраторов` | строка 12 `Премии всем и %% шеф-повару` | месячный лист, строка 37: `LOOKUP(... 'Из Отчетов'!C12:N12)` |
| `Накопительный фонд` | строка 13 | месячный лист, строка 50: `LOOKUP(... 'Из Отчетов'!C13:N13)` |
| компонент строки `Результаты ревизии`: штрафы по ревизиям | строка 16 | брать месяц через `LOOKUP`/импорт и добавлять в строку `Результаты ревизии` со знаком минус |
| `Списание невостребованных депозитов` | строка 17 | источник подтвержден владельцем как пригодный для автоматического подтягивания; в проверенном месячном листе строка не подключена формулой |
| `Налоги с ЗП` | строка 18 | не использовать как полный автоматический источник; строка налогов с ЗП собирается из ДДС статьи `Налоги с З/п` |

Формула месяца в строках, подключенных через `LOOKUP`, берет номер месяца из `B1` месячного листа и ищет его в `Из Отчетов!C1:N1`. Если лист `Из Отчетов`, исходная `Зарплатная ведомость`, строка `Свод` или месяц не найдены, статус периода = `требует проверки` / `источник не найден`, не автоматический `0`.

Уточнение владельца по `Налоги с ЗП`: строку нельзя автоматически подтягивать только из `Зарплатной ведомости`, потому что социальные выплаты работодателя за сотрудника, например ПФР/страховые взносы, в зарплатной ведомости не учитываются. Основной источник для этой строки - ДДС, статья `Налоги с З/п`. Строка `Свод!18` в зарплатной ведомости может быть только вспомогательной/контрольной частью, но не полным источником P&L.

Уточнение владельца по `Списание невостребованных депозитов`: строку можно подтянуть автоматическим способом из `Зарплатная ведомость -> Свод`, строка 17, через уже существующий импорт на `Из Отчетов`. В текущем ОПиУ проверенные месячные листы не подключают эту строку формулой; Google Sheets не менять без отдельного разрешения.

Решение владельца 2026-05-25 для MVP P&L: экспорт ФОТ нужен **только итогом по ролям**, без детализации `роль x тип начисления`. Целевой additive export можно получать из Google Sheets `Расчет зарплат NEW`, лист `Свод`, диапазон `C7:C13` и соседние месячные колонки. В MVP нельзя смешивать role-cut и type-cut в одной строке: если нужен разрез по типам начислений, он остается аналитическим drill-down внутри payroll, но не отдельным обязательным разрезом для P&L close.

Последняя поправка владельца 2026-05-25 по налогам ниже EBITDA имеет приоритет над старым processed/report контекстом: ставка **7%** нужна только как расчетное accrual/model-начисление для P&L/API/system model: `УСН 6% + страховые взносы 1% = 7%` от iiko OLAP выручки без учета скидок, до уплаты комиссии партнерам. Это не cash-факт выплаты и не платежное поручение.

Фактическая выплата `659 783` - это только УСН 6%. Ее нельзя трактовать как сумму 7% и нельзя смешивать со страховыми взносами 1%. Если в старых артефактах встречается формулировка `695 783,93 = УСН 6% + страховые взносы 1% = 7%`, считать ее устаревшей: для P&L остается 7% accrual-модель, а cash/payment и tax payable ведутся отдельно.

Отдельная налоговая задолженность фиксируется как `tax_payable`, а не как дубль расхода P&L. Канонический source: WorkMail налогового агента `askad02@mail.ru`, письмо `#837` от 2026-05-20 `0,2 %.xls, ЕНП до 28.05.docx`: `ЕНП до 28.05.docx` = 18 556,93 ₽, `0,2 %.xls` = 78,95 ₽ по травматизму 0,2%. Срок из письма - оплатить до 2026-05-28; owner control deadline - закрыть tax payable до 2026-06-30. Период/разнесение по налоговым основаниям требует tax-mail parse/status `pending_parse`, не owner-question и не 0.

### 2026-05-19. Маркетинговые статьи через ЭДО DocsInbox / СБИС

Уточнение владельца 2026-05-19: документы по таргетированной, наружной и контекстной рекламе поступают в ЭДО DocsInbox, конкретно в СБИС. SEO-оптимизация и сайт/приложение также попадают туда. Для этих строк ДДС не является первичным источником начисленного P&L: ДДС может использоваться как кассовая сверка, рекламные кабинеты - как операционная сверка по показам/кликам/заявкам.

Обновление 2026-05-22: для `Таргетированная реклама` найден рабочий источник через WorkMail `smmbux@yandex.ru`; для `Контекстная реклама` и `SEO - оптимизация` найден более точный рабочий источник через Mail.ru / Biz Panel Синапса; для `Сайт и приложение` по StarterApp найден источник через Mail.ru `leshkina@starterapp.ru` и PDF-счет/УПД. СБИС/DocsInbox остается контуром документной сверки и резервом, но не блокирует фиксацию найденных правил ниже.

Решение владельца 2026-05-22 по таргетированной рекламе:
`Таргетированная реклама` для ОПиУ собирается только по WorkMail-источнику `smmbux@yandex.ru`, но первичным документом является не письмо `Отправка отчета`, а письмо `Документы для ИП Шокина Кристина Юрьевна от ИП Билинский Андрей Романович` с УПД. В интерфейсе почты отправитель может отображаться как `ИП Билинский А.Р.`. Во вложениях искать УПД по абонентскому обслуживанию/продвижению сообщества и УПД по рекламному бюджету, потраченному за период. ДДС/T-Bank по ИП Билинский используется как сверка оплаты, но не заменяет сумму расхода из УПД. Письмо `Отправка отчета` может быть только дополнительным контекстом/контролем, не первичным источником ОПиУ.

Решение владельца 2026-05-25 для MVP: в ОПиУ достаточно одной строки `Таргетированная реклама`. Разделение на рекламный бюджет, обслуживание/ведение, продвижение и прочее не требуется для MVP-отчета; эти компоненты могут сохраняться как документный drill-down по УПД. Доступ к WorkMail есть в `.env`, источник уже подтвержден владельцем. Следующие агенты не должны переоткрывать owner-question по источнику таргета; если сумм нет в processed-слое, задача = распарсить уже известное письмо/УПД, статус периода = `source_not_loaded` / `pending_parse`, не `requires_owner_review`.

Целевой сценарий автоматизации:

1. Завести в Saby отдельное внешнее приложение с сервисным доступом только на чтение нужных участков ЭДО.
2. Получить и хранить в `.env` параметры сервисной авторизации, не записывать секреты в Markdown и Google Sheets.
3. За нужный месяц запросить входящие документы: базово через `СБИС.СписокДокументовПоСобытиям` с `ТипРеестра=Входящие`; если после теста известны конкретные типы документов, можно использовать `СБИС.СписокДокументов` с `Направление=Входящий` и обязательным `Тип`. Период передавать в формате `ДД.ММ.ГГГГ`.
4. Для каждого кандидата сохранить технические поля: `document_id`, дата, номер, сумма, название, примечание, контрагент, ИНН/КПП, наша организация, тип/подтип вложения, сумма вложения, ссылка на архив/документ.
5. Если списка недостаточно для классификации или сверки, дочитать документ через `СБИС.ПрочитатьДокумент`.
6. Классифицировать документы в статьи ОПиУ по справочнику маппинга: ИНН/КПП контрагента + название контрагента + тип/подтип документа + ключевые слова в названии/примечании/вложениях.
7. Суммировать по месяцу даты документа или периода акта; правило даты нужно подтвердить на тестовом месяце. Если в документе есть несколько вложений с отдельными суммами, не дублировать сумму пакета и сумму вложений одновременно.
8. Все нераспознанные документы, дубли, отрицательные корректировки и документы без суммы отправлять в ручную проверку.

## Правила статусов

В этой методологии пустота и ноль не считаются одним и тем же.

Используемые статусы:

| Статус | Когда ставится |
| --- | --- |
| `актуально` | источник найден, заполнен за нужный период, формула понятна |
| `заброшено` | источник исторический и больше не ведется |
| `не обновляется с указанного месяца` | источник есть, но данные остановились с конкретного месяца |
| `формула сломана` | формула возвращает ошибку или ведет в отсутствующий диапазон |
| `источник не найден` | формула/описание указывают на источник, но он не найден |
| `ручной ввод, нужен ответ владельца` | в ячейках стоят ручные числа или ручные формулы без понятного процесса обновления |
| `не используется` | строка есть в справочнике, но явно помечена как неиспользуемая или не участвует в P&L |
| `требует проверки` | структура понятна, но не хватает проверки источника/актуальности |

### 2026-05-20. Оплата систем автоматизации — accrual для подписочных контрактов

Подтверждено владельцем 2026-05-20 после разбора платежей февраля 2026.

**Главное правило:** строка `Оплата систем автоматизации` собирается по **accrual basis** (расход признаётся по периоду услуги), а не по cash basis (по дате банковской выплаты). Это применимо ко всем подписочным контрактам поставщиков.

Обновление 2026-05-22: для iiko и Леммы найден документный контур через Mail.ru. Для них приоритетным основанием месяца P&L является период услуги в PDF-счете/УПД; T-Bank используется для сверки оплаты. Дата платежа сама по себе не определяет месяц расхода. По Лемме на этом шаге подтвержден апрель 2026; другие месяцы нужно брать из документов, а не растягивать апрельскую сумму автоматически.

Решение владельца 2026-05-22 по Реви/Greevy: контрагент оплачивается раз в полгода. Для ОПиУ брать сумму оплаты из ДДС или T-Bank и признавать расход равными частями: `ежемесячный расход = сумма оплаты / 6`. В строку `Оплата систем автоматизации` за каждый из 6 месяцев периода заносится именно эта 1/6 суммы, а не полный cash-платеж месяца оплаты.

Состав строки за месяц = сумма ежемесячных accrual по контрактам:

| Контрагент | Подкомпонент | Ежемесячный accrual | Контракт |
| --- | --- | ---: | --- |
| АО «АЙКО» | iiko курьерское приложение | 4 260 ₽ | `SUB-IIKO-COURIER` |
| АО «АЙКО» | iiko основной тариф | 16 430 ₽ | `SUB-IIKO-TARIFF` |
| ООО «ЛЕММА» | техническая поддержка ресторанов | 3 700 ₽ | счет-договор `52482/1/У` |
| ООО «РЕВВИ» (Greevy) | сервис обратной связи | 9 990,17 ₽ (= 59 941 / 6) | `SUB-GREEVY-HALFYEAR` |
| ООО «ДОКСИНБОКС» | сервис ЭДО | 15 580 ₽ | `SUB-DOCSINBOX-MONTHLY` |
| **Итого для месяца, где подтверждены все компоненты выше** | | **49 960,17 ₽** | |

Реестр контрактов: [research/processed/dds_discovery/vendor_billing_schedules.csv](/research/processed/dds_discovery/vendor_billing_schedules.csv).  
Полное описание правил accrual (4 сценария: ежемесячная по графику, ежемесячная с опозданием, multi-period prepaid, переменная сумма): [research/processed/dds_discovery/vendor_billing_rules.md](/research/processed/dds_discovery/vendor_billing_rules.md).

Связь с балансом:

- Платёж Greevy 59 941 ₽ создаёт в балансе на дату оплаты `prepaid_expenses = 59 941 − ежемесячный accrual за месяц оплаты`. В каждом из 6 месяцев периода в ОПиУ попадает 9 990,17 ₽; в следующих месяцах prepaid уменьшается на 9 990,17 ₽ с переносом в P&L.
- Два платежа iiko по 4 260 ₽ в одном месяце — один catch-up за предыдущий, один по графику за текущий. В P&L текущего месяца идёт только один, второй корректирует P&L предыдущего.
- Доксинбокс может приходить одной платёжкой 15 580 ₽ или двумя (8 300 + 7 280) — в P&L идёт договорные 15 580 ₽/мес независимо от способа оплаты.

Исторический контрольный расчет на февраль 2026 из разбора 2026-05-20, до добавления документного контура Леммы: cash = 100 471 ₽, accrual = 46 260,17 ₽, разница 54 211 ₽ (catch-up январский 4 260 + предоплата Greevy за 5 будущих месяцев 49 951). Этот контрольный расчет не пересчитывался в рамках обновления документации 2026-05-22.

Связь с DDS-модулем: правило согласуется с `DDS-R026` (EDO expense accrual) и расширяет его на подписочные контракты без формального ЭДО-документа. В будущем приложении нужна сущность `vendor_billing_schedules` (см. [21-dds-module-spec.md](/app-spec/modules/finance/dds/spec.md)).

Открытые вопросы владельцу (вынесены в `vendor_billing_rules.md`):

1. Доксинбокс — подтвердить фиксированную договорную сумму 15 580 ₽/мес.
2. iiko — для каждого будущего месяца подтверждать сумму PDF-счетами из `donotreply@iiko.ru`; проверенный апрель 2026 подтвердил структуру 4 260 + 16 430.
3. Есть ли ещё подписочные контракты вне перечисленных (1С, антивирус, домены, хостинги, мессенджеры).

Текущий `pnl_2026_monthly.csv` и `pnl_2026_waterfall.csv` посчитаны по cash basis и должны быть пересчитаны по accrual после ответов владельца или при сборке P&L-модуля приложения.

Текущее решение 2026-05-22: правило по Реви/Greevy подтверждено; старые cash-basis строки `Оплата систем автоматизации` в processed P&L не переносить в ОПиУ без пересчета по accrual.

### Выручка без учета скидок Черникова

**Блок P&L:** выручка.

**Где находится строка**

| Уровень | Место |
| --- | --- |
| Справочник строк | `Статьи!A4:O4` |
| Сводный P&L | `Факт!A7:M7` |
| Январский месячный лист | `1!B5:M5` |

**Формула**

В `Факт!B7`:

```gs
=if($M$1;IFERROR(INDIRECT("'"&B$2&"'!"&$B$1&match($A7;INDIRECT("'"&B$2&"'!B1:B");0)));
IFERROR(INDIRECT("'"&B$2&"!"&$B$1&match($A7;INDIRECT("'"&B$2&"'!B:B");0))))
```

Человеческое объяснение: `Факт` берет номер месяца из `B2` (`1`), ищет название строки из `A7` на месячном листе `1` в колонке `B`, затем берет значение из колонки, указанной в `Факт!B1`. Сейчас `Факт!B1 = M`, то есть итог месяца из `1!M5`.

В `1!M5`:

```gs

```

| Направление | Ячейка | Формула/значение | Значение |
| --- | --- | --- | ---: |
| Роллы | `1!C5` | `=151430+2523724`; это `Суши + Специи, роллы Черникова` из OLAP-отчета | 2 675 154 |
| Пицца | `1!D5` | ручное число | 1 374 065 |
| Горячий цех | `1!E5` | ручное число из OLAP-направления `Шаурма` | 564 253 |
| Бар | `1!F5` | ручное число | 75 581 |
| Итого | `1!M5` | `=SUM(C5:L5)` | 4 689 053 |

Оставшихся вопросов по источнику и разделению ревизий/штрафов нет: штрафы входят в строку `Результаты ревизии`.

**Ответ владельца**

`Результаты ревизии` - это сумма подписанных продуктовых инвентаризаций из iiko и штрафов по ревизиям из `Зарплатная ведомость` -> `Свод` -> строка 16. Продуктовые ревизии проходят еженедельно, обычно по понедельникам. Продуктовый контекст определяется по товарам внутри документа.

**Итоговое правило**

Строка `Результаты ревизии` считается как сумма двух компонентов: подписанный результат продуктовых инвентаризаций за месяц из iiko `Товары и склады` -> `Документы инвентаризации` / API `/reports/storeOperations` с `documentTypes=INCOMING_INVENTORY`, плюс штрафы по ревизиям за тот же месяц из Google Sheets `2026 Зарплатная ведомость • [ИП Шокина]`, лист `Свод`, строка 16. В целевом знаке ОПиУ: `результат инвентаризаций - штрафы по ревизиям`. Если продуктовые инвентаризации за период не найдены, не отделены от упаковки или нет значения штрафов в зарплатной ведомости, статус периода должен быть `требует проверки` / `источник не найден`, а не автоматический `0`.
