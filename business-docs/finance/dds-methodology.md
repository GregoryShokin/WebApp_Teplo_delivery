# Методология заполнения ДДС по статьям

Дата черновика: 2026-05-23.  
Обновлено: 2026-05-24.  
Источник истины: файл `research/private/google_drive/dds_2026_classic.xlsx`, лист `ДДС статьи`.

## Назначение

Этот документ фиксирует только статьи из классического ДДС. Не переносим сюда строки из API, P&L, iiko или будущей модели приложения, если их нет на листе `ДДС статьи`.

Ключевая логика заполнения:

```text
расчетный счет / кошелек
  -> банковская или кассовая интеграция
  -> операция
  -> системное имя контрагента в ДДС
  -> официальное имя контрагента
  -> статья ДДС
```

То есть ДДС заполняется прежде всего по счетам. Для расчетных счетов первичный источник факта - банковская интеграция, а не ручной источник из описания статьи. Колонка `Источники информации` на листе `ДДС статьи` остается подсказкой для подтверждающих документов и ручных/кассовых случаев.

Для каждой статьи ниже указаны:

| Поле | Откуда берем |
| --- | --- |
| Статья, группа, вид деятельности | Лист `ДДС статьи` |
| Описание статьи | Лист `ДДС статьи` |
| Источники информации | Лист `ДДС статьи`; это подтверждающий источник, а не замена банковской интеграции по счету |
| Контрагенты / роль | Фактически встречались в листе `ДДС месяц`; если не встречались, подбираем по описанию статьи и справочнику `Контрагенты` |

Важно: в исходном листе статья `Оплата поставщикам ` содержит пробел в конце. В документации ниже показываем ее как `Оплата поставщикам`, но при переносе в приложение нужно завести alias или очистить пробел в справочнике.

## Правила заполнения

| Правило | Как применять |
| --- | --- |
| Заполнять по счетам | Сначала определяем счет/кошелек операции и источник факта по этому счету. |
| Банк = первичный источник по расчетному счету | Для `Тинькофф` факт идет из T-Bank API, для `Сбербанк` - из Sber API. |
| Контрагент имеет два имени | В ДДС храним системное имя, но рядом фиксируем официальное имя из банка/документа. Например: `Амай` = ООО `ТОРА`. |
| Ориентироваться на `ДДС статьи` | Если статьи нет на этом листе, она не является статьей классического ДДС. |
| Сохранять группу и вид деятельности | Они определяют, куда операция попадет в ДДС: операционная, финансовая, инвестиционная или техническая. |
| Источник из справочника статьи использовать как подтверждение | Колонка `Источники информации` помогает понять, какой документ или ручной источник подтверждает операцию; для расчетных счетов факт все равно приходит из банковской интеграции. |
| Контрагента подбирать отдельно | Сначала смотреть фактические контрагенты в `ДДС месяц`, затем справочник `Контрагенты`, затем уточнять у руководителя. |
| Не закрывать непонятное в `Прочие` автоматически | `Прочие расходы` и `Прочие поступления` использовать только когда статья действительно не описана другим правилом. |

## Источники По Счетам

| Счет / кошелек ДДС | Тип | Первичный источник факта | Как использовать |
| --- | --- | --- | --- |
| `Тинькофф` | Расчетный счет | T-Bank Business Open API | Импортировать операции банка, затем сопоставлять официального получателя/плательщика с системным контрагентом ДДС и статьей. |
| `Сбербанк` | Расчетный счет | Sber API | Импортировать поступления, эквайринг, внутренние переводы и прочие операции, затем классифицировать в ДДС. |
| `Альфа` | Расчетный счет | Нет активного источника | Исторический счет, в 2026 не используется; не заполнять как активный контур без решения владельца. |
| `Сейф` | Наличные | Кассовый журнал / ручной ввод | Использовать для наличных движений и инвентаризации, не как банковскую интеграцию. |
| `ТК Черникова` | Торговая касса | iiko `Главная касса` | Использовать операции iiko по главной кассе и сопоставлять корсчета/комментарии со статьями ДДС. |
| `ТК Гагарина` | Торговая касса | Нет активного источника | Исторический кошелек закрытой точки; не заполнять в активном 2026 без отдельного подтверждения. |
| `ГарантФонд` | Депозиты курьеров | T-Bank / payroll deposit context | По решению владельца 2026-05-25 это депозиты курьеров, физически хранятся в Т-Банке. Не резервный фонд и не нерасшифрованный legacy-кошелек. |

### Owner decisions 2026-05-25: `ТК Черникова` / iiko `Главная касса`

Канонический источник операций `ТК Черникова` - iiko OLAP `TRANSACTIONS`, `Account.Name = Главная касса`. Для rule engine зафиксированы seed-правила:

| Корсчет iiko | Бизнес-смысл | Статус правила | Правило для DDS |
| --- | --- | --- | --- |
| `Алиса наличные` | Деньги за заказы партнера, которые клиент оплатил напрямую партнеру. Физически денег в кассе/сейфе нет; сумма копится как дебиторская задолженность партнера и обычно забирается через 2-3 недели. | `closed_final` | Не признавать cash-in в момент заказа. До фактического получения денег вести как partner receivable; приход DDS появляется только в момент фактического получения денег. |
| `Перемещения` | Рудиментарный счет времен точки Гагарина, когда деньги могли мигрировать между точками. | `closed_final` / `legacy` | Для новых операций не использовать как активную статью. Исторические строки трактовать как internal transfer/legacy и отправлять на review при material сумме. |
| `Всякое Черникова` | Мелкие расходы: пакеты, тряпки, губки и похожие покупки. Часть требует индивидуальных корсчетов, часть - ручной пометки статьи DDS. | `requires_owner_review` | Создать отдельный слой классификации мелких расходов: private comment/чек -> конкретная статья DDS; без уверенного правила не относить автоматически в `Прочие`. |
| `Всякое Гагарина` | Хвост старой точки, нужен для доступа к исторической информации по корсчету. | `closed_final` / `legacy_reference` | Не активная операционная точка; не смешивать с текущей Черниковой. |
| `Депозиты курьеров` / `Депозиты сотрудников` | Операционный корсчет депозитов курьеров; администраторы отвечают за ведение. Обычно собирается 500 руб., иногда 200 руб. для подстраховочных смен. | `closed_final` как DDS/control source | Использовать для контроля движения депозитов и связи с `ГарантФонд`; персональный payroll-subledger и расчёт обязательств не строить только из iiko без payroll-сверки. |

## Сопоставление Контрагентов

Системное имя - это имя, которым контрагент живет в ДДС. Официальное имя - юридическое или банковское имя из выписки, счета, УПД или подтвержденного справочника. Для автоматизации нужно хранить обе формы.

Контрагент считается готовым к автоматизации только когда у него есть:

## Карта Статей

| Статья ДДС | Группа | Вид деятельности | Описание из ДДС | Источники информации из ДДС | Контрагенты / роль для подбора |
| --- | --- | --- | --- | --- | --- |
| `Поступление — Перевод между счетами` | Поступление | Техническая операция | Поступление денег с нашего счета или другого кошелька | Выписки по р/с, личный кабинет банка | не встречалось в журнале; подбирать по описанию статьи |
| `Выбытие — Перевод между счетами` | Выбытие | Техническая операция | Перевод денег на другой наш счет или кошелёк | Выписки по р/с, личный кабинет банка | Розничные покупатели |
