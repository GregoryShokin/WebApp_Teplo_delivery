## ⚠️ ПРЕДУСЛОВИЕ №1 (блокирует ЛЮБОЙ перк-пуш): механизм начисления перка не подтверждён

Перк («подарок-позиция», «комплимент от кухни», «бесплатная доставка») можно обещать в тексте **только если касса умеет его реально выдать и погасить**. Сейчас сквозной автоматический механизм НЕ подтверждён ни для одного перка (push-plan уже флагнул это для бесплатной доставки). Это не копирайт-вопрос, это касса. Кандидаты и статус:

| Перк | Кандидат-механизм | Статус | Атрибутируемость | Fallback сегодня |
|---|---|---|---|---|
| Подарок-позиция / комплимент (себест ~150–250 ₽) | Персональный промокод Starter на бесплатную конкретную позицию | **предусловие** — Starter `GET /promocodes` подтверждён, СОЗДАНИЕ через API не подтверждено (нужен `openapi.json`) | да (по коду) | ручной комп кассиром по флагу заказа (M3) |
| Подарок-позиция | iiko: таргет-бонус на карту / комбо со 100%-позицией | **предусловие** — бонусная программа iiko активна (списание 100%), грант конкретной позиции не подтверждён | частично | M3 |
| Бесплатная доставка | Промокод/правило на снятие платы за доставку для сегмента | **предусловие** — push-plan: «должна реально включаться в системе» | да (по коду) | нет (если плата за доставку не снимается правилом — НЕ обещать) |
| Статус Чемпиона | Невидимый перк = комплимент к заказу, без слов «приоритет/быстрее» | ок (через комплимент) | n/a | M3 |

**Правило:** до подтверждения механизма перк-несущие тексты (всё, кроме «без перка» касаний) — в режиме ревью, не в авто-рассылку. Единственный механизм, работающий СЕГОДНЯ — ручной комп кассиром (M3): не масштабируется и не атрибутируется, годится только для пилота на малом объёме.

**Резолюция предусловия:** (1) прочитать `openapi.json` → есть ли `POST /promocode` (создание) с типом «бесплатная позиция» и «бесплатная доставка»; (2) если нет — спросить вендора (ООО «Назад в будущее», `leshkina@starterapp.ru`), как программно выдать подарок-позицию персонально; (3) до этого — пилот через M3 на «нельзя терять»/welcome малой партией.

## ФАЗА 1 — Контент-библиотека по сегментам

### 1.1. Маппинг: наши iiko-сегменты ≠ кластеры Starter (важно)

Наши RFM-сегменты посчитаны в **iiko OLAP по `Delivery.CustomerPhone`** (9 367 гостей, окно 2025-01-01…2026-06-15, все каналы). Кластеры Starter (`GET /clusters`) — это **другая популяция** (только гости, известные приложению Starter) и **своя RFM-разбивка** (recency/frequency/monetary + `customersCount`). Поэтому:

- **Нельзя** слать «на сегмент Х из iiko» напрямую — Starter не знает наших сегментов. Слать можно либо на **кластер Starter** (`POST /distribution/cluster`), либо на **список телефонов** (`POST /distribution/customers`), либо на **одного** (`POST /distribution/customer`).
- Точные ID/названия/счётчики кластеров Starter **неизвестны до живого `GET /clusters`** (гейтнут сессией). Ниже — маппинг по **определению RFM-ячейки** (R/F/M), чтобы после вытяжки `/clusters` сопоставить детерминированно, не доверяя совпадению названий.

| Наш сегмент (iiko) | Гостей (iiko) | RFM-профиль (R / F / M) | Кластер Starter (по определению) | Как слать |
|---|---|---|---|---|
| **Новые 1→2** (главная течь) | 843 «Новые/разовые», recency 67д, orders 1.0 | R высокий, F=1, M низкий | «New customers» / «Promising» (recent, 1 заказ) | по событию (день 7–14 после 1-го заказа) → список телефонов или `customer` |
| **Остывающие 31–90д** (горячий ROI) | recency_bucket 31–90д ≈ 1 374 (623+436 repeaters + one-timers) | R средний, F≥2, M средний | «Need attention» / «About to sleep» | `cluster` Starter, отфильтровать F≥2 |
| **«Нельзя терять» 428** | 428, recency 346д, orders 6.1 | R низкий, F высокий, M высокий | «Can't lose them» | `cluster` + дубль SMS (Revvy) по списку |
| **Чемпионы** | 2 119, recency 46д, orders 12.3, **61,5% выручки** | R высокий, F высокий, M высокий | «Champions» | `cluster` (cap ≤1–2/мес) |
| ДР (триггер) | вся база, у кого есть дата | n/a | встроенный триггер `server-settings/push` | триггер, не рассылка |
| Любимое блюдо | вся активная база | n/a (персонализация по топ-позиции) | сегмент по последнему/частому блюду | `cluster`/список с переменной `{блюдо}` |

> **Действие на гейте:** вытянуть `GET /clusters`, выписать реальные `id` + `customersCount` каждого кластера, вписать в таблицу. Если у Starter нет ячейки, отделяющей F=1 от F≥2 в «остывающих» — слать «остывающих» списком телефонов из iiko, а не кластером.

**Везде исключить анти-персону ~3%** (free / >50%-скидочный 1-й заказ) — из теста И из holdout-контроля одинаково.

## ФАЗА 2 — Гейт: тест endpoint (РЕЗУЛЬТАТ: НЕ ПРОЙДЕН)

### 2(а) Сервисный токен для headless-доступа — НЕТ → БЛОКЕР автоматизации
- В `.env` и конфигах проекта **нет** токена/ключа Starter. Единственный рабочий доступ = **браузер-сессия владельца** (cookie), которой шла вся разведка (`data-channels.md` §3: «Доступ: сессия владельца (браузер)»).
- **Следствие:** запланированный Python-сервис welcome/«любимое» (`POST /distribution/cluster` по расписанию, паттерн курьерского сервиса, `action-plan.md` шаг 0.8) **не может авторизоваться headless** без токена. Это блокер автоматизации, не разовых ручных действий.
- **Резолюция:** запросить сервисный API-ключ у вендора (ООО «Назад в будущее» / StarterApp, `leshkina@starterapp.ru`). У них есть OpenAPI (282 пути) → токен-авторизация почти наверняка существует; подтвердить и получить scope на `distribution/*`. До этого автоматизация невозможна; вариант «скрести cookie сессии» — хрупкий, не для прода.

### 2(б) Тест-POST `/distribution/customer` (+10 мин, отложенная отправка) — НЕ ВЫПОЛНЕН
Не могу выполнить из этой среды, потому что:
1. нет токена → нельзя дёрнуть headless из Bash;
2. единственная авторизация — **живая сессия владельца** → нужны: Claude in Chrome подключён + владелец залогинен в `crm.starterapp.ru`, **тестовый номер владельца**, и **явное одобрение реальной отправки** (даже отложенная на свой номер — это реальный send на боевом Starter);
3. перед любым POST нужно прочитать `GET /fmteplo/api/v1/openapi.json` и подтвердить точную схему `/distribution/customer` (обяз. поля, формат и таймзона `datetime`, deferred-vs-immediate) — тоже гейтнуто сессией.

**Протокол теста (выполнить, когда есть браузер + одобрение):**
1. `GET /fmteplo/api/v1/openapi.json` → выписать схему `POST /distribution/customer`: обязательные поля, тип `datetime` (ISO? unix? таймзона — MSK/UTC?), как помечается отложенная vs немедленная.
2. Подтвердить `title_translate` / `body_translate` = MultiLang `{ "ru": "..." }`.
3. POST на **один номер владельца**, `datetime` = now+10 мин:
   ```json
   {
     "phone": "<номер владельца>",
     "title_translate": { "ru": "Тест Тепло" },
     "body_translate":  { "ru": "Проверка отложенной отправки — игнорируйте." },
     "datetime": "<now+10мин в подтверждённом формате/TZ>"
   }
   ```
4. Зафиксировать: пришёл ли push **ровно через ~10 мин** (не сразу) → подтверждает deferred. Записать фактический формат/TZ `datetime`, обязательные поля, поведение немедленной (без `datetime`).

**ГЕЙТ:** пока 2(б) не подтверждён — реальные рассылки гостям ЗАПРЕЩЕНЫ, Фаза 3 не активируется.

## ФАЗА 3 — Календарь рассылок (ЧЕРНОВИК — НЕ активировать до гейта + одобрения)

> Активировать **только** после: (1) гейт 2(б) пройден; (2) предусловие №1 (механизм перка) закрыто хотя бы для пилота; (3) пер-текстовое ревью владельца. Любой НОВЫЙ текст и любой broadcast — всегда под ревью владельца перед реальной отправкой.

### 3.1. Стартуем 3–4 механики (остальное — backlog push-plan)

| Механика | Триггер / когда | Сегмент → как слать | Текст (A/B) | Holdout | Канал |
|---|---|---|---|---|---|
| **Welcome 1→2** | день 7–14 после 1-го заказа (до медианы межзаказа 21д) | новые платящие, список телефонов / `customer`; анти-персона искл. | A1/A2/A3 | 10% без триггера vs 90% → lift доли до 2-го заказа (база ~20%) | push (+SMS без-апп) |
| **Реактивация горячих 31–90д** | молчание 28–35д | `cluster` (F≥2) / список | B1/B2 (касание 1, без перка); B3 при молчании | 10–20% контроль | push (бесплатно) |
| **Любимое блюдо** | персонально, по топ-позиции | `cluster`/список с `{блюдо}` | F1/F2 | 10% контроль (проверка инкрементальности) | push |
| **День рождения** | триггер ВКЛ | встроенный `server-settings/push` | E1/E2 | n/a (триггер) | push (+SMS дубль ценным) |

### 3.2. Частота / suppression (жёстко)
- ≤1 промо-push/нед на гостя; цель ≤2–3/мес; push+SMS считать вместе.
- Чемпионы — ≤1–2 касания/мес суммарно.
- Приоритет на гостя: оперсервис > welcome/win-back > любимое > повод > статус. Получил касание → на неделю выпадает из остальных.
- Триггерные (по событию гостя), **не** broadcast по календарю.

### 3.3. Встроенные триггеры — поправить заодно (`GET/PUT server-settings/push`)
| Триггер | Сейчас | Сделать |
|---|---|---|
| День рождения | ВЫКЛ (500 ₽ настроено) | ВКЛ; **подарок-позиция ~150–200 ₽**, не 500 ₽ деньгами |
| Реактивация (retention) | `afterDays=40` | `afterDays=28` (медиана межзаказа 21 → ловить раньше) |
| Сгорание баллов | `afterDays=10050` (**сломано**, ≈27,5 лет) | починить: привязать к реальному TTL баллов. **NB:** механика «баллы сгорают» = по сути скидочный нудж, против бренд-философии «перк≠скидка» → **НЕ** в стартовые 4; включать отдельно с одобрением. Конкретное число задать по политике TTL баллов (узнать). |
| Отзыв (30 мин) + статусы заказа | ок | не трогать |

### 3.4. Holdout (минимально достаточный — инфры H0-2 нет)
- Исключить 10–20% каждого сегмента как контроль (не получают рассылку); мерить lift по реальной марже дошедших.
- Платные каналы (SMS «нельзя терять») — **промокод обязателен** для атрибуции (last-touch 72ч не инкрементален).
- Анти-персона исключена из теста и контроля одинаково.
