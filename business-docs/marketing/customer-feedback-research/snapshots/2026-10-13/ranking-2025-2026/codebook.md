# Единые правила смысловой разметки отзывов (v2025-2026-2)

Нужно прочитать смысл КАЖДОГО комментария, включая оценки 5. Нельзя делать тематическую разметку одним регулярным выражением или угадывать по оценке. У одного отзыва несколько кодов, но один код один раз. Только явная неприятность/сервисное трение или конкретная просьба исправить существующее неудобство. Положительные пожелания новых блюд отделять как suggestion. «Ужас», «не понравилось», «испортилось» без понятной конкретики — vague_negative, без тематического кода. «Невкусно» имеет конкретную тему food, даже без названия блюда. Проблема, которую быстро исправили, всё равно кодируется; похвалу исправления не считать communication-жалобой.

Допустимые коды:
- food: вкус, приготовление, текстура/консистенция, несвежесть по словам клиента, качество ингредиента, посторонний предмет, неприятная рецептура. Просто «мало начинки» без оценки вкуса/качества -> value, не автоматически food. «Много риса и невкусно» -> food+value, если количество начинки/баланс явно критикуется.
- waiting: прямо долго, опоздание против обещанного, неправильное время, заказ не получен/сорван на момент написания. Просто указано «доставка 1.5 часа» без недовольства/нарушения обещания — не автоматически жалоба. «Долго, зато вкусно» всё равно явное трение; «небыстро, понимаем, заказываем заранее, всё устраивает» — positive_caveat без жалобы.
- communication: грубость/невнимательность, не отвечают, не информируют, отказ/неудовлетворительная обработка обращения, проблема передачи/поведения курьера. Простое упоминание звонка/курьера без претензии не кодировать. Жалобу на продукт не дублировать как communication по факту обращения.
- temperature: клиент явно недоволен холодным/остывшим/не той температурой. В том числе холодные роллы по восприятию клиента; это не доказывает нарушение технологии. Не считать каждый холодный компонент автоматически дефектом. При негативе температуры горячего блюда отмечать подтип hot_food; роллов unknown_expectation если неясно.
- completeness: неверный состав заказа, перепутали/не довезли блюдо, заявленную/заказанную опцию/соус/приборы/подарок не вложили или не добавили. Описанная невнимательность при приёме заказа может одновременно быть communication. Условие подарка само по себе не устанавливай.
- value: мало/уменьшился объём или начинка, дорого/подорожание как претензия, плохое соотношение цены/порции. Не добавлять food автоматически к нехватке начинки. Платные/дорогие соусы или доставка -> value; ожидание бесплатного уже обещанного/оплаченного подарка -> completeness; сбой бонусов -> ordering.
- ordering: сайт/приложение, невозможность оформить/оплатить/применить бонусы, некорректная информация состава в приложении, ограничения зоны/времени доступа к заказу, ошибка/обещание в приложении. Обещанное время нарушено -> waiting, не автоматически ordering только потому, что срок показан на сайте.
- presentation: повреждение/развалившийся внешний вид, перемешанная доставка, проблема упаковки/переноски/протекания. Рассыпчатый рис по консистенции -> food; явно развалившиеся роллы по виду/невозможности есть могут иметь food+presentation только если обе проблемы описаны.
- menu_options: нет нужной позиции/дополнения/выбора в ассортименте и это прямо мешает заказу. Просто предложение нового блюда/комплимент меню -> suggestion без жалобы.

Не домысливать причинность, заражение/отравление, недовоз окончательно, точные температуры. Слова владельца/оператора не являются текстом клиента. Пять звёзд не отменяют конкретную жалобу.

Формат результата: один JSON object на каждую входную запись (JSONL):
{"feedback_id":123,"codes":["waiting"],"status":"specific_issue","note":"Доставка дольше обещанного.","subcodes":[],"confidence":"high"}
status ∈ specific_issue / positive_or_neutral / vague_negative / suggestion / unclear. Если кодов нет, note можно ""; если есть — короткий обезличенный пересказ, без цитат/имён/контактов. Для спорных случаев confidence=medium/low и note объясняет сомнение. Готовое output содержит каждую входную запись ровно один раз. Можно записывать списки IDs по кодам + скриптом разворачивать output, но только ПОСЛЕ смыслового прочтения всех текстов; нельзя заполнять пропуски непроверенным default.

## Решения итоговой сверки 13.10.2026

- Окно — по дате отзыва/сообщения, 01.01.2025 включительно — 01.01.2027 исключительно, фактический срез до 13.10.2026. Для Starter границы Europe/Moscow, не дата заказа или выгрузки.
- Просьба изменить существующее блюдо без явно выраженной нехватки/недостатка — suggestion: «чуть меньше сахара», «побольше соуса». Прямое «начинки не чувствуется», «раньше вкуснее», «невкусно» — конкретная проблема.
- Симптомы после еды и приписываемое еде отравление — зарегистрированное клиентское сообщение по food с subcode reported_symptoms_unverified. Ни диагноз, ни связь с нашим продуктом не устанавливаются. В этом срезе таких сообщений 8. Шутка о переедании при похвале исключена.
- Сообщение о неполученном ожидаемом подарке — completeness, право на подарок остаётся неизвестным. Нельзя автоматически трактовать это как доказанное нарушение акции.
- Разный размер кусочков без жалобы на общий объём — presentation. Невыполненная просьба по комплектации/упаковке — completeness; сам факт звонка не добавляет communication.
- Полностью одинаковый длинный текст — кандидат на повтор публикации. Для двух вручную проверенных групп сохраняем обе исходные строки, но повтор исключаем из объединённой суммы: public:R121 = Starter:8009 (тот же день и уникальный текст); public:R004 = public:R003 (одинаковый длинный положительный текст в двух площадках).
- Межканальная уникальность заказов/людей не установлена. Все прочие строки остаются наблюдениями в источниках; не выдавать их за отдельных людей или доказанные инциденты.
- Три отзыва Еды имеют день и месяц, но не отображённый год. Предполагаемый 2026 хранится отдельно; в строгий итог 2025–2026 они не включены. Условное добавление YE-003 даёт +1 food и +1 temperature, порядок рейтинга не меняется.
