# Архитектура платежного календаря

Дата анализа: 2026-05-20.

Источник: Google Sheets `Копия Платежный календарь • [Факт из ДДС] •ИП Шокина`, режим read-only. Исходная таблица не изменялась. Персональные строки плановых платежей и контрагентов не переносятся в этот файл.

Важно: календарь построен вокруг недель 2023 года и факта из старого ДДС. Его можно использовать как прототип логики план-факт, но не как факт или прогноз 2026.

## Карта листов

| Лист | Роль | Тип | Комментарий |
| --- | --- | --- | --- |
| `Регламент` | Правила ведения | Документация | Описывает цель календаря: контроль денежного потока и кассовых разрывов |
| `Как настроить` | Настройка шаблона | Документация | Пошаговые правила первичной настройки |
| `Календарь` | Главный недельный план-факт отчет | Расчетный | Недельные пары `план` / `факт`, поступления, платежи, изменение недели, остаток на конец |
| `Плановый Реестр поступлений` | Плановые входящие деньги | Ручной ввод + формулы | Контрагент, статья, сумма, плановая дата, комментарий, расчетный год/месяц/неделя |
| `Плановые Реестр выбытий` | Плановые платежи | Ручной ввод + формулы | Контрагент, статья, номер счета, сумма, дата оплаты, комментарий, расчетный год/месяц/неделя |
| `Факт ДДС` | Фактические операции из ДДС | Импорт + формулы | Через `IMPORTRANGE` подтягивает дату/сумму/контрагента/назначение/статью из `ДДС: месяц` |
| `Поставщики` | Аналитика/план по поставщикам | Расчетный/справочный | Использует факт ДДС и контрагентов; в миграцию лучше переносить как отдельный отчет, не как ядро календаря |
| `Справочник` | Статьи календаря | Импортированный справочник | Должен импортировать статьи и тип движения из ДДС |
| `Контрагенты` | Список контрагентов | Импортированный справочник | Должен импортировать список контрагентов из ДДС; приватный |
| `Диапазон недель` | Календарь недель | Ручной старт + формулы | Номер недели, дата начала, дата конца |
| `НФ` | Служебная страница шаблона | Не учетная | Не влияет на расчеты |

## Как устроен `Календарь`

`Календарь` разложен по неделям: каждая неделя имеет две колонки, `план` и `факт`. Например, для недели 1 используются соседние план/факт колонки, дальше пара повторяется.

Ключевые строки:

| Строка | Назначение | Логика |
| --- | --- | --- |
| `1` | Чекбоксы / флаги периода | BOOLEAN; участвует в выборе остатка для следующего периода |
| `3` | Год | В снимке видны устаревшие значения; год не должен быть ручным источником истины |
| `4` | Начало недели | `VLOOKUP(номер недели; Диапазон недель; 2)` |
| `5` | Конец недели | `VLOOKUP(номер недели; Диапазон недель; 3)` |
| `6` | Номер недели | Ручная/шаблонная разметка недели |
| `7` | План/факт | Текстовый признак колонки |
| `8` | Остаток на начало | Берет предыдущий остаток на конец, с учетом флага в строке 1 |
| `9` | Поступления | `SUM` строк поступлений |
| `10:56` | Статьи поступлений | Список статей через `FILTER(Справочник; тип = Поступление)` и `SUMIFS` по плану/факту |
| `57` | Платежи | `SUM` строк выплат |
| `58:110` | Статьи выплат | Список статей через `FILTER(Справочник; тип = Выбытие)` и `SUMIFS`; плановые выбытия берутся со знаком минус |
| `111` | Изменения за неделю | `Поступления + Платежи` |
| `112` | Остаток на конец | `Остаток на начало + Изменения за неделю` |

Главная логика будущего приложения: недельный roll-forward денежных средств:

```text
opening_balance_week = previous_week_closing_balance
planned_inflows_week = sum(payment_calendar_items where type=inflow and due_date in week)
planned_outflows_week = -sum(payment_calendar_items where type=outflow and due_date in week)
actual_inflows_week = sum(cashflow_transactions where amount > 0 and date in week)
actual_outflows_week = sum(cashflow_transactions where amount < 0 and date in week)
net_week = inflows + outflows
closing_balance_week = opening_balance_week + net_week
```

## Как берется факт из ДДС

Лист `Факт ДДС` должен подтягивать данные из `ДДС: месяц`:

| Колонки `Факт ДДС` | Источник / логика |
| --- | --- |
| `A` Год | `YEAR(C)` |
| `B` Месяц | `MONTH(C)` |
| `C:D` Дата и сумма | `IMPORTRANGE(...; "'ДДС: месяц'!C5:D")` |
| `E:G` Контрагент, назначение, статья | `IMPORTRANGE(...; "'ДДС: месяц'!G5:I")` |
| `H` Платеж/поступление | `VLOOKUP(G; Справочник!A:B; 2)` |

В текущей копии импорт сломан: формулы `IMPORTRANGE` показывают `#REF!` и ссылаются на другой spreadsheet id, а не на предоставленную копию ДДС. Это нормальный риск шаблона, но в приложении такой связи быть не должно: факт календаря должен читаться напрямую из таблицы `cashflow_transactions`.

## Плановые реестры

`Плановый Реестр поступлений`:

- ручные поля: контрагент, статья поступлений, сумма план, дата планируемого получения, комментарий;
- формулы: год, месяц, номер недели из даты;
- validations: контрагент из `Контрагенты`, статья из `Справочник`, дата валидная.

`Плановые Реестр выбытий`:

- ручные поля: контрагент, статья, номер счета, сумма план, дата планируемой оплаты, комментарий;
- формулы: год, месяц, номер недели из даты;
- validations: контрагент из `Контрагенты`, статья из `Справочник`, дата валидная.

Для приложения это прототип сущности `payment_calendar_items`. Минимальные поля:

| Поле | Назначение |
| --- | --- |
| `direction` | `inflow` или `outflow` |
| `status` | `planned`, `approved`, `paid`, `cancelled`, `overdue` |
| `due_date` | Плановая дата оплаты/получения |
| `amount` | Плановая сумма, хранить положительной; знак выводить по direction |
| `article_id` | Ссылка на `dds_articles` |
| `counterparty_id` | Ссылка на `counterparties`, приватная |
| `wallet_id/account_id` | Опционально: планируемый кошелек/счет оплаты |
| `invoice_number_private` | Номер счета/документа, приватное поле |
| `comment_private` | Комментарий/назначение, приватное поле |
| `linked_transaction_id` | Связь с фактической операцией ДДС после оплаты |
| `week_id` | Расчетное поле или ссылка на календарную неделю |

## Формулы, которые нужно заменить серверной логикой

- `IMPORTRANGE` заменить прямой связью с `cashflow_transactions`, `dds_articles`, `counterparties`.
- `FILTER` статей заменить запросом к активным статьям по `movement_type`.
- `SUMIFS` по неделе и статье заменить агрегированными SQL-запросами.
- Номер недели считать календарной функцией / таблицей `calendar_weeks`, а не формулой с ручным диапазоном.
- Остаток на начало недели брать из предыдущего закрытого остатка или из snapshot по кошелькам.
- План-факт сверять на уровне item -> transaction link и агрегатов week/article.

## Риски старого календаря

1. Факт ДДС в копии не подключен: `#REF!` на `IMPORTRANGE`.
2. Импорт ссылается на старый ID ДДС, а не на предоставленную копию.
3. Недельный диапазон жестко завязан на 2023 год.
4. Строка года в календаре содержит устаревшие значения, не совпадающие с датами недель.
5. Статьи и контрагенты импортируются через внешние диапазоны; при ошибке импорта ломаются выпадающие списки и `FILTER` в календаре.
6. Плановые реестры содержат приватные данные: контрагентов, номера счетов, комментарии. В открытые файлы и отчеты переносить только агрегаты.
