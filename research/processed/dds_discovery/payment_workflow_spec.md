# Спецификация платежного процесса

Дата сборки: 2026-05-20.

Цель: описать рабочий платежный процесс для будущего приложения так, чтобы ДДС, P&L, payroll, ЭДО, ОС и баланс не смешивались.

## Основные сущности

| Сущность | Назначение |
| --- | --- |
| `counterparty` | юридическое и рабочее название, роль, owner status, источники распознавания |
| `payment_plan` | плановая заявка на платеж до фактической банковской операции |
| `payment_approval` | согласование суммы, статьи, даты, контрагента и документа |
| `bank_operation` | факт из банка: дата, сумма, направление, банк, технический контрагент |
| `dds_classification` | статья ДДС, payment role, качество разметки, правило/автор |
| `source_document` | акт, счет, УПД, счет-фактура, payroll run, налоговое основание, договор, чек |
| `document_match` | связь документа с платежом: полная, частичная, аванс, переплата, без оплаты |
| `pnl_or_balance_posting` | управленческое признание: P&L, актив, обязательство, капитал, suspense |
| `reconciliation_case` | задача на сверку, если сумма, дата, контрагент или статья не сходятся |
| `audit_log` | кто, когда и почему изменил заявку, статью, документ или статус |

## Статусы платежа

| Статус | Значение |
| --- | --- |
| `draft` | платеж создан, но не готов к согласованию |
| `needs_document` | требуется документ или договорное основание |
| `ready_for_approval` | сумма, контрагент, статья и основание заполнены |
| `approved` | согласован владельцем/ответственным |
| `scheduled` | платеж запланирован в платежном календаре |
| `paid_unmatched` | деньги ушли/пришли в банке, но заявка еще не связана |
| `bank_matched` | банковская операция связана с заявкой |
| `classified` | присвоена статья ДДС и payment role |
| `document_matched` | платеж связан с документом, payroll run, договором или ОС |
| `posted` | создана P&L/балансовая запись по правилам блока |
| `reconciled` | платеж, документ и учетная запись сверены |
| `owner_review` | требуется решение владельца |
| `closed` | кейс завершен |

## Базовый workflow

1. Создать `payment_plan`: контрагент, рабочая роль, сумма, дата оплаты, статья ДДС-кандидат, подразделение/точка, комментарий без полного банковского назначения.
2. Указать основание: ЭДО-документ, договор, payroll run, налоговое начисление, счет/чек, кредитный график или owner decision.
3. Проверить обязательные документы по статье. Если статья документная, платеж не должен уходить в `ready_for_approval` без `source_document` или явного исключения.
4. Согласовать платеж: лимит, cash balance, владелец статьи, период P&L/баланса.
5. Исполнить платеж в банке или импортировать факт из банка.
6. Смэтчить банк с заявкой по сумме, дате, контрагенту, назначению-классу и payment role.
7. Присвоить финальную статью ДДС. Если правило не уверено, отправить в `owner_review`.
8. Связать платеж с документом или ledger-событием.
9. Создать posting: P&L expense/revenue, fixed asset, loan liability, payroll liability settlement, owner equity, internal transfer или suspense.
10. Выполнить сверку и закрыть кейс.

## Workflow по типам платежей

### Поставщики продуктов и упаковки

- План: поставщик, ожидаемая сумма, дата, статья `Оплата поставщикам`.
- Документ: iiko приходная накладная, счет/УПД или акт сверки.
- ДДС: факт оплаты.
- P&L: не по оплате. Food cost идет из iiko OLAP/списаний по периоду.
- Исключения: аванс поставщику, возврат переплаты, бизнес-карта без чека.

### Payroll

- План: payment batch без персональных строк в открытых ДДС-артефактах.
- Документ/основание: закрытый payroll run и ведомость выплат.
- ДДС: `Выплата ЗП`, `Выплата аванса`, `Выплата накоплений`, агрегаты `Зарплата производственного/административного персонала`.
- P&L: начисления из payroll ledger, не выплаты.
- Сверка: сумма выплат по batch = банковские операции + касса; разница идет в reconciliation case.

### Payroll taxes

- План: налоговый платеж по периоду и типу налога.
- Документ: налоговый календарь/платежное основание, payroll control.
- ДДС: `Налоги с з/п`.
- P&L: строка `Налоги с ЗП` по ДДС, потому что payroll не содержит полный контур взносов работодателя.
- Исключение: если платеж общий, нужна разбивка между payroll taxes и прочими налогами.

### Маркетинг, сайт, приложение, сервисные расходы

- План: подрядчик, статья, период услуги.
- Документ: входящий документ ЭДО DocsInbox/СБИС, счет, акт, УПД.
- ДДС: дата оплаты.
- P&L: дата документа или период оказания услуги, правило нужно закрепить владельцем.
- Исключения: предоплата, документ на несколько услуг, одна оплата на несколько статей.

### Аренда и коммунальные

- План: договорный график или счет арендодателя/ресурсника.
- Документ: договор, счет, акт, платежка арендодателя.
- ДДС: факт оплаты.
- P&L: расход периода по договору/документу.
- Важно: отсутствие оплаты создает кредиторку, а не ноль расхода.

### Банковские комиссии и эквайринг

- План обычно не нужен, если комиссия списывается автоматически.
- Документ: банковская выписка/отчет эквайринга.
- ДДС: `Эквайринг`, `РКО`, `Прочие банковские комиссии`.
- P&L: комиссия периода; валовая выручка берется из iiko/заказов, не из нетто-зачисления.
- Исключение: интернет-партнер/StarterApp, где зачисление, комиссия и платформа должны быть разделены.

### Кредиты, займы, овердрафт

- План: график платежей, банк, тип части платежа.
- Документ: кредитный договор/график/выписка.
- ДДС: получение, погашение, проценты, комиссии.
- Баланс: получение увеличивает обязательство, погашение тела уменьшает обязательство.
- P&L: только проценты и комиссии, ниже EBITDA.

### Основные средства

- План: заявка на покупку ОС или крупного оборудования.
- Документ: счет/УПД/чек, акт ввода, owner decision по порогу ОС.
- ДДС: `Покупка ОС`.
- Баланс: создать актив, локацию, дату ввода, срок полезного использования.
- P&L: только амортизация по графику.
- Исключение: ремонт, расходник или улучшение — требует owner review.

### Внутренние переводы и собственник

- План: перевод между счетами, депозитный счет, cash movement или owner withdrawal.
- Документ: owner decision или cash movement record.
- ДДС: `Поступление — Перевод между счетами`, `Выбытие — Перевод между счетами`, `Возврат денег собственникам`.
- P&L: не влияет.
- Баланс: меняет деньги, капитал/расчеты с собственником или внутренние счета.

## Классификация и owner review

Автоклассификация может закрывать платеж без owner review только если:

- контрагент подтвержден или правило статьи стабильно;
- направление и тип операции совпадают;
- сумма и дата укладываются в ожидаемый платеж/документ;
- статья не требует бизнес-решения по периоду или роли;
- нет конфликта между bank merchant, DDS-контрагентом и документом.

Owner review обязателен для:

- бизнес-карты без чека или документа;
- нового контрагента;
- контрагента с несколькими возможными ролями;
- `Прочие расходы`, `Корретировки кассы`, `Покупка ОС`, `Возврат переплаты от поставщиков`;
- внутренних переводов, смешанных с payroll или собственником;
- любых строк, где оплата и документ относятся к разным статьям.

## Правила не-нулей

В приложении нужны статусы качества вместо автоматических нулей:

| Статус | Когда ставить |
| --- | --- |
| `no_bank_payment` | документа/начисление есть, оплаты нет |
| `no_document` | оплата есть, документа нет |
| `source_not_loaded` | источник не подключен или не выгружен |
| `not_applicable` | статья не применяется в периоде по бизнес-правилу |
| `confirmed_zero` | источник проверен, операций/документов нет, владелец или правило разрешает ноль |
| `legacy_not_active` | историческая статья, не активная в 2026 |
| `owner_review` | без владельца нельзя определить статью, период или роль |

## Контроль доступа и приватность

- Полные назначения платежей хранить только в защищенном банковском регистре.
- Payroll-строки сотрудников хранить только в payroll-модуле с правами HR/payroll.
- В управленческие handoff-файлы выводить агрегаты, статьи, роли и статусы без персональных сумм сотрудников.
- Для ЭДО хранить ссылки/ids и метаданные; вложения и документы защищать правами.
- Все ручные изменения статьи, контрагента, периода и P&L/balance posting должны попадать в audit log.

## Минимальный MVP платежного контура

1. Справочник контрагентов с owner status и payment roles.
2. Справочник ДДС-статей из `dds_article_map.csv`.
3. Импорт банковских операций T-Bank/Sber.
4. Очередь `owner_review`.
5. Связь bank operation -> DDS article -> counterparty -> source document.
6. ЭДО-реестр для маркетинга и сервисных расходов.
7. Payroll payment batch reconciliation.
8. Реестр ОС-кандидатов из платежей и документов.
9. Отчет `cash-flow vs P&L`: оплата, документ/начисление, разница периода, статус.
