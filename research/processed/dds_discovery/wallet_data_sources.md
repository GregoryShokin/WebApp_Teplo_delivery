# Карта источников данных по кошелькам ДДС

Дата фиксации: 2026-05-20.  
Последнее обновление: 2026-05-25.  
Источник: пояснение владельца 2026-05-20, уточнение migration blockers interview 2026-05-25.

## Назначение

Этот документ фиксирует, **откуда** и **как** должны подтягиваться данные для каждого кошелька / счёта ДДС в будущем веб-приложении. Без этой карты нельзя построить рабочий импорт ДДС и `wallet_balance_snapshots`.

| Wallet | Тип | Источник | Способ | Статус |
| --- | --- | --- | --- | --- |
| `Тинькофф` | банк | T-Bank Business Open API | REST | подключен |
| `Сбербанк` | банк | Sber API | REST + mTLS | подключен |
| `Альфа` | банк | — | — | `legacy_not_active` |
| `Сейф` | наличные | внутренний журнал | manual | `manual_only` |
| `ТК Черникова` | торговая касса | iiko Финансы → План счетов → Главная касса | `GET /reports/olap`, `report=TRANSACTIONS`, фильтр `Account.Name=Главная касса` | подключен read-only с 2026-05-20, см. [22-iiko-finance-chart-of-accounts.md](/app-spec/integrations/iiko/finance-chart-of-accounts.md) |

## Подробности по каждому кошельку

### 1. Тинькофф → T-Bank Business Open API

- **Юридический контур:** Т-Бизнес, расчётный счёт ИП Шокина в Т-Банке.
- **API:** [14-tbank-api-endpoints.md](/app-spec/integrations/tbank/api-endpoints.md).
- **Скрипт:** [research/scripts/tbank/export_statement.py](/research/scripts/tbank/export_statement.py).
- **Сырые выписки:** `research/private/tbank/statement_*.json`.
- **Размеченная:** `research/private/tbank/statement_classified.csv`.
- **Роль в контуре:** основной банк расходов (98% расчётов с поставщиками + ФОТ + налоги). Малая доля прямого эквайринга T-Bank (~4% выручки).
- **Статус:** подключен read-only с 2026-05-19.

### 2. Сбербанк → Sber API

- **Юридический контур:** СберБизнес, расчётный счёт ИП Шокина в Сбербанке.
- **API:** [12-sber-api-endpoints.md](/app-spec/integrations/sber/api-endpoints.md).
- **Скрипт:** [research/scripts/sber/export_statement.py](/research/scripts/sber/export_statement.py).
- **Сырые выписки:** `research/private/sber/...`.
- **Размеченная:** `research/private/sber/statement_classified.csv`.
- **Роль в контуре:** основная точка приёма выручки (эквайринг, интернет-эквайринг, переводы клиентов). Дальше деньги уходят на Т-Банк через цепочку `Sber → T-Bank → контрагенты`.
- **Статус:** подключен read-only с 2026-05-19.

### 3. Альфа

- **Статус:** `legacy_not_active` (подтверждено владельцем 2026-05-20).
- **Контекст:** рудиментарный счёт, не используется в 2026.
- **Поведение в приложении:** не создавать активный `wallet` запись; в миграции из Sheets — пометить флаг `active_flag=false`, сохранить как историю.
- **Сверки:** не участвует в текущих сверках 2026.

### 4. Сейф

- **Статус:** `manual_only` (подтверждено владельцем 2026-05-20).
- **Тип:** наличные деньги в физическом сейфе.
- **Источник:** внутренний кассовый журнал, ведётся вручную.
- **Способ ввода в приложение:** ручной с обязательной периодической инвентаризацией (рекомендуется ежемесячно + при крупных движениях).
- **Контроль:** `wallet_balance_snapshot` после каждой инвентаризации с подписью ответственного.
- **Открытый вопрос:** актуальность остатков в 2026 — есть ли реальное движение или это статичная сумма? Уточнить у владельца.

### 5. ТК Черникова → iiko Финансы → План счетов → Главная касса

Это **новая критическая интеграция**, не закрытая текущими API-картами.

#### Что такое ТК Черникова физически

- Торговая касса активной точки Черникова.
- Деньги физически лежат у администраторов на баре.
- Складывается из:
  - **наличной выручки** ежедневной торговой деятельности;
  - **депозитов курьеров** — администраторы собирают депозиты ежедневно для тех курьеров, у кого ещё не накоплен целевой депозит.
- Деньги тратятся на разные оперативные цели (без банка).

#### Где это в iiko

- Раздел: `Финансы` → `План счетов` → счёт `Главная касса`.
- **Эндпоинт iikoServer API:** не известен, требует разведки (отдельная задача — см. промт ниже).

#### Структура операции в iiko Главная касса

| Поле iiko | Назначение для DDS |
| --- | --- |
| `Дебет` | поступление на счёт |
| `Кредит` | расход по счёту |
| `Корсчёт` | основной ключ для определения статьи ДДС |
| `Комментарий` | контекст для классификации и owner review |
| `Статья ДДС` | заполняется автоматически только для счёта `Задолженность перед поставщиками`; для остальных пусто |

#### Виды дебетовых операций (поступления)

| Корсчёт / тип | Описание |
| --- | --- |
| Торговая выручка наличными | поступление от торговой деятельности (наличная часть выручки, не прошла через эквайринг) |
| `Депозиты сотрудников` (= депозиты курьеров) | удержание у курьеров для накопления целевого депозита; всегда курьеры, не другие сотрудники |
| Прочие зачисления | по факту, нужен анализ корсчетов |

#### Виды кредитовых операций (расходы)

| Корсчёт / тип | Описание |
| --- | --- |
| `Задолженность перед поставщиками` | автоматически попадает в статью ДДС `Оплата поставщикам` |
| Прочие корсчета | требуют rule engine на стороне приложения (комбинация корсчёта + комментария + суммы) |

#### Правило классификации для приложения

```text
если корсчёт == "Задолженность перед поставщиками":
    dds_article = "Оплата поставщикам"  # автомат из iiko
иначе:
    dds_article = rule_engine(corr_account, comment, debit_or_credit, amount)
    если правило не сработало:
        статус = "owner_review"
```

#### Связь с payroll-модулем

- `Депозиты сотрудников` в дебете Главной кассы должны:
  1. Порождать запись в `deposit_account` (см. [19-payroll-module-spec.md](/docs/business-control/19-payroll-module-spec.md), сущность `deposit_account`) с типом `Депозит удержание`;
  2. Не учитываться как выручка в управленческом отчёте;
  3. Связываться с конкретным курьером (employee_id).
- Возврат депозита при увольнении (`Депозит возврат`) — обратное движение из кассы.
- Списание невостребованного депозита (`Депозит списание`) — внутренний audit trail, не показывается в персональном отчёте курьера.

#### Качество данных в iiko на текущий момент

- **Колонка «Статья ДДС» в iiko не заполняется** для большинства корсчетов. Это означает: при импорте в приложение нельзя полагаться на iiko как на готовый классификатор — нужен собственный rule engine.
- На текущий момент в iiko корректно автоматизируется только корсчёт `Задолженность перед поставщиками` → `Оплата поставщикам`.
- Все остальные операции из Главной кассы при импорте получают статус `requires_owner_review` до построения правил.

#### Что нужно сделать перед использованием

1. Найти эндпоинт iikoServer API для чтения плана счетов и операций по счёту `Главная касса` — отдельная задача-разведка (см. промт ниже).
2. Зафиксировать структуру JSON.
3. Снять полный список корсчетов (как дебетовых, так и кредитовых) за период 2026-02..2026-05.
4. Сопоставить корсчета iiko → статьи ДДС нашего справочника `dds_articles` (с учётом aliases).
5. Прописать правила в `classification_rules` для каждого корсчёта.
6. Использовать `Депозиты сотрудников` / `Депозиты курьеров` как DDS/control source и сверять с payroll `deposit_account`; не создавать персональные payroll-события только из iiko без payroll-сверки.

### 6. ТК Гагарина

- **Статус:** `legacy_not_active`.
- **Контекст:** точка Гагарина закрыта с января 2024. Касса не работает.
- **Поведение в приложении:** не активировать, в миграции — пометить как историю.
- **Открытый вопрос:** есть ли «хвостовые» операции 2024-2026 по этой кассе, которые нужно отдельно классифицировать? Если есть — owner review case.

### 7. ГарантФонд

- **Статус:** `confirmed` по бизнес-смыслу; `requires_document` для суммы opening на 2026-02-01.
- **Owner decision 2026-05-25:** `ГарантФонд` - это депозиты курьеров, физически хранящиеся в Т-Банке.
- **Связанные источники:** T-Bank balance/выписка, iiko корсчет `Депозиты курьеров` / `Депозиты сотрудников`, payroll `deposit_account`.
- **Правило приложения:** использовать как wallet/control account депозитов курьеров; персональные обязательства и списания сверять с payroll, а не выводить только из iiko.

## Сводное правило для wallet_balance_snapshots

```text
для каждого активного wallet:
    opening_balance(period) = closing_balance(previous_period)
    + sum(cashflow_transactions.amount_signed where wallet_id and period)
    = closing_balance(period)

проверка сходимости с источником:
    closing_balance из приложения должен сходиться с
    - балансом банковского API (Sber, T-Bank) для банковских wallets;
    - балансом iiko Главная касса для ТК Черникова;
    - инвентаризационной записью для Сейф.
```
